# AD-093 — The App token is scoped to this repository and not to a list of verbs

- **status**: active

## Decision

1. **The App token is scoped with `owner` and `repositories`.**
2. **`permission-contents` and `permission-pull-requests` are not set**, so the token carries the App's own grant.

## Why

**The verb scope broke the release and the repository scope did not.** With both set, release-please reached
`Creating 1 releases for pull #11` and failed with
`Resource not accessible by integration — /rest/releases/releases#create-a-release`. Creating a GitHub Release is
nominally `contents: write`, which was granted, so something else in that call falls outside the two verbs named.
Rather than guess which, the narrowing is removed: it was copied from a repository that uses it successfully for a
different release configuration, and copied without measuring what this one needs.

**The repository scope is where most of the value was anyway.** An App token defaults to everything the App can
reach across every repository it is installed on. `owner` plus `repositories` bounds a leaked token to this
repository, which is the difference between one repository and an organisation. The verb list would have narrowed it
further, from "everything here" to "two verbs here", and that increment is what cost the release.

**This is the third thing today that was adopted from another repository and did not transfer.** `--admin` did
transfer and was the answer to a real problem. `persist-credentials: false` transferred. The verb scope did not,
because it depends on the exact API calls the tool makes, and those differ between two release configurations that
look identical from the outside.

## Trade-offs

**A token that can do everything the App can do, in this repository.** The App is installed for release automation
and holds `contents` and `pull-requests`; the token now carries both in full rather than the subset. What bounds
the blast radius is the repository scope and the fact that the token is minted inside `release.yml` and revoked when
the job ends.

**Which call needs more than `contents: write` is still unknown.** Finding out means bisecting the permission list
against a live release, and each attempt costs a release cycle. The question is recorded rather than answered.

## Not decided here

- **Which permission release creation actually requires.** Worth knowing, expensive to bisect.
- **Whether the App's own grant should be narrowed at the App level**, which would apply to every repository it is
  installed on and is the operator's setting rather than this repository's.

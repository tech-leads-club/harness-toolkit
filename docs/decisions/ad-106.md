# AD-106 — A build step's own exit code cannot be the publish guarantee when it is also a recovery path

- **status**: active

## Decision

1. **`bin/tlc-build.mjs` imports its schema generator dynamically**, and treats `ERR_MODULE_NOT_FOUND`
   specifically as a reason to skip schema generation rather than fail the script.
2. **The dist bundle rebuild above it is unaffected either way** — it has no devDependency-only step,
   so it is not what this decision is about.
3. **`tools/dev/verify-package.mjs`'s `assertPayload` requires `schema.json`** in the packed tarball,
   alongside the runtime files it already required. This runs before the `publish` environment's human
   approval, on every release.
4. **The build script's exit code is not the publish guarantee.** Only the packed artefact is.

## Why

**`bin/tlc-build.mjs` is not only a build script — `bin/tlc-exec.mjs` tells a production install with
a missing `dist/` to run it directly**, as the recovery path AD-097 left in place once the installers
that used to rebuild it were deleted. A `typescript-json-schema` devDependency is never present on that
machine, so a hard failure there would break the one thing the message promises: that running this
command fixes a broken install.

**The same `catch` cannot distinguish two different failures that produce the identical error code.**
`ERR_MODULE_NOT_FOUND` fires whether the generator module itself is missing (once true, before it moved
to `bin/generate-schema.ts` — see the file's own history) or whether `typescript-json-schema` is missing
underneath it in a development or CI environment where it should be installed. A `prepack` run with a
genuinely broken `node_modules` — a botched `npm ci`, a resolution failure — degrades exactly the same
way a healthy production install does, and nothing inside `bin/tlc-build.mjs` can tell those apart.

**So the question moved from "did the step run" to "did it produce what the tarball needs."**
`verify-package.mjs` already reads npm's own packed file list before anything installs — it is the one
place in the release pipeline that already asserts required files are present, and it runs before the
human approval on `publish`, not after. Adding `schema.json` to that list is the one assertion that
holds regardless of which of the two failures actually happened, because it asks the question a
reviewer would ask anyway: is the artefact this feature exists to ship actually in the box.

## Trade-offs

**A broken `typescript-json-schema` during local development still fails at `node bin/tlc-build.mjs`
immediately**, same as before — a resolvable module whose code throws is not `ERR_MODULE_NOT_FOUND` and
is not caught by this exception. Only a *missing* module degrades. A contributor who runs the script
without ever having installed devDependencies gets the intended skip; a contributor whose install is
broken in some other way still gets a hard failure at the point it happens.

**The two checks live in two files and can drift.** `bin/tlc-build.mjs` decides what degrades;
`verify-package.mjs` decides what is required. Nothing ties them together beyond this record — a future
devDependency-only generation step added to `bin/tlc-build.mjs` needs its own line in `assertPayload`,
and there is no test that would catch a step that forgot one.

## Not decided here

- **Whether other build-time-only, devDependency-gated steps should adopt this same split.** This
  record covers `schema.json` because it is the one that exists; a second such step is a future
  decision, not a precedent this one claims to set on its own.
- **A single mechanism that derives the required-artefact list from what degrades**, instead of two
  hand-maintained lists. Worth doing once there is a second case to generalise from, not before.

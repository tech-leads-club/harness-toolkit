# AD-128 — Every provider wiring writer backs up the target file before overwriting it

- **status**: active

## Decision

Add a shared `src/platform/config-backup.ts` module with two exports:

- `backupPathFor(targetPath, now?)` — returns `<targetPath>.<ISO-8601 timestamp with : and . replaced by ->.bak`
- `backupBeforeWrite(targetPath, existingText, now?)` — writes `existingText` to the timestamped backup path

Call `backupBeforeWrite` from every provider writer that changes a file on disk:

1. `applyClaudeWiring` — when `existingText !== null` and the merge reports `changed`
2. `applyCodexWiring` — when `existingText !== null` and the merge reports `changed`
3. `applyCursorWiring` — when `existsSync(targetPath)` before the `writeFileSync`
4. `applyOpencodePluginWiring` — when `existsSync(targetPath)` before the `writeFileSync` (both managed-write and `--force` overwrite paths)
5. `applyVSCodeWiring` — when `existsSync(targetPath)` before the `writeFileSync`

Never back up when no file existed (a fresh install writes, but there is nothing to snapshot), and never back
up when the file exists but the merge reports `unchanged` (the write is skipped).

Backups are never rotated or pruned — the timestamp in the filename is the disambiguator, and a human who
needs one picks the right one.

## Why

**A merge that mangles a foreign entry has no recovery path without a backup.** Three of the five targets are
shared documents — Claude's `settings.json` carries `permissions`, `sandbox`, and `env` alongside our hook
groups; Codex's and Cursor's `hooks.json` files carry entries from other tools. The merge function is supposed
to preserve foreign entries byte-for-byte, but a defect in the merge logic would silently drop them. A
timestamped `.bak` written before the write gives the operator something to diff against.

**The other two targets are replaced wholesale, which is the case that needs the guard more, not less.**
OpenCode's bridge plugin and VS Code's hook file are generated text — there is no merge to audit. A defect in
the generator that writes a broken bridge leaves the operator with a non-functional opencode until they
reinstall or hand-restore. The backup is the only automated recovery.

**The pattern already exists in the upstream project.** paypal-stargate (`src/platform/config-backup.ts`)
added the same helper and wired it into the same call sites after encountering this class of failure. Porting it
here prevents re-discovering the same lesson.

## Trade-offs

**Backups accumulate and are never cleaned up by the tool.** A machine that runs `tlc harness update` twenty
times over a month has twenty `.bak` files in `~/.claude/`. The operator who never needed one sees clutter;
the operator who does need one sees the exact version they need. The timestamp in the filename makes it
obvious which is which, and automatic pruning is what would delete the right one.

**The backup is a raw file copy, not a structured snapshot.** A merge that corrupts a foreign entry and a
merge that drops our own entries produce the same `.bak` — the operator has to know which one they are
restoring from. A structured backup with metadata about what changed would be more informative, but it would
also be a second format to maintain and a second thing to go wrong.

**VS Code is backed up like every other provider, not deferred.** The VS Code provider is preview
([/decisions/ad-126.md](/decisions/ad-126.md)),
and its wiring writer was the only one that had no backup path at all before this change. The decision here
treats preview the same as stable — the backup costs one `writeFileSync` and is just as useful whether the
provider is preview or not.

## Not decided here

- **Rotation, pruning, or a retention policy.** The files are never deleted by the tool. An operator who
  wants cleanup runs `rm` themselves, and the shape (`<target>.<timestamp>.bak`) makes that safe to
  automate in a cron job.
- **Whether the `--force` path should back up too.** It already does — `applyOpencodePluginWiring` and
  `applyVSCodeWiring` both back up before overwriting a foreign file, because that is the most destructive
  path this writer has and the one where a backup cannot be skipped.
- **Adding backup to `uninstall`.** The uninstall path reads files it changes (`unmergeClaudeSettings`,
  `unwireCursorHooks`) but writes them through the same wiring functions, which now back up. The backup
  before the uninstall write is implicit in those functions.

# AD-128 — `pr-open` and `push` recognize their `gh api` equivalent, and `pr-merge` exists

- **status**: active

## Decision

1. **`rules.trigger.ts` gains a second matching primitive, `matchesApiShape`**, alongside the existing
   phrase-based `matchesShape`/`containsPhrase` ([/decisions/ad-127.md](/decisions/ad-127.md)). It parses a
   `gh api <path> [flags]` invocation's endpoint path (segments, stripped of query string, scheme and host) and
   infers its effective HTTP method — an explicit `-X`/`--method`, else `POST` when a body flag (`-f`, `-F`,
   `--input`) is present, else `GET` — confirmed against `gh api --help`'s own documented default-method rule,
   not assumed.
2. **`pr-open` recognizes `POST` to a path ending in `pulls`** as the same act as `gh pr create` — the exact
   incident's shape. **`push` recognizes `POST`/`PATCH` to a path containing the adjacent segments `git`,
   `refs`** as the same act as `git push` — the analogous, not-yet-evidenced case, closed in the same change.
3. **A new `pr-merge` trigger kind** joins `pr-open`/`commit`/`push`/`stop` as a fifth bare trigger word. It
   fires on `gh pr merge` (CLI) and on `PUT` to a path whose last segment is `merge` and which contains `pulls`
   earlier — GitHub's actual merge endpoint — never on an unrelated `PATCH` to a bare `pulls/{number}` path (a
   title edit, say), which the last-segment check excludes by construction. It also joins
   `FULL_BATTERY_KINDS` (`src/entrypoints/ship-gate.ts`), so the same lint/test/docs battery `push`/`pr-open`
   already pay runs before a merge too.
4. **`docs/concepts.md`'s operator-rules section is corrected**, not merely extended: its trade-off sentence
   named `gh api instead of gh pr create` as an unconditional escape, which is no longer accurate for the two
   shapes this record closes. The remainder — GraphQL, `curl`, a browser, a `gh api` `PATCH` that sets
   `draft:false` on an existing PR — is restated, not silently dropped. The section gains an explicit,
   actionable recommendation: GitHub branch protection with a required status check, and bypass disabled for
   any automation actor, is the boundary that actually closes what a local trigger cannot — this project's own
   rule mechanism has always been a fast local nudge in front of that boundary, never a replacement for it,
   and this is the first place that is written down for an operator to act on.
5. **[/decisions/ad-100.md](/decisions/ad-100.md)** keeps `status: active` — its reasoning for why the
   mechanism is policy rather than containment remains entirely correct — and gains a prose correction note
   pointing here, the same pattern [/decisions/ad-125.md](/decisions/ad-125.md) used when
   [/decisions/ad-126.md](/decisions/ad-126.md) corrected it. Its `Decision`/`Why`/`Trade-offs` text is left
   exactly as written.

## Why

**The incident was the accepted trade-off being used, not a bug being found.** `docs/concepts.md` and AD-100
already said, before this incident happened, that `gh api` escapes `gh pr create`. An agent ran `gh pr create`,
was blocked, read the failure message, and — within the same turn, 66 seconds later — ran
`gh api repos/{owner}/{repo}/pulls -f title=... -f head=... -f base=...`, the identical REST call `gh pr
create` itself sends, which is not gated by any CLI-subcommand pattern. This distinguishes it from
[/decisions/ad-127.md](/decisions/ad-127.md): that record fixed a matcher that should have fired and silently
didn't; this one narrows a gap the project's own design already knew about and named.

**Narrowing an accepted gap is still worth doing, and the reasoning is the same each time.**
[/decisions/ad-121.md](/decisions/ad-121.md)'s basename fallback and AD-127's position-agnostic scan both
closed one concrete, evidenced instance of a wider, still-open class without claiming to close the class
itself. This record follows the same shape: `gh api` still escapes for GraphQL, `curl`, a browser, and a
`PATCH`-to-ready call this project does not parse a request body for — all named explicitly in the corrected
documentation, not silently assumed closed.

**The detection has to be grounded in the actual REST semantics, or it trades a false negative for a false
positive.** `gh api repos/{owner}/{repo}/pulls` with no parameters is a `GET` — listing open pull requests, the
single most common, entirely harmless use of that endpoint. A detector matching on path words alone (the same
`containsPhrase` primitive the CLI shapes already use) would fire on every such read, training an operator to
distrust or disable the rule the same way an over-eager antivirus trains a user to click through warnings. The
method has to be inferred correctly — `gh api --help`'s own text was read for this, not guessed — for the
narrower fix to be worth shipping at all.

**`pr-merge` closes a gap that has nothing to do with `gh api`.** A pull request merging is performed by
GitHub itself, server-side, whether triggered by `gh pr merge`, a click in the browser, or an API call — it is
never a local `git push`. An operator's `push`-triggered rule, however well it matches every wrapper and every
REST equivalent, structurally cannot see this moment, because the moment does not run on the operator's
machine at all when it happens through the ordinary GitHub merge flow. `pr-merge` is the trigger kind that
makes gating it possible at all, which no amount of widening `push`'s detection could have done.

**The durable fix was never going to be a better pattern matcher, and the documentation now says so.** Every
detection this record adds, and every one AD-127 added before it, is defense in depth for a cooperative agent —
a fast, local, useful nudge. None of it is a guarantee against a client that chooses another path, because the
client surface (CLI verbs, REST paths, GraphQL mutations, a browser tab) is not a closed set this project's
code can enumerate completely, and was never claimed to be one. GitHub's own branch protection, enforced
server-side at merge time regardless of which client opened or attempted the merge, is the boundary that
actually closes the remainder — and until this record, that recommendation existed nowhere an operator reading
this project's own documentation would find it.

## Trade-offs

**Two matching primitives now do conceptually the same job in one file.** `matchesShape` reads CLI-subcommand
words; `matchesApiShape` reads a REST path and an inferred method. Forcing one grammar into the other's shape
would read as unification but cost precision on both sides — a `ShellShape` widened with optional
path/method fields would be mostly-empty every time `matchesShape` is the one called. The duplication is of a
declarative *table*, not of an *algorithm*: `matchesApiShape` still reuses `findPhraseIndex`/`tokenMatches`,
the same primitives `matchesShape` and `matchesPhrase` already share.

**`gh api` detection still has real gaps, named rather than hidden.** GraphQL mutations
(`gh api graphql -f query='mutation { createPullRequest ... }'`), raw `curl`/`wget` direct to
`api.github.com`, and a `gh api` `PATCH` that flips `draft:false` on an existing pull request (the API
equivalent of `gh pr ready`) all still escape every trigger this record adds. Each would need a materially
different detector — parsing an arbitrary query string for a mutation name, or inspecting request-body field
values rather than only the path and method — and none is evidenced as exploited. Named explicitly in
`docs/concepts.md` rather than left for the next incident to rediscover.

**`pr-merge` joining `FULL_BATTERY_KINDS` mostly no-ops in the common case.** At merge time there is usually no
local uncommitted diff, so `scope.codeTargets`/`scope.testTargets` are empty and the lint/test steps abstain —
not a gap, since the commits being merged already ran this same battery at their own push/pr-open time, but
worth stating plainly so a future reader does not mistake the abstain for a bug.

**This project's code cannot configure branch protection on any operator's repository.** The recommendation in
`docs/concepts.md` is guidance an operator acts on themselves, in their own repository's GitHub settings — not
a capability this harness gained. The gap between "documented" and "done" on any specific repository (including
the one this incident happened in) is the operator's to close.

## Not decided here

- **GraphQL mutation detection, `curl` detection, or `gh api` body-field inspection for the `ready` shape.**
  Named above as still-open; none is built here.
- **A `doctor` check that verifies an operator's repository actually has branch protection configured**, which
  would require this project's code to call GitHub's API against a specific repository and hold credentials to
  do so — a materially larger capability than reading a local shell command, and not evidenced as needed by any
  report yet.
- **Auditing every other built-in trigger for the same class of gap.** `commit` was not touched — this project
  has not observed a `gh api` equivalent for `git commit` in any real workflow, and inventing one to close
  speculatively would be exactly the kind of ungrounded scope this decision's own reasoning argues against.

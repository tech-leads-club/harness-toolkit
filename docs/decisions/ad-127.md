# AD-127 — A rule's shell triggers match the act at any word position, not only at word 0

- **status**: active

## Decision

**`matchesShape` (`rules.trigger.ts`) no longer anchors its check to word index 0.** The prefix comparison that
used to live in `startsWithShape` — `prefix.every((token, index) => words[index] === token)` — is replaced by
`containsPhrase`, a new shared helper that tries every starting index in the tokenized command and requires the
shape's words to match contiguously from there, using the same `tokenMatches` equality (including its
[/decisions/ad-121.md](/decisions/ad-121.md) basename fallback) `matchesPhrase` already used for operator-written
`command(<pattern>)` triggers. `matchesPhrase` itself is now expressed in terms of `containsPhrase`, so the
built-in `pr-open`/`commit`/`push` shapes and an operator's own pattern share one scan instead of two.

No wrapper, proxy, or prefix is named, listed, or special-cased anywhere in this change. That is the point: the
fix is a property of the matcher, not a fact about any particular tool that happens to sit in front of a command
today.

## Why

**A real, enabled rule with a correctly placed configuration never fired, and the cause was confirmed by reading
the matcher, not guessed.** The rule's trigger was `pr-open`; the command that opened the pull request the rule
was supposed to gate was recorded, verbatim, with a prefix in front of `gh pr create` — the operator's shell
routes commands through a transparent local proxy before they reach the real program. `startsWithShape` compares
`words[0]` against `"gh"` and nothing else; with a prefix in front, `words[0]` is never `"gh"`, and the function
returns `false` on every single invocation, forever. Nothing about the rule, the config, or the wiring was wrong.
The trigger itself could not see past its own anchor.

**This project already had the correct shape for this problem, in the same file, for a different trigger kind.**
`command(<pattern>)` triggers and `command(...)` proofs both go through `matchesPhrase`, which has scanned every
starting index in the tokenized word list since it was written — `x && gh pr review 42` matches `command(gh pr
review)` today because the scan does not require the phrase to start the command. `startsWithShape` was a second,
narrower implementation of essentially the same idea, written only for the three built-in shapes, and it never
inherited that scan's tolerance. One correct algorithm existed in this codebase; the defect was that a second,
weaker one was written next to it instead of reused ([/decisions/ad-100.md](/decisions/ad-100.md) — one
tokenizer, because a second splitter is the duplication that drifts).

**An enumerated list of known prefixes was considered and rejected.** The alternative — keep the position-0
anchor, but skip past a fixed list of recognized wrapper names before checking it — only closes the gap for
prefixes someone thought to add to the list in advance. The list this project already keeps for a related purpose
(`floor.verb.ts`'s `WRAPPERS`, used to decide ask/deny tiers for destructive or network shell effects) exists for
a different question and at a different layer, and even there it is a fixed set that a new, unlisted wrapper does
not appear on. Applying that same fixed-set shape to trigger matching would fix exactly one prefix at a time and
leave the structural gap — any prefix not yet on the list — open for the next one. A scan that does not need to
know what a wrapper is called closes the whole class at once, and costs nothing extra: the tokenized word list
for a single shell command is short, and `matchesPhrase` has run this same scan in production, on this exact
class of input, without incident.

## Trade-offs

**The shape's words can now match when they appear as unquoted, literal arguments to an unrelated command, not
only when the act is actually invoked** — e.g. an unquoted `echo gh pr create` would now be read the same as
running it. This is not a new risk this fix introduces: it is the same trade-off `matchesPhrase` already made,
silently, for every operator-written `command(<pattern>)` trigger and proof since it was written, and the two
directions of error are not symmetric. A false negative here is a security-relevant rule silently never
evaluating — the exact incident this record exists to close. A false positive is, at worst, a rule evaluating (and
asking for or checking a proof) once against a command that merely mentioned the words, and the common real shape
of "mentioning" rather than "running" — a quoted string — is still excluded, because the tokenizer yields one word
for a quoted argument regardless of where the scan starts.

**`docker commit`, or any other unrelated command that merely contains one of a shape's words, still does not
match** — the scan requires every word in the shape's prefix to match contiguously from some starting index, so a
single shared word is not enough. Verified directly: `docker commit abc image` does not fire the `commit`
trigger, which means `git commit`, before or after this change.

**A wrapped invocation of the real verb by its full path now also composes with the AD-121 basename fallback**
(`time /usr/local/bin/gh pr create` now fires `pr-open`, where the old anchored, `===`-only check would have
missed it even without a wrapper in front). Not a separate decision — `containsPhrase` reuses `tokenMatches`
wholesale rather than a narrower comparison, so this followed from closing the same root cause the wrapper case
exposed, not from a second fix.

## Not decided here

- **Whether the floor's own `WRAPPERS`-based classification (`floor.verb.ts`, `shell-policy.service.ts`) should
  move to the same position-agnostic shape.** That code answers a different question — how severe is this shell
  effect, at this posture — and reads the *first* verb specifically to attach a severity to it, which a scan that
  ignores position cannot do the same way. Left untouched here; not audited for the same defect class.
- **A trigger kind for an operator to declare "this exact word must be the first word of the command."** No rule
  in this project has asked for that shape; `command(<pattern>)`'s scan-anywhere semantics have covered every
  case reported so far, including this one.

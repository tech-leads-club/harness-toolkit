# AD-126 — the VS Code writer ships complete and is never dispatched, because Agent Hooks are Preview and the hook file schema is unpublished

- **status**: active

## Decision

`vscode-hooks-json` joins `ProviderWiringKind` (`src/providers/provider.port.ts`) with a real writer.
`vscodeWiring` (`src/providers/vscode/vscode.wiring.ts`) targets `~/.copilot/hooks/tlc-harness.json`,
`strategy: "replace"`, one entry per event VS Code documents, each launching with `--provider vscode` because
this host has no content fingerprint. `renderVSCodeHooksText` produces the document, asserted against a golden
file.

Nothing calls it. All three dispatchers take an explicit deferral branch:

| Call site | Branch | Effect |
| --- | --- | --- |
| `applyProviderWiring` (`bin/write-user-hooks.mjs`) | `case "vscode-hooks-json"` | returns `status: "deferred"`, writes no file, does not fail the install |
| `providerWiringStatus` (`tools/doctor.ts`) | `case "vscode-hooks-json"` | returns the new `"deferred"` status, printed as an `ok` row carrying the reason |
| `applyPlan` (`tools/init-project.ts`) | `DEFERRED_PROJECT_SHIMS` + the `vscode` outcome | names `.github/hooks/tlc-harness.json`, creates nothing, prints why |

One string, `VSCODE_DEFERRAL_REASON`, carries the reason to all three, so the operator reads the same sentence
wherever they meet it and no call site can drift into its own wording.

## Why

**Two facts hold the deferral, and either alone is enough.**

1. **Agent Hooks are Preview.** The payload format is not frozen. `vscode.inbound.ts` already tolerates the two
   spellings GitHub publishes, but tolerance is not a promise, and a wiring file written today addresses a
   contract that can change without notice.
2. **The hook file's own schema is not published.** The VS Code page names the discovery locations
   (`.github/hooks/*.json` for a workspace, `~/.copilot/hooks` for a user) and the exit-code contract; neither it
   nor GitHub's reference inlines the file's shape. What `renderVSCodeHooksDocument` emits is the shape of the
   host whose payloads VS Code reuses byte for byte — the best-supported guess available, and still a guess.

Writing a guessed format to a real path is the failure this whole feature exists to prevent, one layer up: a file
that looks installed, is parsed by nobody, and reports as wired. The hazard is worse on this host than on any
other, because VS Code reads `.claude/settings.json` by default, so an operator with Claude wiring already has
VS Code running hooks against tool names the Claude parser does not know (design §10, and the doctor check T19
adds).

**The alternative — leave the adapter unwritten until GA — is worse.** It ships nothing and it learns nothing.
The adapter as written is the artifact that makes the eventual GA change small: detection, capabilities, parsing
and rendering are settled and tested against documentation-derived fixtures, and the remaining work is one branch
deletion in three files.

**Deferred is a status of its own, not a refusal and not a warning.** A refusal tells an operator to fix
something they cannot fix. A warning that nothing on the machine can clear is the defect
[/decisions/ad-034.md](/decisions/ad-034.md) records — it fires on every run of a correctly configured machine
until it is scrolled past. The `ok` row states the position and moves on.

## Correction — the schema is published, and the deferral stands on the other fact

Fact 2 above is withdrawn. VS Code has published the hook file's schema
(<https://code.visualstudio.com/docs/agents/reference/hooks-reference>, read 2026-09-05), and the guess this
record labelled as one was wrong in three ways: each event maps to a flat array of command objects with no group
wrapper, `command` is a single shell command line rather than an argv array, and `matcher` is inert — quoted
verbatim, "Currently, VS Code ignores matcher values, so hooks run on all tool invocations regardless of the
matcher". `timeout` is in seconds and defaults to 30. `renderVSCodeHooksDocument` and the golden file now emit the
vendor's shape.

Fact 1 is untouched and holds the deferral by itself: Agent Hooks are Preview, and the reference states "The
configuration format and behavior might change in future releases." `VSCODE_DEFERRAL_REASON` no longer claims the
schema is unpublished; it names Preview and the vendor's own change warning.

This also narrows what the trade-off below fears. The golden file still pins what the writer emits rather than
what VS Code accepts, but what it emits is now read off the vendor's page instead of borrowed from another host.

## Correction — the schema is published, and the user-level writer is dispatched

This record rested on two facts. One has since fallen.

VS Code now publishes the hook file schema and the per-event input/output contract
(<https://code.visualstudio.com/docs/agents/reference/hooks-reference>, read 2026-09-05). The shape this adapter
emitted was a guess borrowed from the host whose *payloads* VS Code reuses, and the guess was wrong in two ways:
it carried Claude's group wrapper (`event -> [{ hooks: [command] }]` where the vendor has `event -> [command]`),
and it emitted `args` as an array where `command` is a single shell command line. Both are corrected, and the
deferral is what kept the wrong shape off every machine in the meantime.

**`tlc harness install` now writes `~/.copilot/hooks/tlc-harness.json`.** Ownership is decided by the launcher
path every emitted `command` names, rather than by a marker field of our own — the schema enumerates the keys a
hook object may carry, and adding one it does not document would be the same class of guess this correction
removes. A file at that path whose commands do not all name our launcher is refused, not overwritten.

`ProviderWiringStatus` loses its `deferred` member. Every kind in the union now has a writer that runs, so a
status no branch can return would be a row an operator can never see — the [/decisions/ad-034.md](/decisions/ad-034.md)
defect in a different costume.

**What stays deferred is the project shim.** `.github/hooks/tlc-harness.json` is still not written, and that is
scope rather than doubt: the workspace surface has no presence probe and no entry set pointing at a project
launcher, so dispatching it would mean inventing a surface rather than enabling a finished one.

**What has not changed:** Agent Hooks are still Preview, quoted from the reference — "The configuration format
and behavior might change in future releases". Writing against a published schema that may move is a different
risk from writing against a guess, and it is visible and reversible: the file is ours, named, and refused if
touched. The T19 mismatch hazard still fires, and matters more now — VS Code reads `.claude/settings.json` by
default, so an operator who wires both will have two hook sets live at once.

## Trade-offs

**The writer is code nobody runs, which is the class of code that rots.** Its only defence is the golden-file
test, and a golden file pins what the writer emits, not what VS Code accepts — so it will keep passing while
being wrong about the host. That is a real cost and it is accepted for one reason: the alternative was writing
the guessed format to a real path.

**The deferral is held by three branches rather than one flag.** A single `if (deferred)` at the top of the
registry loop would be shorter, and it would also skip the host everywhere at once — including in doctor, which
should still say something. Three explicit branches cost three edits at GA and, in exchange, each call site
states its own behaviour.

**`~/.copilot` decides whether this host is present at all**, so `doctor` prints the deferral row only on a
machine that has it. On every other machine the row reads "not installed", which is accurate but hides the
deferral from exactly the reader who might otherwise ask for it. Judged the better noise trade.

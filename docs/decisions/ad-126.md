# AD-126 — The provider scaffold is a contributor tool; it never belonged on the published CLI

- **status**: active

## Decision

`tlc harness new-provider` is removed from `bin/tlc-cli.ts` entirely — no import, no `Action` union member, no
`route()` case, no dispatch case. `route(["new-provider", ...])` now resolves exactly the way any other
unrecognized command does. The scaffold logic (`scaffold`, `scaffoldFiles`, `validateProviderName`,
`appendProviderToRegistry`, `runNewProvider`) lives at `tools/dev/new-provider.ts` — a directory
`package.json`'s `files` list already excludes from the published package — with its own `import.meta.main`
entry point. The one supported way to scaffold a provider adapter is `node tools/dev/new-provider.ts <name>`,
run from a clone of this repository, by someone about to hand-write the adapter and open a pull request against
this repository's own source.

`AD-125`, which recorded the original (wrong) decision to publish this as a CLI subcommand, is marked
`superseded by AD-126` below — its `Decision`/`Why`/`Trade-offs` text is left exactly as written, because it
accurately describes what was believed and decided at the time. This record exists to correct the standing,
not to rewrite the history.

## Why

**A real install's runtime home has no durable place for a scaffolded provider to live, and this was checked
against the actual mechanism, not assumed.** `tools/install-runtime.ts`'s `RUNTIME_PAYLOAD` — `["bin",
"capabilities", "dist", "docs", "skills", "src", "tools", "config.example.json", "package.json"]` — is the list
every `tlc harness update` deletes (`rmSync(to, { recursive: true, force: true })`) and re-copies from the
installed npm package, in full, on every run. `src` is in that list, so `src/providers/<name>/` is too.
`OPERATOR_OWNED` — `["config.json", "state", "flags", "rules"]`, the only paths an update spares — does not
include it. Verified directly against a real installed copy: `~/.tlc/harness/src/providers/` mirrors this
repository's own `src/providers/` exactly, confirming the runtime home really is a full materialized copy, not
a thin shim. A provider scaffolded there survives until the user's very next update, and nothing warns them.

**Even before an update destroys it, the scaffold has no effect on a real install without a manual step most
users have no reason to take.** The Node fallback path runs from `dist/*.mjs`
([/decisions/ad-012.md](/decisions/ad-012.md)); a newly scaffolded `src/providers/<name>/` is not in `dist/`
until someone runs `tlc harness build`, which needs Bun or esbuild — a toolchain this project's own runtime
model exists specifically to make optional for *using* the harness, not for extending it.

**The earlier fix (the commit that moved the module from `tools/dev/` to `tools/` so the CLI's import would
resolve in a real install) treated the symptom, not the defect.** That commit was correct on its own narrow
terms — it made a broken `import` in a published file resolve — but it never asked whether the subcommand
should have been reachable from a published install at all. The broken import was a *visible* failure (the
command crashed); the wrong reachability was a *silent* one (the command appeared to work, then quietly stopped
mattering). Fixing the loud failure without re-examining the premise it exposed is exactly the gap this record
closes.

**The defect was found by the harness's own operator asking the right question, not by any gate in this
pipeline.** Neither the full `tlc harness test` gate, the discrimination sensor two independent Verifier passes
ran against the `provider-scaffold` feature, nor `verify-package.mjs`'s clean-install check caught this — all of
them confirmed the command *ran*, none of them asked whether what it wrote would *survive* on a real machine.
That is a real gap in this project's own verification coverage for any future CLI subcommand that writes to the
runtime home, not merely a one-off mistake in this feature. No new gate is added by this record (see Not decided
here) — the gap is named so it can be closed deliberately, not left implicit.

## Trade-offs

**`v0.11.0`, already published to npm, ships the removed subcommand.** This record's fix does not retroactively
repair an already-installed copy — a user who installed `v0.11.0` before this fix's release still has the
broken command until they run `tlc harness update` to the version that carries this fix. There is no mechanism
to recall a published npm version; the only remedy is shipping the correction in the next release and letting
the existing update path carry it forward, the same way any other fix reaches an installed machine.

**A contributor now needs a repository clone to scaffold a provider — there is no "download this later" middle
ground.** This is the intended trade-off, not an accepted cost: the scaffold's only coherent audience is someone
about to commit to this repository's own source tree, and a clone is the correct place for that regardless of
this defect.

## Not decided here

- **A gate that would have caught this defect systematically** — for instance, one that checks any command a
  CLI subcommand writes against `RUNTIME_PAYLOAD`/`OPERATOR_OWNED` for survivability across an update. Named as
  a real gap above; building it is future work, not required to close this specific defect.
- **Whether other existing subcommands have the same class of defect.** Not audited here — this record closes
  the one reported and confirmed instance.

# AD-141 — Cursor's empty-string cwd no longer outranks the real project root

- **status**: active

## Decision

1. **`cursor.inbound.ts`'s `shell.before` mapping now uses `if (cwd)` instead of
   `if (cwd !== undefined)`** when deciding whether to set `event.cwd` from the raw payload's `cwd`
   field. An empty string no longer promotes onto the event.
2. **A regression test** (`src/providers/cursor/__test__/cursor.inbound.test.ts`) asserts a
   `beforeShellExecution` payload with `cwd: ""` produces `event.cwd === undefined` — the same as if
   the field were absent.

## Why

**Found live, during a workshop demo rehearsal.** A `review-before-pr` operator rule (`require:
command(review.sh) since HEAD`) denied a `gh pr ready` call even though
`.tlc/harness/state/rule-observations.jsonl` held a matching `command(review.sh)` observation recorded at
the exact same HEAD sha the check should have used. Replaying that exact observation, rule, and context
through `missingProofs()`/`proofSatisfied()` (`src/core/rules/rules.proof.ts`) directly returned no missing
proofs — the matching logic was correct given that data, so something upstream computed a different
context than what was recorded.

**Reproduced directly, not assumed.** The raw Cursor payload for the failing tool call, read from
`.tlc/harness/state/audit.jsonl`, showed `"cwd":""` on the event. Feeding an equivalent fabricated payload
(`{ hook_event_name: "beforeShellExecution", cwd: "", workspace_roots: [<demo repo>] }`) through
`cursorToEvent` → `shaScopeRoot` → `currentGitSha` reproduced the defect exactly: `event.cwd` came out as
`""` (not `undefined`), `shaScopeRoot`'s `event.cwd ?? event.projectDir`
([/decisions/ad-114.md](/decisions/ad-114.md)) picked the empty string
over the real project root, and `currentGitSha("")` resolved against whatever directory the calling
process's own OS-level cwd happened to be — in the reproduction, a completely unrelated repository's sha.

**AD-114 already got the intent right; this was an adapter-boundary translation gap.** AD-114's own
Decision item 1 says `event.cwd` should be "absent everywhere else (never guessed)" — an empty string is
not a real cwd, so it should have counted as absent too, but the boundary code compared against
`undefined` literally instead of checking for a real value. `claude.inbound.ts` already handles the
identically-named field with `if (cwd)` (a truthy check) rather than an `undefined` comparison — this
fix makes `cursor.inbound.ts` consistent with the pattern its sibling adapter already used, rather than
inventing a new one.

**Fixed at the adapter boundary, not in `shaScopeRoot`.** `shaScopeRoot`'s `??` is correct for what it
promises: prefer `event.cwd` when the provider reports one. The defect was Cursor's adapter reporting a
value (`""`) that does not actually mean "here" — translating a vendor's payload quirk into the shared
contract's true meaning is exactly the job of the provider adapter, not the shared entrypoint that reads
it. Fixing at the boundary also means every other consumer of `event.cwd` (comment-policy's diff scoping,
duplication, `ship-gate.ts`, `stop.ts`) is corrected by the same change, with no need to audit or patch
each call site individually.

## Trade-offs

**Only the `shell.before` mapping was changed.** No other Cursor event kind reports `cwd` today
([/decisions/ad-114.md](/decisions/ad-114.md)),
so no other mapping needed the same fix. If a future Cursor event gains a `cwd`-shaped field, the same
truthy-check convention should be applied there too, but that is a decision for whenever that happens, not
today.

## Not decided here

- **Whether Cursor's empty-string convention applies to any other field this adapter reads** (this record
  only confirmed and fixed `cwd`). Not audited here.

# AD-086 — The write lock read the wrong error code on Windows, in a module that already listed the right ones

- **status**: active

## Decision

1. **Contention is `EEXIST`, `EPERM`, `EBUSY` or `EACCES`.** The lock waits on all four and throws on anything else.
2. **The lock opener and its sleep are injectable**, so the branch has a test that needs neither Windows nor a
   second process.
3. **The lock's budget and the rename's budget are separate fields** — `lockAttempts` and `lockSleep` against
   `attempts` and `sleep`.
4. **`withFileLock` is exported**, because its contention behaviour is worth asserting directly.

## Why

**The answer was already in the file.** `fs-atomic.ts` opens with
`RETRYABLE_CODES = new Set(["EPERM", "EBUSY", "EACCES"])`, used by `writeJsonAtomic` so a rename that loses a race
is retried. Twenty lines later the lock loop — the one place in this module where contention is the *expected* case,
not the exception — checked `errorCode(error) !== "EEXIST"` and threw. So the module knew which codes mean "busy,
come back" and the function that most needed that knowledge did not consult it.

**`EEXIST` is a POSIX assumption.** On Windows a `wx` open against a file another process is creating, or has open,
or is unlinking, answers `EPERM`. Measured in CI: `EPERM: operation not permitted, open
'…\tlc-handoff-concurrency-6yxC9F\.tlc\harness\state\handoff.json.lock'`, failing
`two concurrent writers under the same provider merge without losing either field`. The same commit passed on
ubuntu and macos, and passed on Windows in other runs — because it needs two writers to collide inside the same
millisecond, which is what the test is deliberately arranging.

**The names had to be prefixed or one budget would eat the other.** `UpdateJsonAtomicOptions` is the intersection
of the write options and the lock options, and both wanted `attempts` and `sleep`. Sharing them would mean a caller
tuning the rename retry silently changed how long the lock waits, in whichever direction the destructuring
happened to resolve. That is a defect that would never produce an error message.

**Injecting the opener is what makes this checkable at all.** The failure lives on the one platform a contributor
here cannot run, and the trigger is a millisecond-scale race. Four tests now assert each code is treated as
contention, one asserts a non-contention code still throws, and one asserts the two budgets stay apart. Reverting
the one-line predicate fails five of them.

## Trade-offs

**Retrying on `EACCES` can mask a real permissions problem.** A lock directory the process genuinely cannot write
to will now spin for 200 attempts before failing with `could not acquire lock` instead of failing immediately with
the fs error. The message names the path, and the alternative — telling a permission error apart from a race by its
code alone — is not possible, because Windows uses the same code for both.

**`withFileLock` is now public API.** It was private, and exporting it for a test widens the surface. It is the
honest option: the behaviour under contention is the thing that broke, and asserting it through
`updateJsonAtomic` only would test it at one remove.

**Four injected options on a platform primitive.** They exist for tests, which is the same trade `rename`,
`writeFile` and `removeFile` in this file already made.

## Not decided here

- **Whether other `EEXIST` checks in this repository share the assumption.** This one was found by a CI failure on
  a specific test, not by a search for the pattern.
- **A lock that survives a crashed holder.** A stale lock file still blocks for 200 attempts and then fails; no
  ownership or timestamp is recorded, so nothing can tell a dead holder from a slow one.
- **Whether the concurrency test should run on Windows at all.** It is the test that found this, so it earns its
  place.

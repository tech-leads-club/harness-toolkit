# AD-111 — The comment gate advises at edit-time, cheap enough to afford per edit; duplication stays stop-only

- **status**: active

## Decision

1. **`tool-after.ts` scans for an undeclared comment on `edit.after`**, scoped to `event.filePath` only,
   diffed against the same `turn_base_sha` stop already uses. Gated on exactly the condition stop's
   comment gate already checks (`comments.enabled && comments.onViolation === "followup"`) — no new
   policy field.
2. **A hit returns `{kind: "context"}`**, never `deny`/`continue`/`ask`. The edit itself is never blocked.
3. **The message is distinct from `commentViolationMessage`.** `commentEditAdvisory` says `HEADS UP`, not
   `BLOCKED` — nothing is blocked yet, and claiming otherwise would be a refusal this call cannot make.
4. **Stop's comment gate is unchanged.** It remains the authoritative block, catching whatever this
   advisory does not — a comment written by a tool that never fires `edit.after` (a shell heredoc), or a
   session under a provider without `contextAtToolAfter`.
5. **Duplication does not get the same treatment in this pass.** `scanProject` reads up to
   `MAX_SCAN_FILES` (2000) / `MAX_SCAN_BYTES` (8MB) of tracked files, uncached, on every call
   (`src/core/duplication/duplication.service.ts:191-192,198`).

## Why

**Reported directly, twice, in one session.** The operator hit the comment gate's stop-time-only block
after several turns of unrelated work had already happened on top of an undeclared comment — the fix was
cheap, the tokens spent in between were not. The ask was general — "não só com comentários, mas com
tudo" — and the honest answer is not "make everything real-time": the harness's gates split cleanly into
two different cost shapes, and only one of them affords per-edit checking.

**The channel already exists and already works.** `edit.after` (`PostToolUse` for Edit/Write) already
returns a `context` decision for the untrusted-content rail — Claude renders it as
`hookSpecificOutput.additionalContext`, Cursor as `additional_context`, both confirmed live in
`src/providers/*/*.outbound.ts`. Reusing this for comments needed no new plumbing, only a scan scoped to
the single file the edit touched — cheap by construction, since `findAddedComments` is a regex/syntax
match with no subprocess and no disk scan beyond the one file's diff.

**Lint, test, docs, and duplication are a different shape, and stay where they are.** They either spawn a
real process (lint/test/docs, already amortized by `runLockedGate`'s content-hash cache — AD-045) or scan
the whole tracked tree with no cache (duplication). Running any of these once per edit instead of once per
turn multiplies real cost — CPU and wall-clock, not LLM tokens, but the same "spend less, not more"
principle the ask was about. Comments is the one gate that was both stop-only and cheap enough to move;
this record moves that one.

## Trade-offs

**A comment fixed and then re-broken later in the same turn re-triggers the advisory.** Scoped per file
per edit, not deduplicated across the turn — a standing violation in a file the agent keeps returning to
will keep surfacing until it is actually fixed. Accepted: the alternative (suppress after the first
advisory) would let a real, still-present violation go silent for the rest of the turn.

**Only `edit.after` is covered.** A comment written via `Bash` (a heredoc, `sed`, `python3 -c`) gets no
early advisory — only the stop-time block, unchanged. Not worth a shell-content scanner for this pass;
`edit.after` covers the tool this project's agents overwhelmingly use to write code.

## Not decided here

- **Duplication at edit-time, once it has a cache or an incremental index.** The trade-off above names
  exactly what would need to change first.
- **Applying the same channel to supply-chain or the plan gate.** Neither was part of the reported case;
  no evidence yet that either is cheap enough or would save real turns.

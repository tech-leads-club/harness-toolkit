# AD-144 — `turn_base_sha` records the git root it came from, and a mismatch falls back to `HEAD`

- **status**: active

## Decision

1. **`HandoffProviderSlice` gains `turn_base_root?: string`** (`src/core/handoff/handoff.types.ts`),
   written alongside `turn_base_sha` and nowhere else.
2. **`prompt-submit.ts` writes both fields in the same patch.** `shaScopeRoot(event)` is resolved
   through `gitRootOf` once, and both the sha and the resolved root are written together — a sha with
   no root, or a root with no sha, never happens.
3. **A shared resolver, `resolveTurnBase(slice, gitRoot)` (`support.ts`), replaces every inline
   `handoff.turn_base_sha ?? "HEAD"`.** It returns the recorded sha only when `gitRootOf(gitRoot)`
   matches the recorded `turn_base_root`; otherwise it returns `"HEAD"` — the same fallback the
   absent case already used, extended to a mismatched one.
4. **Three call sites now go through it**: `stop.ts`'s own `turnBase` computation, `computeTurnScope`
   (`support.ts`, shared by `stop.ts` and `ship-gate.ts`), and `tool-after.ts`'s comment advisory
   (compared against `event.projectDir`, the root it already diffs with).
5. **A slice with a sha but no root — state written before this shipped — resolves to `HEAD`**, not
   to the stale sha. Self-healing: the next `prompt.submit` writes both fields together.

## Why

**Confirmed live**, on a different project, on a long-running Claude Code session — one
`session.start`, several hours, dozens of turns, working across 25 different git worktrees of the
same repository. `stop` repeatedly blocked citing comments a commit three weeks old had added, in
files the turn never touched; `git status` was clean, `HEAD` matched the branch actually being
worked, and the flagged commit was confirmed (`git merge-base --is-ancestor`) to be an ancestor of
current `HEAD` — same lineage, not a divergent branch. That combination is only possible if
`turn_base_sha`, at the moment those stops ran, was itself older than the three-week-old commit.

**Read from the actual adapters, not assumed.** Cursor's own inbound mapper
(`cursor.inbound.ts`) populates `event.cwd` only on `shell.before`, precisely because AD-141 already
found other event kinds unreliable for it. Claude Code's adapter (`claude.inbound.ts`) populates
`event.cwd` from every hook payload, because the host reports it on every one. `prompt.submit`
(where `turn_base_sha` is captured) and `stop` (where it is read back) each report the shell's `cwd`
at their own moment — and across a session that `cd`s between independent worktrees, those two
moments can name different git roots entirely. `turn_base_sha` becomes "the HEAD of whichever
worktree the shell was sitting in when the prompt was submitted," diffed against whatever the
current worktree happens to be.

**Why a root check and not a narrower fix.** AD-114, AD-117 and AD-129 all address `event.projectDir`
(stable) diverging from `event.cwd` (worktree-following) — but each assumes the sha and the diff
root, whichever they are, at least agree with each other within one turn. None of them record which
root produced the sha, so none can tell "valid baseline for here" from "valid baseline for somewhere
else entirely." Recording the root and checking it before trusting the sha is the same principle
`gitRootOf` already applies everywhere else in this codebase (AD-137, AD-129): two things that look
alike (a sha, a path) are not interchangeable unless they were produced by the same root.

## Trade-offs

**A mismatch falls back to `HEAD`, not to a re-captured baseline.** The session's actual turn-start
sha for the *current* root is unknown once a mismatch is detected — `HEAD` is the same answer already
used for "no `turn_base_sha` recorded," and it is correct in practice: an unrelated root has no
turn-scoped uncommitted changes of its own for the previous root's sha to have described anyway.

**One extra `git rev-parse --show-toplevel` per `prompt.submit`.** Already paid, at the same moment,
by `currentGitSha`'s own internal call to `gitRootOf` — this record makes the harness read the value
that call already computes, rather than adding a new spawn to the hot path.

## Not decided here

- `tool-after.ts`'s comment advisory already diffs against `event.projectDir`, not
  `shaScopeRoot(event)` — a separate, narrower, pre-existing gap this record does not touch.
- Whether a session that moves between many worktrees should get a *per-root* baseline instead of one
  shared value falling back to `HEAD` per mismatch — not needed today; one logical "turn" per session
  is still the right model, and the fallback already gives the correct practical answer.

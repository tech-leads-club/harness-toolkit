# AD-118 — `pr-open` does not fire on a draft, so a proof needing the pull request to exist has a way to run

- **status**: active

## Decision

1. **`rules.trigger.ts`'s `pr-open` shape for `gh pr create` now excludes the invocation when
   `--draft` or `-d` is present anywhere in the command's words.** `gh pr ready` is unchanged — still
   matched unconditionally, since that is the transition GitHub's own tooling treats as "now open for
   review."
2. **`SHELL_SHAPES` gains a shape type (`{prefix, excludeIfAny?}`)** instead of a bare token list, so
   a future shape needing the same kind of exclusion — a flag that changes what an otherwise-matching
   command actually does — has a place to declare it rather than a second ad hoc check.
3. **docs/concepts.md's proof-kind table row for `command(<pattern>)` is corrected** from "ran
   (regardless of exit code)" to "ran and did not fail," matching both the prose two paragraphs above
   it and the actual producer: `rules.observe.ts`'s `observedFact` only emits a `command` observation
   on `tool.after`/`shell.after`; a failing invocation arrives as the separate `tool.failure` event and
   produces no observation at all. No behavior changed for this part — the docs were wrong, not the
   code.
4. **skills/harness-init/SKILL.md's rule-authoring checklist gains a fourth "say out loud" item**
   naming the draft carve-out, and docs/concepts.md gains one paragraph doing the same, generically —
   no project- or skill-specific naming, matching every other example already in that section.

## Why

**Reported live.** A project rule required `command(<script>) since HEAD` on `pr-open`, where
`<script>` posts a review by reading the pull request through `gh pr view`. Two real branches sat
blocked — the script could never run successfully before a PR existed, and the trigger refused every
way to create one, draft or not. `gh pr create --draft` matched the identical `["gh","pr","create"]`
prefix as a real open; `startsWithShape` reads only a fixed-length prefix and never looked at the rest
of the words, so a flag that changes the actual act (draft vs. real) was invisible to it.

**Confirmed against 2026 practice before changing the trigger, not guessed.** The GitHub Actions
community's own converged pattern for gating on PR state is to run the heavy job on
`ready_for_review`, not on `opened` while draft — `github.event.pull_request.draft == false` gates it,
and the transition to ready is treated as the meaningful trigger, with draft explicitly used as safe
iteration space because a draft cannot be merged. `pr-open`'s existing second shape, `gh pr ready`,
already matches that transition; the only gap was that the first shape didn't distinguish a real open
from a draft open the same way.

**The docs contradiction was found investigating the same deadlock, in the very table this fix
concerns.** `docs/concepts.md` said `command(<pattern>)` matches "regardless of exit code" two lines
from prose that says the opposite ("a command that ran and did not fail"). Fixed here rather than
filed separately, next to the mechanism it describes.

## Trade-offs

**A combined short flag (`-fd`, `-df`) is not recognized as carrying `-d`.** `excludeIfAny` checks for
exact tokens; `tokenizeShell` does not expand combined POSIX short options. Accepted: `gh`'s own CLI
does not document combined short flags for `pr create` (confirmed via `gh pr create --help`), and the
existing `matchesShape`/`startsWithShape` style throughout this file already reads words, not flag
semantics — expanding that is a larger change than this fix warrants.

**Every other operator-authored `command(<pattern>)` proof still cannot be satisfied before `pr-open`
fires**, if it depends on something only a real, non-draft-adjacent PR state can produce. The fix is
specific to the trigger's own shape recognizing draft as a distinct act; it does not change what a
`command(<pattern>)` proof means or when it is recorded.

## Not decided here

- **`gh pr create --dry-run`**, already named in [/decisions/ad-116.md](/decisions/ad-116.md)'s own
  trade-offs as unevidenced and undecided. The mechanism this decision adds (`excludeIfAny`) could
  carry that exclusion too if it is ever reported; nothing here changes that answer.
- **Extending the same `{prefix, excludeIfAny}` shape to `commit`/`push`.** No reported case motivates
  it; adding it speculatively is the inference [/decisions/ad-100.md](/decisions/ad-100.md) already
  declined.

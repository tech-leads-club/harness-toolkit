# AD-089 — The release is chained to CI instead of racing it, and a superseded run is cancelled

- **status**: active

## Decision

1. **`release.yml` is triggered by `workflow_run` on CI completing**, on `main`, and not by the push.
2. **The `verify` job is deleted.** Nothing calls `ci.yml`, and `workflow_call` comes off it.
3. **The conclusion is the condition**: `github.event.workflow_run.conclusion == 'success'`.
4. **Every workflow has a concurrency group.** Shared per pull request, unique per commit otherwise.
5. **Every job has `timeout-minutes`.**

## Why

**Four live runs for one release, from two separate causes.** On the release pull request, two pushes left two
three-platform matrices running at once, the older one answering about code that no longer existed. On the commit
in `main`, `ci.yml` and `release.yml` both fired — and `release.yml`'s `verify` job called `ci.yml`, so the same
matrix ran twice against the same commit. The second cause was introduced one commit earlier, by the change that
removed a *different* duplication ([/decisions/ad-084.md](/decisions/ad-084.md)): the publish job had been running
its own weaker copy of the gate, and replacing it with a call to the real one traded a wrong verification for a
redundant one.

**Chaining fixes it and makes the ordering real rather than incidental.** With `workflow_run`, the release workflow
exists only because CI finished, so there is nothing to duplicate and nothing to race. Before this, `publish`
depended on `verify` and therefore on a matrix run *inside the release*, while the CI run for the same commit
proceeded in parallel and was ignored. Now the gate that gates the release is the gate everybody looks at.

**`workflow_run` fires on completion, not on success, and that distinction is the whole safety of it.** Without
`conclusion == 'success'` a chained release runs after a red matrix exactly as it does after a green one — which
would be strictly worse than the duplication it replaces. The condition also allows `workflow_dispatch`, so a
manual release is still possible.

**`cancel-in-progress` cannot be made conditional, whatever the docs imply.** `cancel-in-progress: ${{
github.event_name == 'pull_request' }}` is accepted without a validation error and still cancels runs on `main`.
The shape that works is a group key that is *shared* for a pull request and *unique* otherwise:
`${{ github.workflow }}-${{ github.event.pull_request.number || github.sha }}`. Two pushes to a PR collide and the
older is cancelled; two commits on `main` never collide because their keys differ.

**Measured, per commit on `main`:** 11 jobs to 8, and the three-platform matrix once instead of twice. On a release
PR taking two pushes: 6 matrix jobs to 3.

**A job with no timeout holds a runner for six hours.** On a matrix of three that is eighteen runner-hours for a
hang. The gate takes about three minutes, so 15 is generous and finite. `BHubAI/platform` sets one on every job for
the same reason.

## Trade-offs

**`workflow_run` runs the workflow definition from the default branch, not from the commit that triggered it.** A
change to `release.yml` on a branch is therefore not exercised until it is on `main` — the release path cannot be
tested in a pull request. That was already half-true (the push trigger only fired on `main`) and is now fully true.
`workflow_dispatch` is the escape hatch for trying it.

**The release now starts a few minutes later**, because it waits for the whole matrix instead of running beside it.
That is the ordering being real: a release that started earlier was starting before anything had verified the
commit.

**Cancelling a superseded PR run loses its logs.** A run cancelled halfway leaves a partial record, and a flake
that only appeared in the older run is gone. The alternative is paying for a matrix that answers about a tree
nobody has.

**A `concurrency: release` group serialises releases and is not a queue.** GitHub allows one running and one
pending job per group, so a third release queued behind two is cancelled rather than lined up. Releases arriving
three-deep in minutes is not a state this repository has.

## Not decided here

- **`paths-ignore` on CI.** A docs-only commit still runs the full matrix. The gate checks documents, so most
  doc changes are exactly what it should read; picking which are inert needs a list nobody has.
- **Making CI a required status check.** With the release chained to it, the branch rule would be belt on braces —
  but it is also what would stop a human merge from bypassing the gate.
- **Whether `zizmor` and CI should be one workflow.** Two triggers, two concurrency groups and one extra job for a
  five-minute audit on a path filter.

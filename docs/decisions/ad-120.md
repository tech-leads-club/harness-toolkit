# AD-120 — A rule denial names the directory and sha it actually checked

- **status**: active

## Decision

1. **`ruleMessage` takes the resolved `shaRoot` (the directory `since HEAD` was computed against) and `sha`
   (the result), and appends `— checked <shaRoot> at <sha or "no HEAD">` to every denial.** Unconditional, not
   only on the stale-reason path AD-119 added — a wrong root can just as easily present as a proof that looks
   never-observed, if the harness is comparing against the wrong repository's history entirely.
2. **`RuleContext` (`rules.service.ts`) gains `shaRoot: string`**, threaded from every caller that already
   computes it as a local variable for `currentGitSha` — `tool-before.ts`'s `rulesDecision`, `stop.ts`'s
   `decideStopRules`, `ship-gate.ts`'s ship-time battery. No new computation: the string was already in scope
   at every call site, just never hitched to the outcome it explains.
3. **`ProofContext` (`rules.proof.ts`) is untouched.** `shaRoot` answers nothing about whether a proof is
   satisfied — only `evaluateRules`, one level up, needed it to build the message. Widening the narrower type
   would have handed it to `missingProofs`/`proofSatisfied` for no reason.

## Why

**Reported live, and this time genuinely unexplained.** A `command(post_review.py) since HEAD` proof had run,
recorded, and matched the project's real current HEAD by every check available: `git rev-parse HEAD` in the
real directory, `git rev-parse origin/<branch>`, and `gh pr view --json headRefOid` all agreed. A synthetic
replay of the exact same event through the installed binary allowed the action. Yet the real attempt denied,
identically, three times across thirteen hours. Forensics took roughly forty minutes across two conversations
and still could not produce the one fact that would have settled it in the first sixty seconds: what directory
did the harness actually resolve for that one denied event.

**The denied event itself is invisible by construction.** A `deny` at `shell.before` happens before the tool
ever runs, so `tool.after`/`shell.after` — the only events `rules.observe.ts` turns into an observation — never
fire for it. Every log this harness already writes (`rule-observations.jsonl`, `obs.jsonl`'s `shell.start`/
`policy.deny`, the raw Claude transcript) recorded the command, the verdict, and the rule name, and not one of
them recorded the directory the decision was made against. There was no forensic path that did not require
guessing at what the host might have handed the harness for that specific call.

**A message that already reports a bare sha but not the directory it was measured in reports half the fact.**
`since HEAD` is a comparison of two things — the recorded sha and the current one — and the current one is only
ever as trustworthy as the directory it came from. Naming the sha without the directory hides exactly the
failure mode that happened here: a right-looking sha computed against a wrong directory is indistinguishable,
in the old message, from a right sha computed against the right one.

## Trade-offs

**This does not fix the underlying cause**, whatever it turns out to be — a host quirk in how `cwd` is reported
around a background Task-tool agent completing is the leading hypothesis, not a confirmed one. What this adds
is the one fact that would make the *next* occurrence, if there is one, self-diagnosing in the message itself
rather than in an hour of cross-referencing three separate log files by hand.

**Every denial is now a few characters longer.** Accepted: a rule denial is already an interruption an operator
or agent reads carefully, per [/decisions/ad-034.md](/decisions/ad-034.md)'s own reasoning about a message that
already exists rather than a new alarm — this adds to an existing interruption, it does not create one on a
healthy path.

## Not decided here

- **What actually produced the wrong resolution, if the leading hypothesis is even right.** Recorded as a
  hypothesis, not fact, per [/decisions/ad-060.md](/decisions/ad-060.md)'s own distinction — nothing here
  confirms a host bug, and nothing here would need reverting if the real cause turns out to be something else
  entirely.

# AD-132 — Git-root discovery replaces an exact-match guard, in the six functions and their consumers

- **status**: active

## Decision

1. **`gitRootOf(dir): Promise<string | null>`** (new, `src/platform/git.ts`) runs `git rev-parse --show-toplevel`
   and returns the resolved absolute path, or `null` for any failure — not a repository, a missing directory,
   or `spawn` itself failing (caught explicitly; `spawn` rejects instead of resolving a non-zero exit code when
   the given directory does not exist at all, unlike every other git call in this file).
2. **`listChangedRepoFiles`, `listCommitFileSets`, `localRepoRemote`, `currentGitBranch`, `currentGitSha`**
   replace `existsSync(join(dir, ".git"))` with `gitRootOf(dir)`, and use the resolved root — not the original
   argument — as every subsequent git call's `cwd`. None of these take a repo-root-relative pathspec, so this
   is a pure correctness fix with no output-shape change for the case that already worked.
3. **`listAddedLines`** gets the same swap, and additionally routes its own `readFileSync` (the untracked-file
   branch) through the resolved root. Its `relativePaths` argument is repo-root-relative everywhere it is
   produced in this codebase (`listChangedRepoFiles`'s own output, threaded through `computeTurnScope`) — using
   anything other than the true root for its git calls was the second-order failure mode this record's own
   review caught before it shipped: fixing only the guard, without also fixing this function's `cwd`, would have
   left every added-line lookup silently empty whenever the caller's directory was a subdirectory.
4. **`listTrackedFiles`** gets the same `gitRootOf` swap. `git ls-files` has no `existsSync` guard to remove, but
   unlike `git diff --name-only`/`git log --name-only`, it scopes its output to the directory it runs from —
   measured: run from a subdirectory it returns names relative to that subdirectory, not the repo root, silently
   disagreeing with every other function here. `runCommand` itself is untouched; it is a generic command runner,
   not a git-specific reader.
5. **Three call sites that read a repo-root-relative path directly off the original, possibly-subdirectory
   argument** — found by the same review, one level up from the six functions themselves — switch to the
   resolved root too: `comment-policy.service.ts`'s `diskLineReader` (via `scanAddedComments`, which resolves
   the root and hands it to the reader), the duplication-scan `readFileSync` callback in both `ship-gate.ts`
   and `stop.ts`, and `stop.ts`'s supply-chain-manifest `readManifest`.

## Why

**One check, wrong test.** `existsSync(join(dir, ".git"))` answers "does an entry named `.git` exist exactly
here", not "is this directory inside a git repository" — the second is what every caller actually needed, and
git itself already answers it correctly from any subdirectory. Reimplementing that discovery in Node would have
duplicated logic git already gets right, including worktrees (a worktree's `.git` is a file, not a directory) —
exactly the kind of duplication [/decisions/ad-100.md](/decisions/ad-100.md) already argues against, generalized
from tokenizing to git discovery.

**Confirmed in production, and traced to a specific, distinct defect.** An operator rule requiring a proof
before `pr-open` never fired for a `gh api .../pulls` command whose event `cwd` was a subdirectory of the
project. [/decisions/ad-130.md](/decisions/ad-130.md) added a repo-remote check that fails an API-shaped match
closed when the remote resolves to `null` — correct for "this genuinely is not the project's repository," wrong
for "this directory is a subdirectory of it." AD-130 built a correct check on top of the six functions' existing
blind spot; this record fixes the blind spot itself, which also affects `since HEAD` proof resolution
([/decisions/ad-120.md](/decisions/ad-120.md)) and the diff-scoped gates whenever the same condition holds.

**Fixing the guard alone would have introduced a second bug.** `listAddedLines` takes repo-root-relative paths
as input. A fix that resolved the true root only to decide "is this a repository" — while still running the
actual git calls with the original, possibly-subdirectory `cwd` — would have made every pathspec resolve against
the wrong directory, silently returning nothing. The fix uses the resolved root for every subsequent call in
every one of the six functions, not only the guard, closing that class of regression uniformly rather than
function-by-function.

**An independent review of the first version of this fix found the same class one level up, before it shipped.**
`listTrackedFiles` builds the tracked-file index the duplication gate scans; `diskLineReader` reads the file a
new comment attaches to; three `readFileSync` callbacks read a tracked file's content for the duplication and
supply-chain gates. All five read a repo-root-relative path against the original, possibly-subdirectory
argument — the same mismatch `listAddedLines` already had to avoid, reproduced empirically: an attached,
informative doc comment misread as undeclared, and a duplication gate reporting a file as a copy of itself,
both scanned from a real subdirectory. Fixed the same way, in the same record.

## Trade-offs

**One additional process spawn per call**, on every function and call site fixed here that previously paid
nothing for a guard that was free but wrong. Same cost class as the git call each of them already makes;
accepted for correctness.

**Worktree compatibility is preserved, not re-derived.** `git rev-parse --show-toplevel` run from inside a
worktree's own subdirectory already resolves to that worktree's own root — the same guarantee
[/decisions/ad-129.md](/decisions/ad-129.md) established, now proven for the subdirectory case its own tests
never exercised.

## Not decided here

- **A configurable git binary path or an alternative to shelling out to `git`.** Not evidenced as needed; every
  function in this file already shells out.
- **A codebase-wide audit for the same mismatch outside the comment/duplication/supply-chain gates.** Review
  found and closed every instance reachable from `shaRoot`/`projectDir` in those three gates; a broader audit
  is a distinct task if evidence surfaces elsewhere.

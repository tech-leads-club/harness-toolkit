# AD-102 — A green gate is not a working product, so four checks that look where it cannot

- **status**: active

## Decision

1. **The suite gets a fake home.** `HOME`, `USERPROFILE`, `CLAUDE_CONFIG_DIR` and `CURSOR_CONFIG_DIR` are
   redirected into one throwaway directory, and the guard asserts the *resolver* — that `os.homedir()` answers the
   fake — not the variable.
2. **knip walks the module graph.** `--files --dependencies` blocks at zero; `--exports` blocks on growth past a
   ceiling written in code.
3. **The packed artefact is driven in a clean room** before `npm publish`, never after.
4. **A release publishes to `next`.** `latest` moves by a separate tag-move workflow, dry-run by default, behind the
   publish environment.

## Why

**Six defects reached a live machine in one day, every one with the gate green.** They are not six accidents; they
are four blind spots:

| defect | what it needed |
|---|---|
| a test deleted this repository's own `bin/` | a home the suite cannot escape |
| a wiring step pointed the operator's `tlc` at a temp directory | the same |
| `observe` was exported, wired into the facade, and called by nothing | something that walks the graph |
| 0.3.0 installed nothing; 0.4.0 left `tlc` off `PATH` | driving the published artefact |
| 0.4.2 shipped a defect 0.4.3 fixed minutes later | somewhere for a release to sit |
| a POSIX path assumption in a test | the Windows leg of CI — which already caught it |

The last row matters as much as the others: one of the six was already covered, and the check worked. The problem
was never "add more checks", it was that three specific things nothing looked at.

**A fake home closes a class instead of an instance.** The first three defects were patched one variable at a time,
each after it reached a machine — `TLC_HOME`, then `TLC_ORIGIN` and `TLC_HOME_FROM_ENV`, then `TLC_INSTALL_DEST`,
then `TLC_BIN_DIR`. Four paths derive from `homedir()` and none of them was redirected, so `wireRuntime` in a test
linked skills into the operator's own `~/.cursor` and merged their `settings.json`. Nothing had broken there yet
only because no test happened to step in it. The published pattern is to redirect the home in a session fixture and
assert on the resolver, so a name added to the list without the setup honouring it fails.

**Nothing here walked the module graph.** The existing checks look for a union member read and never written, a
suppression whose reason is not a reason, a screen that paints its own strings. All are shape checks on files.
`ts-prune` was archived in December 2023 and its author points at knip, which uses the same mark-and-sweep
algorithm over a full graph and additionally reports unused files and dependencies — things ts-prune could not see.

**The suite runs against the working tree, which is not the package.** Three install defects reached operators
through exactly that: 0.3.0 installed nothing, 0.3.2 shipped bundles where every entry answered as the CLI, 0.4.0
left the command off `PATH`. Packing, installing the tarball the way `npx` would, and driving the installed binary
is the only thing that speaks about the artefact.

**And a release had nowhere to sit.** `latest` is the only tag npm treats specially, so publishing onto it means
every new install gets a version the moment it exists. The npm CLI publishes to a non-latest tag and promotes
separately; React runs four channels; the Gemini CLI treats the tag move as its primary incident lever, for
rollback and roll-forward alike.

## Trade-offs

**A fake home makes some tests unrepresentative, silently.** Two floor tests asserted that destroying a
home-relative path is denied, and went vacuous the moment the fake home moved into the OS temp directory — which
that rule treats as disposable on purpose. The rule was right for the input it was given. Those tests declare their
own home now, but the lesson generalises: a hermetic fixture can be *too* hermetic, and only reading the assertion
tells you.

**knip's coverage here is incomplete and I could not find out why.** A dead export added to
`src/platform/paths.ts` or `src/platform/links.ts` is not reported, while `style.ts`, `pricing.ts`,
`rules.proof.ts` and `rules.trigger.ts` all are. Five hypotheses tested — entry file, imported-by-an-entry,
imported-by-the-CLI, `export *` re-export, `--include-entry-exports` — none explains it. The ceiling mechanism does
work: 76 findings against a ceiling of 75 exits non-zero. So the step is real and its coverage is not complete, and
`CONTRIBUTING.md` says so in the row itself. A check trusted past its evidence is worse than no check.

**The exports ceiling is a debt, and a number can be raised.** It is in code rather than a snapshot file precisely
so raising it is an argument in a diff somebody reads.

**The clean room is weaker without docker.** It falls back to a throwaway npm prefix, which covers packaging and the
command's behaviour but shares the host filesystem. The output names which of the two ran.

**Promotion is now a manual step.** A push to main publishes to `next` and stops. That is the point — but it means
a release is not finished until someone runs Promote, and forgetting leaves `latest` behind with no error anywhere.

**And a tag move reaches new installs only.** Anyone who already has the command keeps it until they update, so a
bad `latest` still needs a patch behind it. The workflow says this on every run.

## Measured while building it

- The isolation was verified by reading the resolver, not the variable: inside the suite `os.homedir()`, the
  conventional runtime home and both provider config directories all resolve inside the throwaway.
- **`TLC_HOME` was redirected without being declared**, so no guard checked it. Found by a new test that reads the
  setup module's own source and pairs every assignment with the declared list. Before it existed, a mutation
  removing a name from the list survived — the guards simply checked fewer names.
- **`check-boundaries` forbids `process.env.HOME`** so production resolves the home portably
  ([/decisions/ad-006.md](/decisions/ad-006.md)). The harness does the opposite job. One named exemption, and a test
  asserting the list is exactly one entry, because an allowlist grows by append and each append is invisible.
- **Six of the seven files knip first called unused were test fixtures** a test spawns as a child process, which no
  import graph can see. Declared as entries — a false positive left in place is how a check stops being read. The
  seventh was real: `src/core/floor/index.ts`, a barrel nobody imported.
- **The clean room found something on its first real run:** in a fresh container the install reports
  `/root/.local/bin is not on PATH`, which is the previous day's warning working on a machine that had never seen
  the tool.
- **A substring assertion cannot see logic being neutered.** The promotion checks began as inline shell, and a probe
  that wrapped one in `false &&` left the test green. They moved into `verify-promotable.mjs` with injectable probes;
  eight mutations now die, including that one.
- **The step-list test asserted args by position**, so inserting two steps rewrote a dozen unrelated lines. By label
  now, so each assertion states the one fact it owns.
- One of my own tests failed against a correct workflow: it matched the loose string `npm publish`, which appears in
  prose above the step that runs it.

## Not decided here

- **Property-based testing on the path functions.** It would have caught the home-claimed-as-project defect, but the
  mutation probe caught that one too, and modelling paths well is a real cost.
- **A mutation-testing tool.** The by-hand probes in this repository found six surviving mutants in two days, every
  one of them a missing test rather than a missing feature. Tooling it is a convenience, not a gap.
- **`platform/` and `contracts/` as barrel-only.** The architecture validator wants it; this repository's own checker
  permits deep imports into them by design, because they are the shared base and the rule it enforces is direction.
  Changing that is a decision, not a cleanup.

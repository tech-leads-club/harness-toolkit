# AD-101 — Machine data belongs to the machine, not to the install

- **status**: active

## Decision

1. **`machineHome()` is where this machine's operator data lives**: the user-tier config, the global lesson tier,
   the global rules, the price catalogue, the cross-repo spool.
2. **The launcher's own resolution never chooses it.** `tlc-exec` marks a derived home `TLC_HOME_FROM_ENV=0`, and
   that value alone sends `machineHome()` to the conventional path. Anything else — an operator's exported
   `TLC_HOME`, a suite pinning one — is honoured.
3. **`runtimeHome()` keeps naming where the code lives** and stays free to move: dist bundles, docs, the shipped
   capability catalog, the launcher being wired.
4. **`install` links the `tlc` command** into `TLC_BIN_DIR` (default `~/.local/bin`), reports the path, and says
   when that directory is not on `PATH`. A refusal is reported and the install continues.

## Why

**"Global" meant "this install", and nothing said so.** `--global` writes to `<runtime home>/state/lessons.json`
and the user tier is `<runtime home>/config.json`. The runtime home is derived from the launcher that was invoked
when nothing else names it, so a machine with an npm install and a checkout has **two** of each. Measured on an
operator's machine, in one sitting: a lesson saved with `--global` landed in a checkout's state directory while
the CLI printed *"every product on this machine will read it"*; and a user-tier config holding a subagent
allowlist stopped being read the moment the runtime home changed, which read as the setting having been deleted.

**Two concepts were wearing one name.** Where the code lives has to move — that is the whole point of `TLC_HOME`,
and of being able to run a checkout without disturbing the machine. Where the operator's data lives must not move,
or "machine-wide" is a claim the code does not keep. Splitting them is the fix; the alternative — pinning
`TLC_HOME` everywhere — makes every operator responsible for a detail the tool created.

**The flag already existed.** `TLC_HOME_FROM_ENV` was introduced so the installer could tell an operator's choice
from the launcher's own resolution, and `installDest()` already branched on it. This is the same question asked by
a second caller, not a new mechanism.

**And the reason the two installs existed at all** was that `install` never put `tlc` on `PATH`. The command came
from npm's shim, which sits in the bin directory of whichever Node version npm ran under and leaves `PATH` the
moment a version manager switches. Measured: a successful install followed immediately by
`tlc: command not found`. Meanwhile `uninstall` removed `<bin dir>/tlc`, `doctor` failed without it, and the
README said install added it — three halves of a thing that did not exist. The bin directory is now defined once
and both halves read it.

## Trade-offs

**A test that pins `TLC_HOME` without the marker keeps it.** That is deliberate: the suite's hermeticity depends on
it, and `test-env.mjs` scrubs `TLC_HOME_FROM_ENV` so a test can never be handed the launcher's answer. The cost is
that the rule is "the marker sends you to the conventional home", not "only an explicit choice is honoured" — a
weaker statement, and the honest one.

**A non-conventional `TLC_INSTALL_DEST` seeds a config nothing reads.** `install` seeds `config.json` at the
destination, and the loader now reads `machineHome()`. For the ordinary install they are the same directory. For a
relocated one they are not, and nothing warns.

**The launcher link is a convenience, not a contract.** Where a platform refuses to create a file symlink the
reason is reported and npm's shim remains the route. This does not attempt to be a package manager.

## Measured while building it

- Reverting the machine-tier rule fails 2 tests; making it always conventional fails 6 — the suite's own
  hermeticity is what that one protects; reading the marker as "chosen" instead of "derived" fails 3.
- **Nothing failed when the behaviour was first changed.** The machine tier had no rail at all, which is why the
  defect could ship: the gate was green before and after.
- Two mutations **survived** the first pass at the launcher rails, and both were the test's fault rather than the
  code's: the tests called `launcherLines` directly, so deleting its call from `wireRuntime` changed nothing, and
  the fixture had been given the launcher wrapper, so the missing-source guard was never exercised. A function that
  works and is wired to nothing is the shape this repository keeps finding
  ([/decisions/ad-100.md](/decisions/ad-100.md)).
- The missing-source guard exists because a test found it: `symlinkSync` creates a link to a path that is not
  there, and `existsSync` on a dangling link is false — so a broken launcher would have reported as linked while
  `doctor` said there was no `tlc` on `PATH`.

### The launcher step wrote into a live machine's `PATH`

Making `wireRuntime` link the command had a consequence nobody asked for: the suite calls `wireRuntime` with a
temp runtime, `launcherBinDir()` read the real `~/.local/bin`, and a test wrote a launcher there pointing at a
temp directory the same test then deleted. The operator's `tlc` became a dangling link into `/tmp` — measured on
the machine it happened to, within minutes of the change.

`test-env.mjs` redirected `TLC_HOME` and `TLC_INSTALL_DEST` and knew nothing about this one. It now redirects
`TLC_BIN_DIR` too, and the name list is split in two: variables that are **deleted** and variables that are
**redirected**. Putting the new name in the delete list is what happened first, and the guard test — which asserts
every name there is absent — failed against a value the setup had deliberately set. Two behaviours in one list is
how that happens.

Verified by measurement rather than by reading: the real launcher's mtime is unchanged across a full gate run.
Removing the redirect fails the guard, and that probe is run against the guard file alone — running the whole suite
to prove it would reproduce the defect on the machine under test.

### The lessons list cut the operator's own words

`row.instruction.slice(0, 160)`, with no marker. A 263-character lesson lost 103 characters mid-word, and the
operator asked whether their lesson had been cut. It had not — only its display had, and nothing distinguished the
two.

The fix is not a nicer marker. It is that nothing is hidden: a section can declare its lines as prose, and prose is
broken at word boundaries to fit the terminal. Then there is no magic number to keep and no truncation to announce.

Two details are deliberate. **Wrapping is opt-in per section**, because a section's lines are sometimes a command
to copy and breaking `tlc harness policy accept <path>` across two lines makes it unpasteable — prose and payload
look identical to a renderer, so the caller says which it has. And **a word wider than the width stands on its own
line** rather than being cut: an overlong line is visible, a missing character is not.

Two mutations survived the first pass, and both were the tests':

- Restoring the slice in the lessons list changed nothing, because no test asserted the list shows the whole
  instruction — the defect being fixed had no rail.
- Cutting the first word of a wrapped line changed nothing, because the fixture's first word was one character
  long, so that branch was never reached.

### `init` wrote what nobody chose, and overwrote what somebody had

Two defects at the source of the 29 shadowed keys.

**It wrote the whole default policy.** `resolvePolicy` returned `DEFAULTS`, and the wizard's `--stdin-json` carried
every knob it had collected. So a project shadowed the machine tier in dozens of places before anyone had chosen
anything. The wizard's answers are pruned against the resolved tiers now, and `--minimal` writes `{version: 1}` —
a project that decided nothing says nothing.

Pruning `DEFAULTS` was the first attempt and was not enough: against a machine tier that *enabled* things, the
shipped defaults differ, so a fresh project wrote `comments.enabled: false` and turned off, in that repository, a
capability the operator had switched on for the machine. The test that should have caught it passed, because the
suite's machine tier is empty — where `DEFAULTS` and the resolved tiers are the same object, pruning one against
the other produces `{version}` and the semantics never come up. That test now writes a machine tier first.

**And it overwrote an existing config.** `applyPlan` wrote unconditionally, so `init --minimal` on a configured
project replaced the operator's file — with the whole default policy before this change, with a bare version marker
after it. Both destroy choices nobody asked to undo, and neither said so. An existing config is now replaced only
by `--stdin-json`, which is the wizard supplying a policy and therefore the one route that carries consent;
everything else keeps the file and says it kept it. This is the rule `linkDir` already follows: a real file at the
target is somebody's work.

`update` was never the risk, and it is worth stating with evidence rather than assurance: `config.json`, `state/`
and `flags/` are `OPERATOR_OWNED` and appear in no payload. Measured live — an install into a home holding a
hand-written config and lesson store left both byte-identical.

### A hook that cannot run must not block the turn

Measured: with the runtime missing, the launcher emitted **nothing** on stdout and exit 1. Claude Code reads a
non-zero exit as a non-blocking error, so it carries on; Cursor's `beforeShellExecution` contract expects a JSON
verdict and does not describe empty output. On the day this was written an operator had every tool in an unrelated
session blocked while a linked checkout was mid-edit, and the only route out was editing provider hooks by hand.

A hook entry now answers `{}` and exits 0 — measured against both providers' own renderers, an abstain is `{}` for
Cursor and empty for Claude, and `{}` satisfies both. The diagnosis still goes to stderr: failing open is not
failing silently. The project shim carried the same defect one layer up (`exit 127`, no verdict) and now does the
same thing.

**A command is the opposite duty and still fails loudly.** `tlc harness doctor` exiting 0 on a broken runtime would
be a green light nobody earned, so the launcher distinguishes the two by entry name. That list is compared against
the entrypoints that actually run as programs, because a hook missing from it fails closed — the direction that
blocks a working machine.

This is deliberately not a kill switch. It changes what happens when the harness *cannot* run, and adds no way to
tell it not to.

### One place per question

Three duplications, two of them introduced by this change:

- **The `PATH` walk existed four times** — the CLI's executable finder, `doctor`'s, the launcher's Bun probe, and a
  third added here for the install check. Three were the same function differing only in which executable
  extensions they tried. `platform/paths.ts` owns it now: `pathEntries`, `executableOnPath`, `isOnPath`. The CLI's
  finder survives because it also answers for a name that is already a path, which a `PATH` walk has nothing to say
  about — but it no longer repeats the walk.
- **`shadowedKeys` and `pruneShadowed` were two recursions over one tree** applying the same leaf test, so a change
  to what counts as a restatement had to be made twice and the report could disagree with the pruner about the same
  config. One `walk` answers both.
- **The realpath comparison existed twice**, privately in `install-runtime` and again where the launcher link
  needed it. `sameLocation` in `platform/` is the only one.

**The barrels were widened the wrong way first.** Publishing `DEFAULTS` and `resolveObsLevel` from
`core/index.ts` failed the rail that says that barrel exports types and `coreFacade` and nothing else — a store or
a service reachable from it is the coupling the facade exists to prevent
([/decisions/ad-004.md](/decisions/ad-004.md)). They sit on the facade instead, which is the front door this
repository actually decided on. The repo's own test caught it, which is the only reason it is not in this commit.

**And the check that should have seen the four could not**, because the direction checks scan production sources
only and every offender lived in a test. A test reaching past a barrel is the same coupling as production reaching
past it, so `entrypoints-deep-imports-core` and `entrypoints-deep-imports-providers` include tests. Calibrated:
putting one deep import back fails the gate with the file and line, and removing it passes.

One duplicate is left and is structural: `bin/tlc-exec.mjs` walks `PATH` itself. It is plain JavaScript that runs
before any loader exists, so it cannot import from `platform/` — the launcher must be able to start with nothing
resolved. Stating it beats pretending it is gone.

### The project is discovered, not declared

`resolveProjectRoot` was `TLC_PROJECT_DIR ?? process.cwd()`. So a command run from a subdirectory took the
subdirectory as the project — found no config there, fell back to the machine tier, and reported a posture the
project had not set. Measured: `tlc harness status` from `src/` printed `solo` in a repository pinned to `focus`,
and `policy accept` with a full absolute path listed none of that repository's own sources, because the root had
resolved to a home directory where `projectConfigPath(root)` *is* the machine config path.

The fix is the convention every tool an operator already knows follows: walk up. `git` for `.git`, npm and cargo
for their manifests, biome and eslint for their config. Anything else makes the shell's position part of the
interface, and the operator finds out by being told the wrong answer confidently.

`TLC_PROJECT_DIR` still wins, because the hooks set it from the host's own payload and the host knows its workspace
better than a directory walk can. With nothing above, the answer is the working directory — so a first `init` lands
where the operator is standing rather than adopting an ancestor's project.

Two smaller things fell out of the same session. The failure path of `policy accept` listed the sources and never
said which project it had resolved, while the success path already did; it says it now. And
`policySourceFingerprint` listed the project config and the machine config without deduplicating, so when they
collide the same file appeared twice and `acceptPolicySources` would have written the same entry twice.

An earlier attempt derived the project from the accepted path instead. It worked, and it was the wrong shape: it
fixes one command and leaves every other one reading the wrong project.

### And the walk claimed the home directory

The machine's runtime home has the exact shape of a project's harness directory. So the discovery above claimed the
home as a project — and a repository under it that had never been initialised resolved its root to the home, where
`projectConfigPath(root)` **is** the machine config path. The machine tier would have been read as the project tier,
and every uninitialised repository's flags, presence and baselines would have landed in one shared state directory.

Measured on the operator's machine the moment it shipped: `policy accept --all` run from a home directory answered
`no policy source diverged in /home/<user>`, which is a sentence about a project that does not exist.

That path is skipped rather than stopped on, so a project genuinely above the home is still reached, and relocating
the runtime home makes the path claimable again. A mutation that stopped there instead **survived** the first pass,
because both answers agree unless a project sits above the home — which is the case that pins the word "skip".

Worth naming: this is a defect the discovery change introduced. The version before it resolved such a repository to
itself, which was wrong for a different reason but not this one.

## Not decided here

- **An operator escape hatch.** There is still no way to switch the harness off deliberately: `pause` disables the
  stop checks and leaves the floor and every action-time rail running. Refused for a measured reason rather than a
  principled one — the floor does not guard shell profiles (`~/.zshrc` and friends evaluate to `allow` on both the
  floor and the policy-surface guard), so an agent could plant `TLC_DISABLE=1` and wait for a restart. A switch
  would turn the floor into something a single line can disarm. If false positives on a floor rule ever make one
  necessary, the rule that misfires is the thing to fix.
- **Warning when a project config restates the machine tier** is already reported by `doctor`
  ([/decisions/ad-100.md](/decisions/ad-100.md)); moving those keys for the operator is not.

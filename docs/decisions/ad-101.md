# AD-101 — Machine data belongs to the machine, not to the install

- **status**: active

## Decision

1. **`machineHome()` is where this machine's operator data lives**: the user-tier config, the global lesson tier,
   the global rules, the price catalogue, the cross-repo spool.
2. **The launcher's own resolution never chooses it.** `tlc-exec` marks a derived home `TLC_HOME_FROM_ENV=0`, and
   that value alone sends `machineHome()` to the conventional path. Anything else — an operator's exported
   `TLC_HOME`, a suite pinning one — is honoured.
3. **`runtimeHome()` keeps naming where the code lives** and stays free to move: dist bundles, docs, the shipped
   capability catalog, the launcher being wired.
4. **`install` links the `tlc` command** into `TLC_BIN_DIR` (default `~/.local/bin`), reports the path, and says
   when that directory is not on `PATH`. A refusal is reported and the install continues.

## Why

**"Global" meant "this install", and nothing said so.** `--global` writes to `<runtime home>/state/lessons.json`
and the user tier is `<runtime home>/config.json`. The runtime home is derived from the launcher that was invoked
when nothing else names it, so a machine with an npm install and a checkout has **two** of each. Measured on an
operator's machine, in one sitting: a lesson saved with `--global` landed in a checkout's state directory while
the CLI printed *"every product on this machine will read it"*; and a user-tier config holding a subagent
allowlist stopped being read the moment the runtime home changed, which read as the setting having been deleted.

**Two concepts were wearing one name.** Where the code lives has to move — that is the whole point of `TLC_HOME`,
and of being able to run a checkout without disturbing the machine. Where the operator's data lives must not move,
or "machine-wide" is a claim the code does not keep. Splitting them is the fix; the alternative — pinning
`TLC_HOME` everywhere — makes every operator responsible for a detail the tool created.

**The flag already existed.** `TLC_HOME_FROM_ENV` was introduced so the installer could tell an operator's choice
from the launcher's own resolution, and `installDest()` already branched on it. This is the same question asked by
a second caller, not a new mechanism.

**And the reason the two installs existed at all** was that `install` never put `tlc` on `PATH`. The command came
from npm's shim, which sits in the bin directory of whichever Node version npm ran under and leaves `PATH` the
moment a version manager switches. Measured: a successful install followed immediately by
`tlc: command not found`. Meanwhile `uninstall` removed `<bin dir>/tlc`, `doctor` failed without it, and the
README said install added it — three halves of a thing that did not exist. The bin directory is now defined once
and both halves read it.

## Trade-offs

**A test that pins `TLC_HOME` without the marker keeps it.** That is deliberate: the suite's hermeticity depends on
it, and `test-env.mjs` scrubs `TLC_HOME_FROM_ENV` so a test can never be handed the launcher's answer. The cost is
that the rule is "the marker sends you to the conventional home", not "only an explicit choice is honoured" — a
weaker statement, and the honest one.

**A non-conventional `TLC_INSTALL_DEST` seeds a config nothing reads.** `install` seeds `config.json` at the
destination, and the loader now reads `machineHome()`. For the ordinary install they are the same directory. For a
relocated one they are not, and nothing warns.

**The launcher link is a convenience, not a contract.** Where a platform refuses to create a file symlink the
reason is reported and npm's shim remains the route. This does not attempt to be a package manager.

## Measured while building it

- Reverting the machine-tier rule fails 2 tests; making it always conventional fails 6 — the suite's own
  hermeticity is what that one protects; reading the marker as "chosen" instead of "derived" fails 3.
- **Nothing failed when the behaviour was first changed.** The machine tier had no rail at all, which is why the
  defect could ship: the gate was green before and after.
- Two mutations **survived** the first pass at the launcher rails, and both were the test's fault rather than the
  code's: the tests called `launcherLines` directly, so deleting its call from `wireRuntime` changed nothing, and
  the fixture had been given the launcher wrapper, so the missing-source guard was never exercised. A function that
  works and is wired to nothing is the shape this repository keeps finding
  ([/decisions/ad-100.md](/decisions/ad-100.md)).
- The missing-source guard exists because a test found it: `symlinkSync` creates a link to a path that is not
  there, and `existsSync` on a dangling link is false — so a broken launcher would have reported as linked while
  `doctor` said there was no `tlc` on `PATH`.

### The launcher step wrote into a live machine's `PATH`

Making `wireRuntime` link the command had a consequence nobody asked for: the suite calls `wireRuntime` with a
temp runtime, `launcherBinDir()` read the real `~/.local/bin`, and a test wrote a launcher there pointing at a
temp directory the same test then deleted. The operator's `tlc` became a dangling link into `/tmp` — measured on
the machine it happened to, within minutes of the change.

`test-env.mjs` redirected `TLC_HOME` and `TLC_INSTALL_DEST` and knew nothing about this one. It now redirects
`TLC_BIN_DIR` too, and the name list is split in two: variables that are **deleted** and variables that are
**redirected**. Putting the new name in the delete list is what happened first, and the guard test — which asserts
every name there is absent — failed against a value the setup had deliberately set. Two behaviours in one list is
how that happens.

Verified by measurement rather than by reading: the real launcher's mtime is unchanged across a full gate run.
Removing the redirect fails the guard, and that probe is run against the guard file alone — running the whole suite
to prove it would reproduce the defect on the machine under test.

## Not decided here

- **An operator escape hatch.** There is still no way to switch the harness off without editing provider hooks:
  `pause` disables stop checks and leaves the floor and every action-time rail running. Measured as viable — `{}`
  on stdout with exit 0 is "no opinion" to both hosts — and deliberately not built here.
- **Warning when a project config restates the machine tier** is already reported by `doctor`
  ([/decisions/ad-100.md](/decisions/ad-100.md)); moving those keys for the operator is not.

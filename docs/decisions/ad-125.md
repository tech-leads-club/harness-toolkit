# AD-125 — VS Code capability flags come from the VS Code hooks page for what a hook returns, and from the Copilot reference only for what a hook receives

- **status**: active

## Decision

The VS Code adapter declares all fifteen `ProviderCapabilities` fields
(`src/contracts/capabilities.ts`) as follows. Two sources are in play, both read 2026-09-04 — VS Code's Agent
Hooks page (<https://code.visualstudio.com/docs/agent-customization/hooks>) and GitHub's Copilot hooks reference
(<https://docs.github.com/en/copilot/reference/hooks-reference>) — and they are not interchangeable:

- **What a hook receives** comes from the Copilot reference, which publishes every payload in two formats, one of
  them labelled VS Code-compatible. That is the source T1's fixtures were written from.
- **What a hook may return, and whether it is honoured**, comes from the VS Code page only. The Copilot reference
  documents `modifiedArgs`, `modifiedResult` and a `notification` event for GitHub's own CLI and cloud agent.
  Those are a different product's output contract, and transferring them here would be analogy across products.

No value is set by analogy to Claude, whose payload shape this host reuses.

| Flag | Value | Provenance |
| --- | --- | --- |
| `enforcesHooks` | `true` | Hooks are invoked synchronously and stdout is read back; exit code `2` is a blocking error. |
| `askSupportedOn` | `["shell.before", "mcp.before", "read.before", "tool.before"]` | `PreToolUse` is the only event documented as returning `hookSpecificOutput.permissionDecision`, and it accepts `"allow" \| "deny" \| "ask"`. Those four are exactly what `PreToolUse` fans out to in `HarnessEventKind`. |
| `sessionEnv` | `false` | Unmeasured. The VS Code page documents no environment given to a hook command. The Copilot reference's `GITHUB_COPILOT_API_TOKEN` / `COPILOT_AGENT_PROMPT` are the cloud agent's, not this host's. |
| `nativeLoopCounter` | `false` | `Stop` carries `stop_hook_active`, a boolean saying a hook already forced this turn to continue. `effectiveLoopCount` (`src/core/turn/turn.loop-counter.ts:50`) reads `event.loopCount` as a *count*, which no VS Code payload supplies. |
| `dedicatedShellEvent` | `false` | There is no shell event. Terminal execution arrives as `PreToolUse` with `tool_name: "runTerminalCommand"`. |
| `toolInputRewrite` | `false` | Unmeasured. The VS Code page documents `permissionDecision` on `PreToolUse` and no argument substitution. `modifiedArgs` exists in the Copilot reference, for the Copilot CLI. |
| `toolOutputRewrite` | `false` | Unmeasured, same split: the VS Code page documents no result replacement on `PostToolUse`; `modifiedResult` is the Copilot CLI's. |
| `contextAtToolBefore` | `false` | Both sources agree here, which is why this one is not merely conservative: the VS Code page documents `PreToolUse` output as a permission decision, and the Copilot reference states outright that `preToolUse` does not return `additionalContext`. |
| `contextAtToolAfter` | `false` | Unmeasured. `additionalContext` on `postToolUse` is documented in the Copilot reference only; the VS Code page does not carry it. |
| `contextAtStop` | `false` | No context channel at `Stop`. The common outputs are `continue`, `stopReason` and `systemMessage` — an operator-visible warning is not context to the model — and the Copilot reference's stop output is `decision` plus `reason`. |
| `sessionStartContextReliable` | `true` | The VS Code page documents `hookSpecificOutput.additionalContext` on `SessionStart`, so this is the host's own output contract rather than a transfer, and the transcription measured it as reliable. |
| `toolOutputAtAfter` | `true` | `PostToolUse` receives `tool_result` with `result_type` and `text_result_for_llm` — an input shape, so the Copilot reference settles it. Reproduced in `src/providers/vscode/__test__/fixtures/post-tool-use-terminal.json`. |
| `usageInPayload` | `false` | No token or cost field in any documented payload on either page. |
| `effortSignal` | `false` | No model or reasoning-effort field in any documented payload. |
| `thoughtEvent` | `false` | Neither source lists a thought or reasoning event. |

The documented event list is `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PreCompact`,
`SubagentStart`, `SubagentStop`, `Stop`. Hook configuration lives in `.github/hooks/*.json` for a workspace and
`~/.copilot/hooks` for a user, which is the target design §8 already names.

## Why

**The two sources disagree, and picking the wrong one would have shipped three rails that do nothing.** The
Copilot reference is a genuinely useful document — it is the only per-event payload schema either vendor
publishes, and every fixture in `src/providers/vscode/__test__/fixtures/` came from it. It also documents an
output contract for GitHub's own CLI and cloud agent that VS Code's page does not repeat: argument substitution,
result replacement, and context injection at `postToolUse`. Reading those as VS Code's would have declared
`toolInputRewrite`, `toolOutputRewrite` and `contextAtToolAfter` true on a host whose own documentation shows a
permission decision and nothing else.

The split is not a preference between sources, it is the asymmetry in `src/contracts/capabilities.ts:14`. Getting
an *input* shape wrong produces a parse that visibly misses a field, and T1's fixtures are checked against the
adapter. Getting an *output* claim wrong produces a decision the host discards in silence.

**This corrects three claims the design carried from the transcription.** The transcription describes
`hookSpecificOutput.additionalContext` for context injection at before, after, and stop, and design §6 repeats
it. Neither source supports it at any of the three: `preToolUse` is documented as not returning it, `postToolUse`
carries it only in the Copilot reference, and `Stop` has no such field on either page. Spec P4 AC4 asserted that
behaviour and has been amended, because a test written to it would have asserted something `degrade()` will now
strip. `SessionStart` is the one place `additionalContext` is documented on the VS Code page, and it survives
intact — which is also why this host still needs no durable lessons file by default.

**`nativeLoopCounter` asks for a count, not a flag.** `stop_hook_active` is a boolean, and both
`effectiveLoopCount` and `stopHandler` (`src/entrypoints/stop.ts:469`) read `event.loopCount` as a number
compared against `policy.grind.maxLoops`. Declaring `true` on a boolean feeds the cap a value that never grows,
so a grind loop would never reach its limit. Claude carries the same `stop_hook_active` field and declares this
flag `false` for the same reason (`src/providers/claude/claude.capabilities.ts:8`);
[/decisions/ad-123.md](/decisions/ad-123.md) is corrected to match.

## Trade-offs

**Four flags are `false` on silence rather than on evidence of absence, and this host is the worst place to be
wrong about that.** VS Code Agent Hooks are Preview, its page documents the output contract loosely, and the
adapter is deliberately not dispatched (spec P4 AC5), so nobody will trip over an understated flag and report it.
`toolInputRewrite`, `toolOutputRewrite`, `contextAtToolAfter` and `sessionEnv` are the four; each costs a rail
that would otherwise work. The check is cheap and it is the same session for all four: one VS Code session with a
hook that returns each field and a look at whether the agent's behaviour changes.

**The Copilot reference may simply be ahead of the VS Code page.** These are two views of one hook system, and
the fields this record refuses are plausible for VS Code — `modifiedArgs` is exactly what `PreToolUse` would need
for a rewrite rail. If they are honoured, this record understates the host by four flags and the fix is a
measurement, not a redesign. The reverse error has no such recovery: an overstated flag produces no error at all.

**`toolOutputAtAfter: true` crosses the line this record draws, deliberately.** It is settled by the Copilot
reference alone, because it describes what the payload *carries* rather than what the host honours, and the
fixtures already parse it. A reader who wants one rule for both directions will find this inconsistent; the rule
is input-versus-output, and it is stated at the top so the inconsistency is a decision rather than a slip.

## Not decided here

- **Whether the VS Code writer is ever dispatched.** `vscode-hooks-json` wiring stays behind an explicit deferral
  branch while Agent Hooks are Preview. This record settles capabilities only.
- **The `mcp_` tool-name prefix.** Neither source enumerates VS Code's MCP tool naming; the single-underscore form
  in the fan-out is design §5's and is flagged in the fixtures' provenance as the first thing a capture should
  confirm. `askSupportedOn` lists `mcp.before` because `PreToolUse` fans out to it, which is independent of how
  the name is spelled.
- **`SubagentStart`'s numeric `timestamp`.** The Copilot reference types it as a number where every sibling event
  types it as an ISO 8601 string; the fixture follows the siblings. Recorded in the fixtures' provenance, not
  settled here — it touches parsing, not capability.
- **The other two hosts' flags.** Codex is [/decisions/ad-123.md](/decisions/ad-123.md), opencode is
  [/decisions/ad-124.md](/decisions/ad-124.md). Nothing here transfers to either, and this host's Claude-shaped
  payload is the reason that rule matters most here.

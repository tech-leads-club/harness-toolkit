# AD-125 — A provider's docs and file scaffold are generated from its own code, never hand-maintained

- **status**: active

**Corrected by [/decisions/ad-126.md](/decisions/ad-126.md).** This record's doc-generation half
(`render-provider-docs.ts`, point 2 below) stands unchanged and still describes the current code. Its
scaffold-reachability choice — publishing `tlc harness new-provider` as a real CLI subcommand (point 1 below) —
was wrong: a real install's runtime home cannot durably hold a scaffolded provider (`AD-126` has the evidence).
The scaffold itself is unchanged in behavior; only where it is reachable from changed, to
`tools/dev/new-provider.ts`, contributor-only.

## Decision

**1. `tlc harness new-provider <name>` scaffolds a new provider's files.** `tools/new-provider.ts` — published
alongside `doctor.ts`, `init-project.ts`, and the rest of `tools/`'s CLI-subcommand modules, not
`tools/dev/` — validates the name (the same whitespace/slash/reserved-word check
`provider.contract.test.ts` already asserts), refuses if `src/providers/<name>/` exists, and writes
`<name>.detect.ts`, `<name>.capabilities.ts`, `<name>.policy-defaults.ts`, `<name>.inbound.ts`,
`<name>.wiring.ts`, `<name>.outbound.ts`, and `<name>/index.ts` — the last two beyond the five originally
planned, because nothing short of a full `ProviderPort` object is registrable, and `provider.contract.test.ts`'s
`assertSatisfiesContract` is the thing a scaffolded stub is meant to fail cleanly against, not crash against
(marked `SPEC_DEVIATION` in the generator's own source). It also seeds `docs/providers/<name>.md` with the
standard section headings and empty generated-marker regions, and appends one line to
`provider.registry.ts`'s `providers` array.

**2. `tools/dev/render-provider-docs.ts` renders each provider's capability and event-mapping tables from its
own code**, the same generated-region mechanism `render-capabilities.ts` already uses
(`<!-- generated:X --> ... <!-- /generated -->` markers, a `--check` mode). `claude.inbound.ts` and
`cursor.inbound.ts`'s `EVENT_KIND_BY_HOOK` maps — previously module-private — are exported, and each file's
`PreToolUse`/`PostToolUse` tool-name fan-out (previously an inline conditional chain) is extracted into an
adjacent exported declarative table, mirroring `claude.wiring.ts`'s existing `ENTRY_SPECS` shape. Both existing
provider docs (`claude-code.md`, `cursor.md`) had their hand-written tables replaced by these markers; the
round-trip against the committed text was verified to be a zero-diff before the markers were trusted.

**3. `tools/__test__/provider-docs-coverage.test.ts` fails when a provider's doc drifts from its code** —
sibling to `docs-coverage.test.ts`, same assertion shape, wired into `tlc harness test`'s existing build-gate
step list as `"provider docs in sync"`.

## Why

**The barrier this closes was never "how do I add a provider" — that was already documented and
contract-tested.** `docs/providers/index.md` already states the pattern precisely, and
`provider.contract.test.ts`'s fixture-provider test already proves a conforming adapter registers by touching
one file's worth of new code. What had no safeguard: the six-file shape two providers happened to share by
convention alone, and a capability/event-mapping table that restated in prose exactly what
`<name>.capabilities.ts`/`<name>.inbound.ts` already declared in code, checked against nothing.

**`capabilities.md` already solved the identical problem once.** It is generated from `capabilities/catalog.json`
and checked by `docs-coverage.test.ts` specifically because a hand-maintained list of this project's own rails
had already drifted before that mechanism existed. Applying the same generate-and-check shape to provider docs
is not a new pattern — it is the existing one, extended to a place it had not yet reached.

**A third-party scaffolding library was evaluated and rejected on its actual dependency cost, not on
reputation.** `plop`/`node-plop` — the more actively maintained option in this space — pull in 7 and 10 direct
dependencies respectively (confirmed against the real npm registry manifests, not a summary), including
`inquirer`'s own tree, to solve a problem `tools/dev/render-capabilities.ts` already proves a ~100-line script
solves with none. This project ships zero runtime dependencies and five devDependencies total; the existing
`render-capabilities.ts` is the in-repo precedent for exactly this shape of tool, and `tools/new-provider.ts`
follows it rather than introducing the first scaffolding dependency this project would ever carry.

**The event-mapping table's source had to be code the generator can actually read, not a description of it.**
`EVENT_KIND_BY_HOOK` was already a declarative `Record`, just module-private; exporting it cost nothing.
`PreToolUse`'s tool-name fan-out was not — it was an inline `if`/`else` chain, which a generator cannot render
into a table without re-implementing the logic it is supposed to describe. Extracting it into an adjacent
declarative table (the same shape `claude.wiring.ts`'s `ENTRY_SPECS` already uses for wiring entries) makes it
data a renderer can consume, and keeps the extraction verified as behavior-preserving by running the existing
`claude.detect.test.ts`/`cursor.detect.test.ts` suites unmodified before and after.

## Trade-offs

**Extracting the fan-out table touched working, tested routing code in both providers.** The risk is a
regression in which event kind a given `tool_name` produces — mitigated by, not merely hoped away by, the
existing detect-test suites passing byte-for-byte unmodified, which is what "behavior-preserving" is claimed on.

**The scaffold generates two more files than the original design named (`outbound.ts`, `index.ts`).** A
six-file scaffold that produces something `assertSatisfiesContract` cannot even attempt to check — because there
is no `ProviderPort` object to check — would have been a smaller diff and a less useful starting point. The
larger scaffold is the one that fails informatively.

**Retrofitting `claude-code.md`/`cursor.md` to fully generated tables happened as part of landing the
mechanism, not deferred.** This was necessary to prove the round-trip before trusting the drift test on new
providers at all — a generator that has never been checked against real, previously-hand-written content is not
yet proven correct.

## Not decided here

- **Generating a provider's `Detection`, `Policy defaults`, `Wiring target`, or `Lessons view` prose sections.**
  Those describe adapter-specific logic (a regex, a merge strategy, a file-write convention) that is not a flat
  table a generator can render from a data structure the way capabilities and event maps are; they remain
  hand-written, inside the generated markers' surrounding, untouched prose.
- **An interactive scaffold wizard** (prompting for provider-specific values as it generates). The generator
  takes a name and emits fixed-shape stubs; a wizard is a larger tool for a problem this scaffold's size does
  not yet require.

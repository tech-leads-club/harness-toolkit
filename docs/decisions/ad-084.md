# AD-084 — The rule about unpinned dependencies is applied to this repository too, and the release gate stops being a copy

- **status**: active

## Decision

1. **Every third-party action is pinned to a 40-character commit SHA**, with the version in a trailing comment.
2. ~~**A gate step refuses a tag**, `tools/dev/check-workflows.ts`.~~ **Superseded within hours by
   [/decisions/ad-088.md](/decisions/ad-088.md):** `zizmor` enforces this as `unpinned-uses: hash-pin` and nine
   other audits besides, so the hand-written checker was deleted rather than kept beside it.
3. **A local reusable workflow (`./.github/workflows/…`) is exempt**, because it is this repository at this commit.
4. ~~**`ci.yml` gains `workflow_call`, and `release.yml` calls it.**~~ The publish job no longer runs
   `tlc harness test` itself — but calling `ci.yml` traded a wrong verification for a redundant one, because CI had
   already run the same matrix on the same commit. **Superseded by
   [/decisions/ad-089.md](/decisions/ad-089.md):** the release is chained to CI completing green instead.
5. **Actions are brought to current**: `checkout` v4 → v7.0.1, `setup-node` v4 → v7.0.0,
   `release-please-action` v4 → v5.0.0, `setup-bun` v2 → v2.2.0.

## Why

**The rail was pointed outward only.** `supplyChain` asks before a turn adds a dependency with no pinned version,
because what a tag resolves to is whatever the publisher last pushed
([/decisions/ad-075.md](/decisions/ad-075.md)). Measured here while that rail was shipping: twelve `uses:`
references, **three** pinned and **nine** on mutable tags. A mutable tag on `actions/checkout` is a third party
holding write access to every job in this repository, including the one that publishes to npm — the exact hazard the
rail describes, in the workflow that enforces it.

**Three of them were three majors behind, which is what a mutable tag hides.** `actions/checkout@v4` resolved to
something maintained; the current release is v7.0.1. `setup-node@v4` against v7.0.0. Nothing surfaced that, because
`@v4` keeps resolving and keeps working. A SHA pin makes the version a fact in the file, so being behind is
visible in a diff rather than discoverable only by going to look.

**A pin without a version comment is unreadable, so both halves are required.** Forty hex characters say nothing
about what you are on; bumping one would mean resolving the SHA by hand first. The comment is what makes the pin
maintainable, so a bare SHA fails as its own rule rather than passing quietly.

**The publish gate was a second, weaker copy of the merge gate.** `ci.yml` runs `tlc harness test` on ubuntu,
macos and windows. The publish job ran `tlc harness test` again, inline, on ubuntu only — so what decided whether
to publish covered one platform while what decided whether to merge covered three, and the two lists of steps had
to be kept in step by hand. Calling the workflow removes both problems at once: one definition, three platforms,
and a publish that cannot run unless the matrix passed at the commit the tag points at.

**`release-please-action` v5's only documented breaking change is its runtime moving to Node 24**, which is the
deprecation warning our own runs were printing. The outputs this workflow consumes — `release_created`,
`tag_name`, `prs_created`, `pr` — are unchanged.

## Trade-offs

**A pin has to be bumped by somebody.** A tag receives security fixes silently; a SHA does not. That is the trade
the supply-chain rail already makes on the user's behalf, and taking it here means action updates are now a commit
with a diff, which is the point. Dependabot can open those, and nothing here does yet.

**The checker validates the shape of a pin, not that the SHA is the version claimed.** Confirming that
`3d3c42e…` really is `v7.0.1` needs the network on every gate run. A comment that lies is possible and would be
caught by anyone reading the diff, which is a weaker guarantee than the one on the SHA itself.

**A called workflow adds a job to the release run.** `verify` is the full three-platform matrix, so a publish now
waits several minutes on work the CI run for the same commit already did — the two are separate runs of the same
matrix, not one shared result. Reusing the earlier run's verdict would mean querying its status by API and trusting
a lookup, which is worse than paying for the second run.

**Four actions moved majors in one commit.** Each is used with basic inputs only — `fetch-depth`, `ref`, `token`,
`node-version`, `registry-url`, `bun-version` — so the surface is small, but the proof is CI on three platforms
rather than a reading of four changelogs.

## Not decided here

- **Dependabot for action bumps.** Pinning creates the maintenance the tag was hiding, and nothing automates it.
- **Verifying that a pinned SHA matches its version comment.** It needs the network, so it belongs in a scheduled
  job rather than in the gate.
- **Whether `verify` should reuse the CI run for the same commit** instead of running the matrix again.
- **The `dist/` build inside the publish job.** It still rebuilds rather than trusting the committed bundles, which
  is deliberate ([/decisions/ad-046.md](/decisions/ad-046.md)) and unaffected by this.

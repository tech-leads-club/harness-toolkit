# AD-135 — `pr-open` recognizes its MCP surface

- **status**: active

## Decision

1. **`rules.trigger.ts` gains a third matching primitive, `matchesMcpShape`**, alongside `matchesShape` (CLI
   words, AD-100) and `matchesApiShape` (REST path and method, AD-128). It normalizes an MCP tool call's own
   name — stripping Claude Code's `mcp__<server>__` prefix (the server name is operator-configured, not
   fixed; the strip is structural, splitting on the *last* `__`, not a literal string) and Cursor's `MCP:`
   host prefix — down to the bare act name, and compares it against a small table of recognized acts.
2. **`pr-open` recognizes the GitHub MCP server's `create_pull_request` tool call** as the same act as
   `gh pr create` and `gh api .../pulls -X POST` — the one tool name evidenced in production, on both
   `mcp__github__create_pull_request` (Claude Code) and the bare `create_pull_request` (Cursor's
   `beforeMCPExecution` payload) forms. An MCP tool name whose normalized form does not exactly equal
   `create_pull_request` — including a plausible near-miss like `create_pull_request_comment` or
   `list_pull_requests` — does not fire; the match is exact, never a substring or suffix test.
3. **Repository scope, the same discipline AD-130 already established for `API_SHAPES`.** When the MCP call's
   own arguments name an `owner`/`repo` and the local repository's remote is known, the trigger fires only
   when they match. Absent fields, an unresolved remote, or a caller that never asked for the remote at all
   behave exactly as `matchesApiShape` already behaves for the equivalent cases — one contract, two
   consumers, not two rules to remember.
4. **`TriggerContext` gains `toolInput?: Record<string, unknown>`**, and `tool-before.ts`'s `rulesDecision`
   populates it and widens the existing "only resolve `repoRemote` when it might matter"
   ([/decisions/ad-130.md](/decisions/ad-130.md)) condition to also cover an MCP call whose tool name could
   possibly be pr-open-shaped — a new `mentionsMcpAct` export, the MCP-side sibling of the existing
   `mentionsGhApi`, checked before paying for the extra `git remote` process.
5. **`docs/concepts.md`'s escape-hatch paragraph, corrected once already by AD-128, is corrected again**: it
   now names the one evidenced MCP tool name as recognized, and restates explicitly that this covers that one
   name, not MCP as a class — the same "narrow what's evidenced, name what remains" shape AD-128 used for
   `gh api`'s own residual gaps.

## Why

**A third grammar for the same act, not a fourth instance of an already-known one.** AD-100's original design
read CLI subcommand words. AD-128 added a second grammar, a REST path and inferred method, for the exact
reason this record repeats now: an agent blocked on one grammar reached for a different tool that performs the
identical real-world act, ungated, because the trigger-matching layer had no code path for it. The shape of
the fix is the same each time — recognize the newly-evidenced grammar, narrowly, without claiming to close the
open class — but MCP is not `gh api` wearing a different hat; it carries no shell command at all, so it needed
its own primitive rather than a wider `ApiShape`.

**The evidence, read directly, not reconstructed.** In one incident window, an operator's `pr-open` rule
correctly denied six distinct attempts — `gh pr create` bare, wrapped, with `--body-file`, and `gh api
.../pulls -X POST` bare and piped — proving AD-127 and AD-128's fixes work exactly as designed for every shape
they were built to recognize. In the same window, the GitHub MCP server's `create_pull_request` tool was
invoked twice and reached `triggerMatches` with `context.command === undefined`, which the existing
`pr-open`/`commit`/`push`/`pr-merge` case returned `false` for immediately, with no MCP-aware fallback of any
kind. Both calls happened to fail for reasons unrelated to this project's own policy; had either succeeded,
the pull request would have opened with zero rule evaluation.

**Exact-name matching, not a suffix or substring test, for the same reason AD-128 inferred the HTTP method
rather than matching the path alone.** A detector firing on any tool name containing `pull_request` would
match `create_pull_request_comment` or `list_pull_requests` — the second of which is the single most common,
entirely harmless MCP call an agent makes when checking whether a pull request already exists. A false
positive here has the same cost AD-128 already named for `gh api`: it trains an operator to distrust or
disable a rule that fires on ordinary work.

**Repository scope reuses AD-130's contract instead of inventing a second one.** An agent managing more than
one repository in a session, with a `pr-open` rule scoped to one of them, should not have that rule fire on an
MCP call that names a different repository. `matchesApiShape` already solved this for the REST grammar with a
three-way `repoRemote` contract (`undefined` = never resolved, `null` = resolved and absent, a value =
resolved and present); `matchesMcpShape` reads the exact same contract rather than defining its own meaning
for the same three states.

## Trade-offs

**A third matching primitive now lives beside the other two.** `matchesShape` reads CLI words;
`matchesApiShape` reads a REST path and an inferred method; `matchesMcpShape` reads a normalized tool name and
optional structured arguments. Three declarative tables sharing almost no fields would read as unification if
forced together and cost precision on all three — the duplication here is of the table shape per grammar, not
of the underlying primitives (`normalizeMcpToolName` is its own pure function, independently testable, the
same separation `apiPathSegments` already keeps from `matchesApiShape`).

**The prefix-stripping normalizer is evidenced on two providers' payloads, not exhaustively on every host this
project might support later.** `mcp__<server>__` (Claude Code) and `MCP:` (a Cursor debug trace) are both
read directly from real payloads captured in the incident and from this project's own provider adapters
(`cursor.inbound.ts`, `claude.inbound.ts`), not guessed. A future provider with a third convention is not
covered until evidenced, the same way `commit` gained no `gh api` equivalent in AD-128 because none had been
observed.

**Only `create_pull_request` is recognized; `push` and `pr-merge` gain no MCP shape.** No MCP tool call
performing either act has been observed in any incident. Inventing one to close speculatively would repeat the
mistake AD-128's own "Not decided here" explicitly declined to make for `commit`.

## Not decided here

- **Any MCP tool name other than `create_pull_request`.** Not evidenced; a distinct record if one surfaces.
- **`push`/`pr-merge` recognizing an MCP equivalent.** Same reasoning as above, restated for the two other
  built-in triggers.
- **A generic "any MCP tool matching a named trigger" authoring surface.** The existing `{kind: "tool", name:
  string}` trigger already lets an operator gate an arbitrary tool call directly; this record extends the
  *built-in* `pr-open` vocabulary to recognize one more grammar for the same act, not a new authoring
  primitive.
- **A second, distinct gap in the same incident — a shell-form `gh api .../pulls` call that escaped rule
  evaluation entirely, from a concurrent session, with the matching logic itself already proven correct for
  that exact shape.** Not yet root-caused with the certainty this project requires before designing a fix.
  Addressed as an observability addition, not a fix, in a separate record.

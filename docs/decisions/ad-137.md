# AD-137 — Gate artifacts are scoped per session, the same fix AD-122 already proved for handoff

- **status**: active

## Decision

1. **`lastGatePath`, `writeLastGate`, `readLastGate` (`src/core/gate/gate.artifact.ts`) require a
   `sessionKey`.** The artifact moves from a single, project-wide `last-gate.json` to
   `gate-sessions/<sanitizeSegment(sessionKey)>.json` — a new `gateSessionsDir(root)` helper in
   `platform/paths.ts`, placed beside the existing `handoffSessionsDir`. `sessionKey` needs no second key of
   its own inside the path (no separate provider dimension) — it is already globally unique across
   providers, the identical reasoning `handoffSessionPath`'s own comment already states.
2. **`cachedVerdict` (`gate.inputs.ts`) is untouched.** It was already a pure function over whatever artifact
   it is handed; the defect was entirely in what `readLastGate` could return, never in the cache-hit
   predicate itself.
3. **`stop.ts`'s two call sites thread `args.sessionKey`** — already present on the enclosing function's own
   parameters, used elsewhere in the same function for `recordGateOutcome`/`creditPendingLessons`. No new
   value introduced, an already-available one finally reaches the two places that needed it.
4. **`pruneGateSessions(root, { maxAgeMs })`, age-only, no liveness check**, deletes a `gate-sessions/` file
   once its own recorded `ts` exceeds the retention window (default seven days, matching
   `pruneDeadHandoffSessions`'s own). Called from `session-start.ts` beside the existing
   `pruneDeadHandoffSessions(root)` call.
5. **`gate.lock.ts`, `gateReportPath`, `clearGateReport` are unchanged.** The lock's pid-based, project-scoped
   mutual exclusion is correct for its own purpose — one long-running gate command executing at a time — a
   genuinely different question from whose cached result a session reads. The report path is read
   synchronously right after the same invocation's own gate run finishes; it was never cached across turns
   or sessions.
6. **A second gap, found by the Verifier reviewing 1–5: `stop.ts`'s `changedFiles` is computed from `git diff`
   against the shared working tree, so a file only a concurrent neighbour touched still counted as "changed"
   for every session.** `filesClaimedByOtherLiveSessions(root, provider, sessionKey)`
   (`src/core/presence/presence.service.ts`) reuses the per-session `recent_files` claim tracking AD-099
   already built for edit-collision purposes: a live neighbour's own claimed file is excluded from this
   session's own `changedFiles`, unless this session's own presence record claims it too. `stop.ts` filters
   `changedFiles` through it once, at the single existing call site, so every downstream consumer —
   `codeTargets`, `testTargets`, the comment scope, supply-chain scanning, duplication detection, ship
   evidence — inherits the correction automatically.

## Why

**AD-122 already answered this question, for a sibling subsystem it never touched.** Its own words: "Two
concurrent sessions of the same provider... silently read and overwrote each other's slice: one session's
blocked-turn follow-up surfaced as if it were the other's own." That record moved `handoff.json`'s continuity
fields — `blockers`, `next_action`, plan state, and, notably, a field literally named `last_gate_result` — into
`handoff-sessions/`. It did not touch `gate.artifact.ts`'s own, separate `last-gate.json`, which is not a
continuity *field* but an entirely different file, carrying the actual gate *artifact* (command, exit code,
output, findings) that `handoff`'s own `last_gate_result` field only ever summarized. The identical defect
class survived, unfixed, in the mechanism that actually produces what a `Stop` decision reads.

**Confirmed live, directly, not inferred from the code alone.** Two concurrent agent sessions working the
same checkout — one making code changes, one making none — reproduced the exact shape AD-122's own incident
described, in the sibling system. The code-changing session ran a failing lint gate and wrote
`last-gate.json`. The other session's own `Stop` event, moments later, combined its own correctly
session-scoped loop counter (`.tlc/harness/state/loops/<sessionKey>.json` — read directly, confirmed already
isolated per session) with the *other* session's gate artifact, read via `readLastGate(args.root)`, which took
no session parameter at all — and built a `BLOCKED: lint failed...` message blaming a session that had touched
nothing.

**Reuse the proven pattern; do not re-derive it.** `handoff-sessions/`'s per-session-file shape, its
`sanitizeSegment(sessionKey)` keying, and the directory-helper convention in `platform/paths.ts` are already
built, already reviewed, already mutation-tested. Gate artifacts needed the identical shape — one file, one
session, one directory — not a second, independently-invented mechanism for the same problem. This is the
same "one algorithm, one place" discipline [/decisions/ad-100.md](/decisions/ad-100.md) already states,
applied to a second consumer of an existing pattern rather than a new algorithm.

**Deliberately narrower than AD-122's own fix — on purpose, not by oversight.** AD-122's predecessor
inheritance (`findDeadPredecessor`, presence-liveness gating, materialize-once-at-first-write) exists because
handoff carries a *continuity narrative* — a restarted session needs its own prior blockers and plan state
back, or the whole point of continuity is lost. A gate artifact carries no narrative: a session that restarts
under a new `sessionKey` simply re-runs its gate once more, which is correct and cheap, not a defect this
record needs to solve. Porting AD-122's inheritance machinery here would be scope the incident never asked
for — the same restraint AD-128's own "Not decided here" already modeled for a different mechanism.

**The artifact fix alone did not close the incident, and a fresh review is what found that, not this
record's own author.** Two sessions sharing one checkout share one git working tree — `git diff` has no
concept of authorship for an uncommitted change, so a file only session A touched still appeared in session
B's own `changedFiles` after Decision items 1–5 shipped, and B ran its own copy of A's gate against A's own
file and blocked on it, the same final text as the original incident. Decision item 6 closes this the same
way as the rest of the record: reuse what already exists (`recent_files`, AD-099's own per-session file-claim
tracking) rather than invent a second mechanism for the same class of question.

## Trade-offs

**A session that legitimately wants to reuse another *live* session's already-passing gate result cannot.**
Before this record, two sessions racing to fix the same lint errors would have let the second one see the
first one's passing result "for free," at the cost of also seeing its failures misattributed — the exact
defect this record closes. After this record, each session always runs its own gate at least once per
distinct file state, even when a concurrent sibling already proved the same command would pass. Accepted: a
session under-informed about a concurrent success is a correctness-neutral inefficiency (one extra gate run);
a session mis-blamed for a concurrent failure was the actual incident.

**One more directory, one more file per session, mirroring `handoff-sessions/`'s own shape and cost.**
Bounded by `pruneGateSessions`'s seven-day, age-only retention — simpler than `handoff-sessions/`'s own
liveness-aware pruning, since nothing here needs to tell a live neighbor from a dead one before deleting.

**Every existing test that read or wrote `last-gate.json` directly, or called `writeLastGate`/`readLastGate`
without a `sessionKey`, needed updating.** All were within `gate.artifact.ts`'s own test file, `stop.ts`'s two
call sites, and a handful of `stop.test.ts`/`stop.gate-cache.test.ts`/`core.facade.test.ts` tests that read
the artifact back to assert on it — a one-time migration cost, not a recurring one.

**Excluding a live neighbour's claimed file costs one presence-directory read per `Stop` event, and only
excludes what is positively attributed.** An unclaimed file — a shell script's own edit, a generated output,
anything predating presence tracking — always stays in scope, for every session, exactly as before this
record; the correction only ever narrows scope when a *different, live* session's own claim names the exact
file, never on an absence of evidence.

## Not decided here

- **Predecessor inheritance for gate artifacts on session restart.** Not evidenced as broken; named explicitly
  in scope, per the Why section above — a materially larger feature than this incident asks for.
- **Any change to `gate.lock.ts`'s mutual-exclusion mechanism.** Already correct for its own purpose; not
  part of this defect.
- **A multi-session gate-status view** (a `tlc harness gate status` equivalent to `tlc harness handoff`).
  The diagnostic surface for gate state is unchanged by this record — only its underlying isolation is fixed.
- **A file changed by a concurrent session through a shell command rather than an Edit/Write tool call.**
  `claimsFile` (`run.ts`, AD-099) only claims a file on `edit.after` or a recognized write-tool event; a
  session that modifies a file via `Bash`/`Shell` (a codegen script, `sed -i`) leaves no presence claim for
  `filesClaimedByOtherLiveSessions` to find, so that file is not excluded from a neighbour's own scope. Not
  evidenced in the reported incident (a direct Edit); a distinct record if a shell-driven instance surfaces.

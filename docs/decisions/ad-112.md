# AD-112 — A codegen tool's own banner is not agent narration

- **status**: active

## Decision

1. **`isCommentLine` also exempts a generated-file banner** via `isGeneratedFileBanner`: the Phabricator/
   GitHub-Linguist `@generated` pragma, or a `generat*` word within the first 20 characters of the comment
   body followed by `do not edit` within 20 characters of it, on a line no longer than 90 characters total
   — covers `// TERRAMATE: GENERATED AUTOMATICALLY DO NOT EDIT`, `// Code generated by go-swagger; DO NOT
   EDIT.`, `# AUTO-GENERATED FILE. DO NOT EDIT.`, and equivalents from other generators.
2. **A declared reason always wins, checked first.** If the line also matches `why:`/`hazard:`/
   `invariant:`, the banner exemption never applies — it is judged as declared prose instead of vanishing
   from the scan uncounted.
3. **No file-position requirement**, matched the same way `TOOL_DIRECTIVE` already is — anywhere a comment
   line appears, not only the file's first line.
4. **Both stop-time (`commentViolationMessage`) and the edit-time advisory
   ([/decisions/ad-111.md](/decisions/ad-111.md)) inherit this for free** — both call `isCommentLine`
   through the same `findAddedComments`/`scanAddedComments` path; nothing else needed to change.

## Why

**Reported live, from a different project running this harness, mid-turn.** A session working an
Infrastructure-as-Code cutover hit the comment gate three times in a row on
`_terramate_generated_app.tf:1`, `_terramate_generated_backend.tf:1`, `_terramate_generated_versions.tf:1`
— all three the identical banner `terramate generate` stamps on every regenerated file, unchanged across
44 other stacks already merged in that repo. The agent correctly refused to delete the line (it would
have broken that project's `terramate-drift` CI check, and reappeared on the next `terramate generate`
regardless), explained this to the operator twice, and then correctly escalated rather than repeat the
same explanation a third time — but had no way to make the gate itself stop firing, because nothing in
`policy.comments` distinguishes a tool's own stamp from prose an agent chose to write.

**The existing exemption already drew this line for a narrower case.** `TOOL_DIRECTIVE` exempts
`biome-ignore`, `eslint-disable`, `@ts-expect-error`, and similar — text a *linter* emits or reads, not
an operator or an agent. A codegen banner is the same category of thing: mechanical, deterministic,
identical on every regeneration, authored by neither party the gate exists to keep honest. Two real
conventions already cover most of what generators emit — Phabricator's `@generated` pragma (which GitHub
Linguist also recognises) and the "Code generated ... DO NOT EDIT" phrasing Go's own tooling popularised
(go-swagger, `go generate` output) — so the pattern generalizes past this one report.

## Trade-offs

**A short, undeclared sentence that happens to open with a `generat*` word and reaches "do not edit"
within 20 characters still exempts** — verified against `"this generates X, do not edit the cache key
without also updating Y"` (70 characters, "generates" at position 5), which still passes both checks.
The declared-reason guard closes the dangerous half of this (real narration tagged `why:`/`hazard:`/
`invariant:` is never swallowed); an *undeclared* sentence built to specifically mimic the shape of a
banner can still slip through unflagged. Same class of risk `TOOL_DIRECTIVE` already accepts — a
`// biome-ignore: because I said so` is not stopped either — and closing it further needs either a
tighter window (risking real generator wording it would then miss) or a stricter grammar than a regex
comfortably expresses. Left as an accepted, documented gap rather than over-fit to one crafted example.

**No file-position restriction, so the match works anywhere in a comment, not only a file's first
line.** Considered restricting to line 1 (where every observed convention actually places the banner).
Rejected for now: the existing `TOOL_DIRECTIVE` exemption already has no positional restriction either,
so this follows the accepted precedent rather than inventing a stricter rule only for this case.

**Requires both a `generat*` word and `do not edit` in the same short span.** A generator whose banner
uses neither phrase (a bare `// autogenerated`, with no "do not edit") is not covered. Not invented
ahead of a real report.

## Not decided here

- **Closing the residual undeclared-sentence gap named above.** Worth doing if it is ever actually
  exploited or hit by accident in a real project; the mitigation (declared reason wins) already covers
  the case that mattered most.
- **Restricting the match to a file's first few lines.** Worth doing if the no-position choice is ever
  actually exploited, not before.
- **A configurable per-project list of generator banners**, for a generator whose exact wording this
  pattern misses. No project has reported one yet.

> **Correction, 2026-08-26.** The first version of this exemption checked only `generat* ... do not
> edit` within a 40-character window, with no declared-reason guard — an independent verifier found that
> a real `why:`/`hazard:` line mentioning both words nearby would vanish from the scan uncounted instead
> of being judged as declared prose. Fixed before this record's first commit reached the remote: the
> declared-reason check now runs first, and the window narrowed to 20 characters with a 90-character
> line cap. The Decision and Trade-offs sections above already describe the corrected version.

# AD-112 — A codegen tool's own banner is not agent narration

- **status**: active

## Decision

1. **`isCommentLine` also exempts a generated-file marker**: `@generated` (the Phabricator/GitHub-Linguist
   pragma) or any line combining a `generat*` word with `do not edit` within 40 characters — covers
   `// TERRAMATE: GENERATED AUTOMATICALLY DO NOT EDIT`, `// Code generated by go-swagger; DO NOT EDIT.`,
   `# AUTO-GENERATED FILE. DO NOT EDIT.`, and equivalents from other generators.
2. **No position requirement.** Matched the same way `TOOL_DIRECTIVE` already is — anywhere a comment
   line appears, not only the file's first line. Simpler, and consistent with how the existing exemptions
   already work.
3. **Both stop-time (`commentViolationMessage`) and the edit-time advisory
   ([/decisions/ad-111.md](/decisions/ad-111.md)) inherit this for free** — both call `isCommentLine`
   through the same `findAddedComments`/`scanAddedComments` path; nothing else needed to change.

## Why

**Reported live, from a different project running this harness, mid-turn.** A session working an
Infrastructure-as-Code cutover hit the comment gate three times in a row on
`_terramate_generated_app.tf:1`, `_terramate_generated_backend.tf:1`, `_terramate_generated_versions.tf:1`
— all three the identical banner `terramate generate` stamps on every regenerated file, unchanged across
44 other stacks already merged in that repo. The agent correctly refused to delete the line (it would
have broken that project's `terramate-drift` CI check, and reappeared on the next `terramate generate`
regardless), explained this to the operator twice, and then correctly escalated rather than repeat the
same explanation a third time — but had no way to make the gate itself stop firing, because nothing in
`policy.comments` distinguishes a tool's own stamp from prose an agent chose to write.

**The existing exemption already drew this line for a narrower case.** `TOOL_DIRECTIVE` exempts
`biome-ignore`, `eslint-disable`, `@ts-expect-error`, and similar — text a *linter* emits or reads, not
an operator or an agent. A codegen banner is the same category of thing: mechanical, deterministic,
identical on every regeneration, authored by neither party the gate exists to keep honest. Two real
conventions already cover most of what generators emit — Phabricator's `@generated` pragma (which GitHub
Linguist also recognises) and the "Code generated ... DO NOT EDIT" phrasing Go's own tooling popularised
(go-swagger, `go generate` output) — so the pattern generalizes past this one report.

## Trade-offs

**No file-position restriction, so the match works anywhere in a comment, not only a file's first
line.** Considered restricting to line 1 (where every observed convention actually places the banner)
to reduce room for an agent to game the exemption by writing "generated, do not edit" mid-file. Rejected
for now: the existing `TOOL_DIRECTIVE` exemption already has no positional restriction either, so this
follows the accepted precedent rather than inventing a stricter rule only for this case. If gaming is
ever observed, the fix is a position check, not a narrower regex.

**Requires both a `generat*` word and `do not edit` in the same short span.** A generator whose banner
uses neither phrase (a bare `// autogenerated`, with no "do not edit") is not covered. Not invented
ahead of a real report.

## Not decided here

- **Restricting the match to a file's first few lines.** Named above; worth doing if the no-position
  choice is ever actually exploited, not before.
- **A configurable per-project list of generator banners**, for a generator whose exact wording this
  pattern misses. No project has reported one yet.

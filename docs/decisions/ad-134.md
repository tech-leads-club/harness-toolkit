# AD-134 — `runCommand` moves to `process.ts`; `listTrackedFiles` never reaches for it again

- **status**: active

## Decision

1. **`runCommand` and `NO_OUTPUT_CAPTURED` move from `src/platform/git.ts` to `src/platform/process.ts`**,
   placed directly after `runProcess`, the primitive they wrap. `stop.ts`'s gate-log capture (the one real
   caller that wants `runCommand`'s display policies) and `gate.artifact.ts`'s `emptyOutput` check (the one
   real consumer of the placeholder constant) update their import paths; neither changes behavior.
2. **`runCommand`'s own tests move with it**, from `git.test.ts` into the existing `process.test.ts`, in a
   `describe("runCommand", ...)` block matching that file's style.
3. **`listTrackedFiles` stops calling `runCommand` and calls `runProcess` directly**, reading `git ls-files
   -z`'s raw stdout, split on NUL, filtered of empty entries — the exact pattern `gitLines` already uses for
   every other structured git read in this file. No `.trim()` on the whole blob, no length cap, no placeholder
   substitution for empty output.
4. **`git.ts` now contains only git-specific structured-data readers**, all sharing one no-trim,
   no-truncation, no-placeholder contract. Nothing in it shapes output for a human to read.

## Why

**Three bug reports, one root cause.** [/decisions/ad-133.md](/decisions/ad-133.md) fixed the first symptom
(truncation) by deleting `runCommand`'s inline truncation logic — a real, necessary fix, but it left
`listTrackedFiles` still reading through `runCommand`, and the SAME review that found the truncation bug found
two more defects in the exact same function within the hour: an empty repo returning `[NO_OUTPUT_CAPTURED]`
instead of `[]`, and a leading space stripped from a real filename by `.trim()`. Patching each individually —
which is what happened, twice — treats three instances of the same mistake as three unrelated ones. The
mistake was never in the details of trim/truncate/placeholder; it was that a function needing exact,
structured data was reading through a helper built for approximate, human-facing text.

**The helper was misfiled, not just misused.** `runCommand` takes an arbitrary `command: string[]` — it has no
git-specific logic at all, and its two real properties (shape output for display, source from
`platform/process.ts`'s `runProcess`) both point away from `git.ts`. Sitting next to `gitLines` in the same
file is what made it easy to reach for by mistake; moving it to where its own primitive already lives makes
that mistake structurally harder to repeat, for `listTrackedFiles` or any function written in `git.ts` after
it. This is the same principle [/decisions/ad-100.md](/decisions/ad-100.md) already states for algorithms — one
place, not duplicated or scattered — applied to a module boundary instead of a single function.

## Trade-offs

**Two files change for what is, in the end, a rename plus one function's implementation.** Accepted: `stop.ts`
and `gate.artifact.ts`'s behavior is provably identical (same functions, same policies, only the import path
moved), confirmed by the existing AD-133 end-to-end gate-log test passing unchanged.

**`listTrackedFiles`'s three prior bug-specific tests are consolidated into one suite** rather than kept as
three separately-themed additions. This is deliberate: it proves the fix is one structural change that closes
all three, not three patches that happen to coexist in the same file.

## Not decided here

- **Whether any other `platform/` file mixes structured-data and display-output concerns the same way.** Not
  evidenced; a distinct task if it surfaces.

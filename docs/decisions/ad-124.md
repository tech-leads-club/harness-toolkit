# AD-124 — A provider's wiring target is a floor surface; secret-shaped tool output is a rail

- **status**: active

## Decision

**1. `ProviderPort` gains `wiringTargets(): string[]`.** Each provider declares the absolute path(s) its own
`wiring()` writes into — `claudeSettingsPath()`, Cursor's equivalent — without taking a `RuntimePaths` argument,
because neither provider's target path is a function of the launcher path today. `run.ts` (the entrypoint layer,
which already imports the provider registry) computes `protectedPaths = providerRegistry.flatMap(p =>
p.wiringTargets())` once per hook invocation and passes it into `HandlerContext`/`FloorInput` as plain data —
`core/floor` never imports a provider, the same boundary every other floor rule already respects.

**2. A new `FloorRule`, `wiring-tamper`, denies a write to any path in that list — no config switch.**
`floor.paths.ts`'s `isPolicySurface` and `floor.policy-surface.ts`'s `checkPolicySurface` are generalized to
accept an extra list of protected paths, checked the same way `.tlc/harness/*` already is (redirect targets,
in-place edits via `sed -i`, the destructive-verb branch for `rm`/`rmdir`/`shred`/`truncate`/`dd`). `checkFile`
gains a write-branch: an `Edit`/`Write`/`MultiEdit` tool call whose `filePath` resolves inside `protectedPaths`
is denied the same way. A read of the same path — `cat`, a `Read` tool call — is unaffected.

**3. `Policy.secrets.redactOutput` (default `true`) masks secret-shaped output instead of blocking the command
that produced it.** A new module, `src/core/secret-scan/`, scans `tool.after`/`shell.after`'s `event.toolOutput`
for named regex signatures (AWS access key, GitHub token, Slack token, Stripe key, PEM private-key block, JWT)
plus a Shannon-entropy fallback for unlabelled secrets, synchronously, with no network call and no active
credential verification. A match is replaced with a deterministic placeholder
(`[REDACTED:<kind>:<8-char-hash>]`) — the same secret value always yields the same placeholder within a
session, persisted in `projectStateDir(root)/secret-redaction.json` keyed by session, mirroring
`shell-policy.stall.ts`'s existing per-session store shape. The raw matched text is never written to disk, only
its hash.

**4. `Decision` gains `rewriteOutput`, degraded per-event by a corrected capability.**
`ProviderCapabilities.toolOutputRewrite: boolean` — declared `true` for both providers since the original
multi-provider design — is replaced with `toolOutputRewriteOn: HarnessEventKind[]`, the same per-event shape
`askSupportedOn` already uses. Claude Code declares every event it fires `PostToolUse`/`PostToolUseFailure` for
(`tool.after`, `tool.failure`); Cursor declares `["mcp.after"]` only. `provider.degrade.ts` passes `rewriteOutput`
through unchanged when the firing event is in that list; otherwise it degrades to a `context` warning telling the
model a secret was masked and must not be repeated — a warning, not a silent drop, because the command already
ran and there is nothing left to block. Claude renders a supported `rewriteOutput` as the documented top-level
`updatedToolOutput` field; Cursor renders it as `updated_mcp_tool_output`, only reachable on `mcp.after` because
`degrade()` has already converted every other event to `context` before render runs.

## Why

**The policy-surface floor rule protected the harness's own files and nothing that depends on them.**
`policy-surface-write` ([/decisions/ad-022.md](/decisions/ad-022.md)) already denies a write to `.tlc/harness/*` with no config switch. It never
covered the file each provider actually depends on to receive events at all — `rm ~/.claude/settings.json`,
`sed -i '/tlc-exec/d' .cursor/hooks.json`, or a direct `Edit` tool call against either path, silenced every hook
that provider has, with no denial and no trace, without touching a single path the floor recognized as
protected.

**Discovery has to come from the registry, never a hardcoded path list.** A literal `~/.claude/settings.json` /
`.cursor/hooks.json` pair in the floor would silently stop protecting anything the moment a third provider
registers — the opposite of `docs/providers/index.md`'s stated reason for the whole adapter design ("a new
provider is a new directory... never a change to `core/`"). `wiringTargets()` on the port interface, enumerated
by the caller that already knows the registry, keeps that guarantee: a new adapter's target is covered without a
floor change, and `provider.contract.test.ts`'s existing fixture-provider test already forces every future
provider to implement it.

**Content-based secret detection does not belong at floor strictness.** A known secret path (`.env`, `~/.ssh`,
a PEM file) is a binary, zero-false-positive question — exactly what the floor's "no config switch" posture is
for. A regex-plus-entropy scan over arbitrary output has a real false-positive rate (a hash, a UUID, a
base64-encoded non-secret blob) and a per-output CPU cost; that is a discretionary trade-off, which is what
`Policy`'s rails — with their own switches — already exist to hold. `secrets.redactOutput` defaults `true`
because it is the one other rail already shipped on by default (`shell.catastrophicAsk`) sets the precedent for:
the cost is a synchronous regex pass, and the risk of a leaked credential outweighs an occasional masked false
positive.

**The pre-existing `toolOutputRewrite` capability was measured, not assumed, and found wrong.** The original
multi-provider design declared it `true` for both Cursor and Claude Code with no per-event distinction. Fetching
each host's own current hook documentation directly (not a secondary summary) found Claude Code ships a
top-level `updatedToolOutput` string, valid on `PostToolUse`/`PostToolUseFailure`, that "replaces the tool's
output before Claude sees it" — the official example is redacting a secret from a file read. Cursor's
`afterShellExecution` and `afterFileEdit` are documented as observation-only (empty response schema); only
`afterMCPExecution` carries `updated_mcp_tool_output`, scoped to MCP results. A boolean that claimed Cursor could
rewrite `shell.after` output was never true — the same per-event correction `askSupportedOn` already went
through for asking ([/decisions/ad-009.md](/decisions/ad-009.md)) and `toolOutputAtAfter` went through for output visibility, applied to the one
capability flag that had not yet had it.

**A hook-based redaction cannot be a stronger guarantee than the pipeline it sits in.** `updatedToolOutput` only
changes what the *model* sees on its next read of that tool result — Claude's own docs state the transcript
keeps the original, unredacted value for audit — and any host mechanism that delivers content to the model
outside the tool-output path entirely (an expansion, a feature this harness's providers do not currently model)
is not something a `PostToolUse`/`afterShellExecution` hook can see at all. This is stated as a limitation, not
implied as a guarantee the mechanism cannot back.

## Trade-offs

**`wiring-tamper` only protects a *registered* provider's wiring target.** A host this harness has no adapter
for yet has no `wiringTargets()` to protect — not a regression (nothing protected it before either), but not a
general "protect every possible agent config file" guarantee.

**The entropy fallback trades false positives against false negatives at a fixed, documented threshold.**
`ENTROPY_THRESHOLD` is a single constant; a string just under it that is genuinely a secret is missed, and a
sufficiently random non-secret string just over it is masked. The threshold is a named, tunable constant rather
than a per-operator setting — see Not decided here.

**Redaction on Cursor outside `mcp.after` is a warning, not a mask.** The raw secret still reaches the model's
context there; the harness can only tell it what happened after the fact. This is the ceiling `toolOutputRewriteOn`
being empty for those events documents honestly, not a bug in the degrade path.

## Not decided here

- **A per-operator-tunable entropy threshold or signature list.** `ENTROPY_THRESHOLD` and `SIGNATURES` are code
  constants today; making either configurable is a natural rail extension, not required by the reported gap.
- **Active credential verification** (calling out to confirm a matched key is still live). Needs network access
  from inside a synchronous hook; against both the floor's posture and this rail's own latency budget.
- **Retroactive transcript scrubbing** of a secret that already reached a raw log or a host's own transcript
  store before this rail existed. Out of scope — `secrets.redactOutput` only affects output as it is produced,
  going forward.

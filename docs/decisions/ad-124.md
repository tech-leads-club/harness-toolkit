# AD-124 — opencode's two plugin API generations get two capability tables, and the rows they disagree on are not the ones the design predicted

- **status**: active

## Decision

opencode registers as two adapters, one per plugin API generation. Each declares all fifteen
`ProviderCapabilities` fields (`src/contracts/capabilities.ts`) from its own reference — the legacy plugin
reference (<https://opencode.ai/docs/plugins>) and the namespaced one
(<https://opencode.ai/v2/docs/build/plugins>), both read 2026-09-04 — or from behaviour measured against a
running opencode and recorded in the feature's transcription. No value is set by analogy to another host, and no
value is carried from one generation to the other.

| Flag | legacy | namespaced | Provenance |
| --- | --- | --- | --- |
| `enforcesHooks` | `true` | `true` | Legacy: a `throw` from `tool.execute.before` blocks execution. Namespaced: `permission.evaluate` takes `effect: "deny"`, and the reference states an explicit deny is final. |
| `askSupportedOn` | `[]` | `["shell.before", "mcp.before", "read.before", "tool.before"]` | Legacy has `permission.asked` and `permission.replied` — notifications of a decision already taken — and no hook that returns one. Namespaced has `ctx.permission.hook("evaluate")`, whose `effect` accepts `"allow" \| "ask" \| "deny"`; the reference scopes it to no tool class, so it is declared across every before-kind this adapter raises. |
| `sessionEnv` | `false` | `false` | Unmeasured. Neither reference documents an environment given to the plugin or to the process it launches. Legacy's `shell.env` and namespaced's `env` on `shell.create.before` are the opposite direction — the plugin *setting* a shell's environment. |
| `nativeLoopCounter` | `false` | `false` | No documented payload carries a turn counter. `effectiveLoopCount` (`src/core/turn/turn.loop-counter.ts:50`) reads `event.loopCount` as a number, so this flag claims a count, not a boolean. |
| `dedicatedShellEvent` | `false` | `true` | Legacy intercepts shell only as `tool.execute.before` with `tool: "bash"`; `shell.env` sets environment and intercepts nothing. Namespaced documents `ctx.shell.hook("create.before")` with `command`, `cwd`, `timeout`, `shell`, and `env`. |
| `toolInputRewrite` | `true` | `false` | Legacy documents `output.args.command` and `output.args.filePath` as mutable at `tool.execute.before`. Namespaced shows the same hook as `(event) => …` over `event.tool` and `event.input` and documents no mutation of it — unmeasured, so the safe value. |
| `toolOutputRewrite` | `true` | `true` | Namespaced documents the mutation outright: `if (event.status === "completed") event.result = { ...event.result, … }`. Legacy documents no output object on `tool.execute.after` at all; `true` there rests on the transcription's measured bridge behaviour, which is admissible provenance and is the weakest value in this table. |
| `contextAtToolBefore` | `true` | `false` | Legacy: the transcription measured the bridge appending a context decision to `output.context`. That measurement was taken against the legacy bridge, so it does not transfer — the namespaced value is unmeasured and takes the safe value. |
| `contextAtToolAfter` | `false` | `true` | Legacy's `after` output shape is undocumented and unmeasured. Namespaced's mutable `event.result` is the carrier, and is documented. |
| `contextAtStop` | `false` | `false` | Neither reference documents a stop hook that accepts context. Legacy's `session.idle` and namespaced's session hooks are notifications or dispatch-time shaping, not a stop verdict channel. |
| `sessionStartContextReliable` | `false` | `false` | Measured in the transcription: opencode cannot be trusted to deliver context at session start, which is why this host carries lessons through a durable view instead. |
| `toolOutputAtAfter` | `false` | `true` | Namespaced documents `event.status` of `"completed" \| "error"` and `event.result` on `execute.after`. Legacy documents neither — unmeasured, so `false`. |
| `usageInPayload` | `false` | `false` | No token or cost field appears in any documented payload on either generation. |
| `effortSignal` | `false` | `false` | No reasoning-effort field in any documented payload. Namespaced's `session.model.request` shapes an outgoing call; it is not an effort signal on a dispatcher payload. |
| `thoughtEvent` | `false` | `false` | Neither documented event list contains a thought or reasoning event. |

## Why

**The split was argued from `askSupportedOn` and `dedicatedShellEvent`, and both references confirm those two
rows.** The namespaced API has a permission hook that can return `"ask"` and a shell interception separate from
tool execution; the legacy API has neither. A single descriptor would have to claim an ask channel the legacy API
cannot honour, or discard the one the namespaced API offers. The first is the failure this table exists to
prevent.

**Reading both references inverted a third row the design had not looked at.** Tool *input* rewriting is
documented on legacy (`output.args`) and undocumented on namespaced; tool *output* rewriting is documented on
namespaced (a mutable `event.result`) and undocumented on legacy. The newer API is not uniformly the more capable
one, and an adapter that assumed it was would have declared `toolInputRewrite: true` on the generation whose
reference does not show it.

**`toolOutputRewrite: true` on legacy is the one value here with no documentary support.** The legacy reference
shows an example for `tool.execute.before` only; a third-party reference states `after` takes no `output`
parameter at all. It stays `true` because the transcription measured it and measured behaviour is cited
provenance — but it is named here rather than presented as settled, so that the first opencode session anyone runs
knows which value to check.

**A flag set by analogy is worse than a missing feature, and that rule binds across generations too.** The two
columns above disagree on five rows. Any value copied sideways between them — or in from Cursor, Claude, or
Codex — would produce a rail that silently does nothing on one of the two adapters. Where a generation's
reference is silent and the transcription measured the *other* generation, the silent one takes the safe value.

## Correction — the plugin locations were wrong, and one bridge serves both generations

This record was written from the two web references and never checked against a running opencode. A real install
(opencode 1.18.29, `~/.opencode/bin/opencode`, read 2026-09-05) settles four things it got wrong. The capability
table above is untouched: none of it reads a path.

**The discovery glob is `{plugin,plugins}/*.{ts,js}`, and it is flat.** The string appears twice in the binary,
once in each of its two plugin loaders. `*`, not `**` — one level only. Both spellings of the directory are
accepted, and the glob is applied to every directory in opencode's config-directory list, the global one included.

**The namespaced target was never discoverable.** `opencodeNamespacedWiring` wrote
`~/.config/opencode/plugins/tlc-harness/index.ts`. That is one level too deep for the glob, so opencode never
loaded it — on any machine, ever. The `hazard:` comment on that function predicted exactly this and the writer
shipped anyway.

**Flattening it into a sibling would have been worse.** Two auto-discovered files in one directory are both
loaded, so every hook would have fired twice.

**So the two kinds now emit one file, `~/.config/opencode/plugins/tlc-harness.js`, which adapts at runtime.** It
carries both register paths and selects between them from the plugin input the host hands it: a plugin input with
`tool.hook`, `shell.hook` and `permission.hook` is the namespaced generation, anything else is legacy. Each path
stamps its own `pluginApi` into the envelope and launches with its own `--provider` hint, so the detectors, the
two capability descriptors and the inbound fan-out are unchanged.

Two facts from the binary decide the module's shape, and neither was guessable:

1. **The module must export a function and nothing else.** opencode's own embedded documentation states it: "A
   plugin module exports `default` (or any named export) of type `Plugin = (input, options?) => Promise<Hooks>`.
   The export is a function, not a plain object literal." The legacy host confirms it — it iterates
   `Object.values(mod)` and throws `TypeError("Plugin export is not a function")` on the first export that is
   neither a function nor an object with a function `server`. It dedupes by identity, so a default export is
   registered exactly once.
2. **`import { Plugin } from "@opencode-ai/plugin"` would have broken the module outright.** The installed package
   (1.17.9, in `~/.config/opencode/node_modules/`) has `dist/index.js` of `export * from "./tool.js"`, whose only
   runtime export is `tool`. `Plugin` is a type. The import is a link-time error, and on an install without the
   package it fails harder. The emitted bridge imports `node:child_process` and nothing else.

**Recorded, not acted on: the namespaced API is absent from this binary.** `Plugin.define`, `shell.create.before`
and `permission.evaluate` return zero matches in opencode 1.18.29, and its documented hook surface is the flat
legacy one (`tool.execute.before`, `tool.execute.after`, `permission.ask`, `shell.env`, and the `experimental.*`
set). The namespaced path in the bridge is therefore dead on this version — the feature test simply never
selects it. That is the safe direction and it costs nothing, but the two namespaced-only rows in the table above
(`askSupportedOn`, `dedicatedShellEvent`) rest on a reference this binary does not corroborate. Left standing
here; a version that ships the API settles it.

## Trade-offs

**`askSupportedOn` on the namespaced adapter claims four before-kinds from a hook the reference does not scope.**
The documentation says only that permission hooks "run for allow and ask decisions"; it never enumerates which
tools reach a permission decision. If opencode does not route, say, a `read` through permission evaluation, an
`ask` rule on `read.before` prompts nobody and the operator sees no error — the exact asymmetry this record
otherwise avoids. The narrower alternative was to declare `["shell.before"]` alone, which the shell hook makes
safe, but that value is no better evidenced: the reference does not scope the hook to shell either, so a narrow
list would be a guess wearing conservatism's clothes. The four kinds are declared, the gap is named, and one
session with an `ask` rule on a read settles it.

**Two rows are conservative on the beta API purely because the measurement predates it.**
`contextAtToolBefore` and `toolInputRewrite` are `false` on namespaced and `true` on legacy, which reads
backwards. It is the correct reading of the evidence — the transcription's bridge was the legacy one — and it
costs the namespaced adapter two rails until someone runs it. The alternative is transferring a measurement
across an API boundary the whole record exists to keep separate.

**Declaring `nativeLoopCounter: false` on both spends a file write per turn.** The harness counts turns itself
(`src/core/turn/turn.loop-counter.ts`). Neither reference documents a counter, and a boolean "a hook already
forced this turn to continue" would not be one — see the correction in
[/decisions/ad-123.md](/decisions/ad-123.md).

## Not decided here

- **Which carrier the namespaced adapter uses for durable lessons.** `sessionStartContextReliable: false` on both
  generations means lessons need a durable view, and the namespaced configuration reference documents no
  `instructions` array. The namespaced `session.context` hook — which documents `event.system.push({ text })`
  immediately before model dispatch, affecting only the outgoing call and not persisted history — is a candidate
  a plugin could use instead of a config array. T8 settles it; this record only pins that the flag is `false`.
- **Whether opencode honours a value the bridge returns.** A reference proves what a hook accepts, never what the
  host does with it (`src/contracts/capabilities.ts:14`). Every `true` above that is not transcription-measured
  is in that class.
- **The field spelling the bridge stamps.** The namespaced reference names `event.input` where the fixtures under
  `src/providers/opencode/__test__/fixtures/namespaced/` carry `args`. The envelope is harness-defined, so the
  bridge maps one to the other; T7 owns which spelling reaches the parser.
- **The other two hosts' flags.** Codex is [/decisions/ad-123.md](/decisions/ad-123.md), VS Code is
  [/decisions/ad-125.md](/decisions/ad-125.md). Nothing here transfers to either.

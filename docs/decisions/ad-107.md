# AD-107 — A subagent's own budget running out is not evidence about the tree, and a stuck handoff now has an exit

- **status**: active

## Decision

1. **`subagent-stop.ts` no longer counts `blockers` as unfinished work when `last_failure_category`
   is `"budget"`.** `previous_gaps`, `pending`, and `in_progress` are unchanged — they still block.
2. **A new `tlc harness reset` clears `blockers`, `previous_gaps`, `pending`, `in_progress`,
   `last_failure_category`, and `next_action`** for every provider slice that has one, and deletes the
   project's grind-loop counters. Nothing else in the handoff is touched.
3. **`reset` joins `pause`, `resume`, `grind`, `mode`, `init`, `gate`, `policy` as a mutating
   subcommand** the `policy-surface-write` floor rule denies from inside a session — it is an operator
   action, run from a terminal, same as the others.

## Why

**A budget signal is not evidence about the tree.** When the main session's grind cap fires, `stop.ts`
writes `blockers: "Grind cap hit (N stop loops)…"` and `last_failure_category: "budget"` into
`handoff.json` — a single file per project, not per session. `subagent-stop.ts` read `blockers` alone,
with no regard for why it was set, so every later subagent that tried to stop — a judge, a juror, a
teammate that had touched nothing — was told `BLOCKED: unfinished work remains`, repeatedly, until the
main session happened to complete one fully clean stop. Observed twice: 2026-08-19 with a jury panel,
2026-08-26 with a `judge-*` teammate panel, both stalled by a grind cap from an unrelated session.

**Session-scoping was the first fix considered, and it does not work.** Claude Code subagents spawned
by the Task tool report the parent session's `session_id` on every hook, including `SubagentStop`
(anthropics/claude-code#7881) — this handler cannot tell its own subagent apart from a sibling or the
main loop by session identity, so keying the signal to `sessionKey` would have left the reported case
unfixed: the judges and the main session shared the one session_id the whole time.

**The category is the correct cut, and [/decisions/ad-073.md](/decisions/ad-073.md) already drew it.**
That record established that a gate verdict is valid evidence across sessions because the sessions share
a tree — a neighbour's lint/test pass or fail is real information about this turn's code. A `"budget"`
category means the session's turn/loop budget ran out; it asserts nothing about whether the tree is
broken. Reading the two the same way blocked subagents on a signal that could never be about their own
work.

**An operator had no way to clear it directly.** `tlc harness pause` writes a flag `subagent-stop.ts`
never read, so it did not help. No `reset` subcommand existed, though an operator working through the
2026-08-26 incident expected one — the closest current practice for a stuck coordination signal
(Terraform's `force-unlock`, a stale-lock override) is an explicit, human-invoked command that clears the
signal without waiting for the system to heal itself. `reset` is that command, and — same as every other
mutating subcommand — it stays out of an agent's own hands.

## Trade-offs

**`previous_gaps`, `pending`, and `in_progress` are still read unscoped.** They can carry real
cross-subagent evidence tied to the same tree, so they were left blocking on purpose — but that also
means a stale non-budget signal from a different branch or a commit nine days old (recorded once,
2026-08-21) can still wrongly block a subagent. This record narrows the one demonstrated, recurring case;
it does not close the wider one.

**`reset` clears every provider's stuck signal, not just the one that is actually stuck.** An operator
who runs it already knows something is stuck and wants it gone — a `--provider` filter would add a
decision the command does not need yet.

**No TTL-based auto-expiry.** A grind-cap blocker still sits until either a clean stop clears it or an
operator runs `reset`; nothing yet measures a duration past which it should expire on its own.

## Not decided here

- **Scoping `previous_gaps` to the commit or branch it was recorded against**, so a stale signal from
  elsewhere stops reading as current. The trade-off above names it; it is a separate, larger change to
  the handoff schema.
- **Automatic expiry of a stuck signal.** Worth doing once a real duration is measured, not invented
  ahead of one.
- **Whether `reset` should accept a narrower scope than "every provider".** No case has needed it yet.

> alongside `previous_gaps`, turned out to have no writer anywhere in the codebase — both conditions
> had read `false` since [/decisions/ad-059.md](/decisions/ad-059.md) introduced the formula on
> 2026-08-10. Removed, not scoped; only `previous_gaps` carries a real, unscoped signal

# AD-121 — `command(<pattern>)` matches a bare word against a path ending in it, not only an exact word

- **status**: active

## Decision

1. **`matchesPhrase` (`rules.trigger.ts`) gains a basename fallback per token, via a new `tokenMatches`
   helper**: a candidate word satisfies a pattern token if it equals the token exactly, **or** the token
   contains no `/` of its own and the word ends with `/<token>`. Order and phrase-length semantics are
   unchanged — this only widens what counts as "this one word matched."
2. **One function, both call sites.** `matchesPhrase` is shared by `triggerMatches`'s `command(<pattern>)`
   trigger and `rules.proof.ts`'s `valueMatches` for the `command` proof kind. Both get the fix from the one
   change; a second, possibly-diverging implementation was not created for either.
3. **A token the operator already wrote with a `/` is not given the fallback.** `command(scripts/build.sh)`
   still requires an exact word `scripts/build.sh` — the operator named a location, and a location is exact
   or it is the wrong one. Only a *bare* token (no `/`) is read as naming an act rather than a place.
4. **The fallback is a basename match, not a suffix scan.** The `/` immediately before the token is part of
   the check, so `command(review.py)` still never matches a real file named `not_review.py` — the words
   `not_review.py` and `/review.py` are not the same suffix.

## Why

**Confirmed against real production data, not guessed.** A downstream project's rule required
`command(<script>) since HEAD`, where `<script>` is a script the operator's own review workflow runs. The
observation store recorded a genuine invocation of that exact script, at the exact commit the rule's `since
HEAD` check resolved (already ruled out by [/decisions/ad-120.md](/decisions/ad-120.md)'s own diagnostic,
which showed the checked directory and sha both correct) — and the rule still denied, every time, for as long
as the rule existed. The recorded command ran the script through its full installed path, as every invocation
of a packaged script does. `matchesPhrase`'s exact-equality check compared the bare filename against that
whole path string and never found a match, because a word and one of its own path segments are never `===`.

**This is not specific to any one script or skill.** The bug is in what `command(<pattern>)` means for *any*
bare-filename pattern — a rule of that shape can never be satisfied by a script invoked any way other than
literally typing its bare name with no directory at all, which is not how a real script is normally run. The
fix is a property of the matcher, not a special case for the script that surfaced it.

**Why the same function serves the trigger too.** `on: command(<pattern>)` has the identical shape problem —
an operator naming `command(build.sh)` to trigger on a build script would face the same silent, permanent
non-match if the build tool is invoked via a path. Fixing only the proof side would have left a second,
harder-to-notice instance of the exact bug this AD exists to close.

## Trade-offs

**A pattern token that happens to equal a common path suffix now matches more broadly than before.** A rule
requiring `command(build.sh)` now matches `./build.sh`, `/opt/ci/build.sh`, and any other path ending in that
filename — previously only the bare word. Accepted: the whole point of a `command(<pattern>)` proof is that a
script is *the same act* regardless of where it lives on disk, and the alternative (exact-word-only) already
proved unsatisfiable in a real, reported case.

**A pattern that already contains a `/` gets no equivalent fallback** (no suffix match for
`command(scripts/build.sh)` against `/opt/ci/scripts/build.sh`). Not reported, not evidenced — the operator
who writes a path in the pattern is the one case where "somewhere else too" would be a guess about how much
of the path they meant to pin down.

## Not decided here

- **Extending the fallback to a pattern that contains its own path segments.** See Trade-offs — no case has
  needed it.

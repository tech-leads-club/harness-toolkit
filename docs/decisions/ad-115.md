# AD-115 — A comment violation refuses commit, push and gh pr create, not only the stop

- **status**: active

## Decision

1. **`tool-before.ts` denies `git commit`, `git push`, and `gh pr create`** (the `commit`/`push`/
   `pr-open` shapes `rules.trigger.ts`'s `SHELL_SHAPES` already recognizes) **when the current
   turn carries an unresolved, undeclared comment.** The condition is identical to the one
   `stop.ts` already gates its own hard block on: `policy.comments.enabled &&
   policy.comments.onViolation === "followup"`.
2. **The scan is the same one `stop.ts` runs**: `turn_base_sha` from the handoff (or `HEAD` when
   absent), changed files filtered by `codePaths` and by the comment-syntax catalog,
   `scanAddedComments` in `policy.comments.mode`. No new scope, no second answer to what counts as
   "this turn."
3. **This runs after the operator rules verdict, before the shell fallback** — same tier as a
   rail, per AD-077. A command an operator rule already denies is never redundantly re-checked.
4. **The edit-time advisory ([/decisions/ad-111.md](/decisions/ad-111.md)) and the stop-time block
   are unchanged.** This adds a third contact point; it replaces neither.

## Why

**Reported live.** An agent added an undeclared comment, the edit-time `HEADS UP` fired and was
not acted on, and the agent proceeded to commit, push, open a PR, and the PR's CI began deploying
— the stop-time `BLOCKED` only surfaced after all four of those had already run. A gate that can
report a violation only after the action it exists to prevent has already shipped is not
enforcement; nothing between the advisory and the stop had any teeth.

**The vocabulary already existed.** `rules.trigger.ts`'s `SHELL_SHAPES` already recognizes exactly
`commit`, `push`, and `pr-open` as one closed family — the operator rules engine
([/decisions/ad-100.md](/decisions/ad-100.md)) has used it for months to gate `pr-open` on
`subagent(the-judge)`. This reuses the same shape matcher for a
different, built-in condition (a comment violation) rather than inventing a second detector for
the same three commands.

**Not a rule the operator authors, so it does not live in `.tlc/harness/rules/`.** It is a
built-in capability (`policy.comments`), the same kind of thing the floor and the untrusted-content
rail are — but unlike the floor it reads policy (`comments.enabled`/`onViolation`), so it is not
unconditional either. It sits where `rulesDecision` already sits: after the floor and the
integrity check, at the rail tier.

## Trade-offs

**A comment written via `Bash`** (a heredoc, `sed`, `python3 -c`) is still invisible to the
edit-time advisory (AD-111's accepted limitation), but this check still catches it before ship —
it re-diffs the whole turn against `turn_base_sha`, the same scope `stop.ts` uses, not just the
last edit. Strictly better than AD-111's per-file scope for this one purpose, not equal to it.

**Cost.** A `git status`-adjacent diff (`listChangedRepoFiles`) plus a regex scan runs on every
`commit`/`push`/`pr-open` attempt while `comments.enabled` — the same cost `stop.ts` already pays
once per turn, now potentially paid more than once if an agent attempts to ship more than once in
a turn. Bounded by the same file-count reality `stop.ts` already tolerates; no new cost shape.

## Not decided here

- **`turn_base_sha`'s own worktree-scoping** (already flagged as "not decided here" in AD-114).
  This reuses `stop.ts`'s exact mechanism rather than inventing a second, possibly divergent
  answer to the same open question.
- **Lint/test/docs/duplication getting the same treatment.** Different cost shape, not evidenced,
  already declined for edit-time in AD-111 on the same grounds.

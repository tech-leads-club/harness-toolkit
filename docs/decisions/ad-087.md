# AD-087 — The tag goes first because npm cannot be undone, and the release stays a draft until the package is real

- **status**: active

## Decision

1. **The tag is still created before the publish.** Not inverted.
2. **The GitHub release is created as a draft** (`draft: true`).
3. **A separate `announce` job promotes it**, after `publish` succeeds.
4. **`announce` holds `contents: write` and `publish` does not.**

## Why

**The obvious fix is the wrong one, and the reason is asymmetry.** A published npm version cannot be removed after
72 hours; a git tag can be deleted and recreated at will. So the order has to put the reversible step first: if the
tag fails, nothing was lost, and if the publish fails, the tag is repaired by publishing. Inverting them — publish
first, tag after — would mean a failed tag leaves an immutable package pointing at a commit nothing references, and
that state cannot be repaired at all, only documented.

**The real defect was that the inconsistent state was silent.** `v0.2.2` was tagged, released on GitHub, and never
published: the `publish` job sat in `waiting` on the environment's required reviewers until it was cancelled. The
result is a release announced to anyone reading the repository, for a version `npm install` cannot resolve. Nothing
in the pipeline noticed, because from release-please's point of view the release succeeded.

**A draft is the state that matches reality.** Between the tag and the publish, the version exists in git and not
on the registry, and a draft release says exactly that: the tag is there, the announcement is not. A reader sees
nothing; a maintainer sees a draft, which is a to-do rather than a claim. Promotion is one API call and it happens
only after `npm publish` returns.

**The promotion is a separate job so the npm credential stays least-privileged.** `publish` holds
`id-token: write` for trusted publishing and `contents: read`. Editing a release needs `contents: write`, and
granting that to the job that also holds the publishing identity would widen the one step where a mistake is
irreversible.

## Trade-offs

**A cancelled publish now leaves a draft nobody cleans up.** That is strictly better than a published release with
no package, and it is still litter. Whether a stale draft should be detected and reported is not decided here.

**The release notes are invisible while the draft is pending.** Someone watching the repository for a release sees
nothing until the publish completes, where before they saw it immediately — including when the publish then failed.
Later and true beats sooner and wrong.

**`announce` runs on `github.token`, not the App token.** Editing a release is not blocked by the org's read-only
default for `GITHUB_TOKEN`, unlike opening a pull request, so the App is not needed here — measured by the fact
that `contents: write` on a job is what release-please's own release creation already relies on.

**This does not repair `v0.2.2`.** The tag and release exist and the package does not, and the next release covers
the same content. Publishing `0.2.2` by hand purely to close the gap would put an unverified artefact on the
registry to make a table look tidy.

## Not decided here

- **Whether a stale draft release should fail something.** It is the visible form of a publish that did not happen,
  and nothing sweeps it.
- **Whether the `publish` environment should keep required reviewers.** With them, a release is attended and can
  time out; without them, unattended. That is the operator's call and the mechanism works either way
  ([/decisions/ad-083.md](/decisions/ad-083.md)).
- **Repairing `v0.2.2`.** It stays as a released tag with no package.

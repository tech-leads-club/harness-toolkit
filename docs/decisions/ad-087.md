# AD-087 — How the release works, and the six wrong shapes it took first

- **status**: active

## Decision

**The pipeline, in the order it runs.** One workflow owns `main`; `ci.yml` owns pull requests.

1. **`gate`** — `release.yml` calls `ci.yml`, so the three-platform matrix is defined once and runs once per commit.
2. **`release-please`** — creates the release and tag for the PR merged last time, and opens the PR for next time.
   A guard runs first: **at most one released version may be waiting for its tag.**
3. **`changelog`** — renders `CHANGELOG.md` from `docs/decisions/` at the pending version, into the PR.
4. **`publish`** — `npm publish` via trusted publishing, behind the `publish` environment's required reviewers.
5. **`merge`** — `gh pr merge --rebase --admin`, and it **needs `publish`**.

**And the settings that make it work:** `draft: false`; the App is a bypass actor on the branch ruleset; the App
token is scoped with `owner` and `repositories` only; `exclude-paths` covers everything the tarball does not ship;
every third-party action is pinned to a SHA; `persist-credentials: false` wherever nothing pushes; a concurrency
group per workflow and a `timeout-minutes` per job.

## Why each of those, and the six shapes that were wrong first

**`--admin`, not `--auto`.** The ruleset requires one approving review and an App cannot approve its own pull
request, so `--auto` armed the merge and waited for a human for ever — measured with the App on the bypass list, all
three CI jobs green, still `REVIEW_REQUIRED`. The conclusion drawn was that a PR-shaped release cannot be
unattended, and the next step taken was to start replacing release-please with a version calculator written here.
`BHubAI/platform` releases through the same action and the same ruleset with one line: `--admin`. **Wrong shape 1:
a hand-rolled release.** About two hundred lines, sixteen tests, reproducing every version already released —
correct code and the wrong thing to own.

**`draft: false`, and this is the expensive one. Wrong shape 2.** `draft: true` was added to close the window where
a tag exists and the package does not. A draft release **does not create its tag**, and the tag is how
release-please knows where the last version ended. Without it, each round reprocessed history, found old `feat:`
commits, computed a minor bump and wrote it into the manifest — moving the base for the next round. Six versions,
`0.2.3` through `0.7.0`, in nine minutes. Nothing reached the registry, and that was the publish environment's
required reviewers rather than anything designed.

**A guard that counts, not one that looks up. Wrong shapes 3 and 4.** The first guard demanded that the manifest's
version be tagged and blocked the next legitimate release: merging the release PR bumps the manifest, and the *next*
run creates the tag. The second exempted the case where `HEAD` is the release commit — but after the merge `HEAD` is
the `docs(changelog)` commit, and during the loop the release commits existed too, so it would have permitted
exactly the thing being guarded. What separates them is repetition: one untagged release is the window, six was the
loop. Proven in a scratch repository before shipping the third attempt.

**`push` on `main`, not `workflow_run`. Wrong shape 5.** Chaining the release to CI completing removed a duplicate
matrix and introduced a high-severity `zizmor` finding: `dangerous-triggers`, because a `workflow_run` job runs with
the base repository's secrets and token regardless of what triggered it. Splitting by ownership does both jobs —
`ci.yml` on pull requests, called by `release.yml` on `main` — and the gate becomes a `needs:` rather than a
condition on somebody else's conclusion.

**`merge` needs `publish`. Wrong shape 6.** One release-please invocation serves two releases: it creates the
release for the PR merged last time and opens the PR for next time. With no dependency between them, the merge
pushed to `main` and started the next cycle while `publish` was still waiting for its approval — two releases in
flight, and a run list nobody could read.

**Repository scope on the token, not verb scope.** `permission-contents: write` and
`permission-pull-requests: write` were copied from a repository that uses them successfully; release creation then
failed with `Resource not accessible by integration`. `owner` plus `repositories` bounds a leaked token to this
repository, which is the difference that matters.

**`exclude-paths`, because only what ships should earn a version.** `0.2.1`, `0.2.2` and `0.2.3` were CI, gate and
packaging work — immutable npm versions that changed nothing for anyone installing the package. The excluded list is
by construction what the tarball does not contain, and `check-manifest` fails if an excluded path starts shipping.

**Pinned actions, because the rail was pointed outward only.** Twelve `uses:` references, three pinned and nine on
mutable tags, while this repository ships a rail that asks before an unpinned dependency enters somebody else's
manifest ([/decisions/ad-075.md](/decisions/ad-075.md)). The tags also hid how far behind we were: `checkout` v4
against v7.0.1, `setup-node` v4 against v7.0.0. `zizmor` enforces the pin as `unpinned-uses: hash-pin` and nine
other audits besides, which is why the hand-written checker for it was deleted rather than kept beside it.

## Trade-offs

**`--admin` bypasses the review for real.** Nothing human looks at a release before it lands on `main`. What
remains is mechanical: every release job needs `gate`, so `--admin` bypasses the *review* and never the matrix. The
lever if that stops being acceptable is the `publish` environment, not this flag.

**The window `draft: true` tried to close is open.** Between the tag and the publish a version exists in git and
not on npm, and `v0.2.2` is still in that state. The order is right — npm is irreversible after 72 hours and git is
not, so the recoverable step goes first — and the draft was the wrong instrument. Nothing detects the gap.

**A failed publish blocks the next release**, because `merge` needs it. Deliberate: the version that failed to
publish is the one to fix first.

**The bot's own pull request is no longer verified before it lands.** Its contents are a bump, a lockfile and a
changelog, and the matrix runs on `main` seconds later. A broken bump means a red `main` for one commit, and cannot
mean a bad publish.

**The guard parses commit subjects and reads thirty commits.** If release-please changes its wording the guard
counts zero and stops guarding — the same failure shape it exists to catch — and nothing tests that.

**Six wrong shapes in one afternoon, each shipped before it was proven.** Four were corrected the same day by the
next one. The pattern was writing the decision from a story about the failure instead of from its signature, and
the signature was in the run list the whole time.

## Not decided here

- **Detecting a tag with no published package.** `v0.2.2` is exactly that and nothing reports it.
- **Whether the `publish` environment keeps required reviewers.** It is the only human step left, and it is what
  contained the loop.
- **Whether `gate` should be a required status check on `main`**, which is what would stop a human merge from
  skipping it.
- **Which permission release creation actually needs.** Bisecting it costs a release cycle per attempt.
- **Whether `zizmor` should run in the local gate.** It would put a Rust binary in a toolchain that needs only Node
  or Bun.

# AD-108 — Two fields in the unfinished-work formula had no writer, and the carried-gap merge dropped this turn's own result

- **status**: active

## Decision

1. **`HandoffProviderSlice.pending` and `.in_progress` are removed** from the type, from
   `subagent-stop.ts`'s and `stop.ts`'s `unfinishedWork` formulas, from `clearStuckSignals`'s
   `CLEARED_SLICE`, and from the `tlc harness handoff` report screen.
2. **`mergeGaps` iterates `[...current, ...prior]`, not `[...prior, ...current]`.** The de-dup key and
   the 12-item cap are unchanged.
3. **`previous_gaps`'s blocking behaviour in `subagent-stop.ts` is unchanged** — this record does not
   revisit the trade-off [/decisions/ad-107.md](/decisions/ad-107.md) already named.

## Why

**A parallel audit of the four subsystems AD-107 touched (lessons, config loading, follow-up messages,
progressive context) was run to ask the question AD-107 itself raised: does the same leak exist
anywhere else.** It reported that `subagent-stop.ts` still reads `previous_gaps`, `pending`, and
`in_progress` unconditionally — correct, and already the subject of AD-107's "Trade-offs" and "Not
decided here" sections. Checking the claim against the code turned up something AD-107 had not: `grep
-rn` for a writer of `handoff.pending` or `handoff.in_progress` across `src/` found none. Neither field
has been set by any code path since [/decisions/ad-059.md](/decisions/ad-059.md) introduced the
`blockers || previous_gaps || pending || in_progress` formula on 2026-08-10. Both conditions have read
as `Boolean(undefined?.length)` — always `false` — for the formula's entire existence.

**This is not a new leak; it is the inverse of one.** A dead field cannot leak between sessions, because
it never carries a value at all. The defect is that two rails, and the operator-facing status screen,
named these fields as though they were live signals — `subagent-stop.ts`'s own top-of-file comment
listed `pending`/`in_progress` alongside `blockers`/`previous_gaps` as "already carried" — which is the
misleading half of the dead-rail pattern this project has hit eight times before. Removing them changes
no runtime behaviour (an always-`false` disjunct removed from an `OR` cannot change the result); it
removes the claim that they do something.

**`mergeGaps` iterating prior-first was a second, independent, and real bug.** Once a session's carried
gap list reaches the 12-item cap, the loop fills `out` entirely from `prior` before it ever reaches
`current` — the fresh result of the gate that just ran, which is the one piece of information a stop-time
report most needs, was silently the first thing dropped. `formatCarriedGaps`'s own comment already frames
carried gaps as "history, not a task list" precisely because they can be stale — a merge order that
buries this turn's own evidence under twelve turns of history worked against that framing rather than
for it.

## Trade-offs

**`previous_gaps` still blocks a subagent across sessions, unscoped by commit.** Unchanged from AD-107 on
purpose — that record's reasoning (real tree evidence, `tlc harness reset` as the manual lever) still
holds, and this record does not reopen it.

**`session_narrative` and `completed` are also unwritten today, and are left alone.** Neither is read by
any blocking formula — only `pending` and `in_progress` were removed, because only those two were both
dead and load-bearing in a gate. An unused-but-inert narrative field is a smaller claim than a field two
rails cite as evidence.

## Not decided here

- **Whether `session_narrative` / `completed` should gain a writer or be removed.** Inert, not misleading
  in the same way — nothing currently claims they carry a signal.
- **Scoping `previous_gaps` to commit or branch.** Still [/decisions/ad-107.md](/decisions/ad-107.md)'s
  open item, not this one's.

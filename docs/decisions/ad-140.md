# AD-140 — an unrecognized shell wrapper can no longer hide a forced push

- **status**: active

## Decision

1. **`forcedGitPush` (`src/core/floor/floor.service.ts`) replaces the `verb === "git"` check inside
   `checkShell`.** It scans every word in the shell segment for `git`, `push`, and `--force`/`-f`, rather
   than requiring `verbOf` to resolve `git` as the head verb. It runs before `verbOf` is even called, so a
   segment `verbOf` cannot resolve a head for at all is still checked. A word names `git` if its basename
   does (`namesGit`, mirroring the same normalization `verbOf` already applies) — caught in review before
   ship: a first draft compared literal text only, which correctly denied a wrapper-prefixed `git push
   --force` but silently allowed the identical command with `git` expanded to its absolute path, exactly
   the shape a path-qualifying wrapper produces.
2. **`verbOf`'s `WRAPPERS` set (`src/core/floor/floor.verb.ts`) is unchanged.** No wrapper name was added to
   it — that was the rejected first draft of this fix (see Why).
3. **Regression tests (`src/core/floor/__test__/floor.test.ts`) use a fictional wrapper name**
   (`some-unlisted-shell-proxy`), not the real one this was found against, to assert the general property:
   an unrecognized prefix does not hide the pattern, and does not turn an ordinary or lease-guarded push
   into a false positive either.

## Why

**Found live, during a workshop demo rehearsal.** An operator's shell had every command passed through a
token-optimizing CLI proxy that rewrites `git push --force origin main` to `<proxy> git push --force origin
main` before it reaches the shell. `verbOf` resolved the head verb as the proxy's own name, `git` became an
ordinary argument, and `history-rewrite` never matched — a force push to `main` executed.

**The first draft of this fix added the proxy's name to `WRAPPERS`, and that was wrong.** `WRAPPERS` is a
closed list (`command`, `doas`, `env`, `nice`, `nohup`, `sudo`, `time`, `xargs`) of wrappers this project
happens to know about. Adding one more name fixes exactly the wrapper that was found and nothing else — the
next unlisted shim, corporate proxy, or sandboxing tool an operator's shell injects reopens the identical
gap under a different name. Research into how other agent/shell policy engines handle this (Codex, Gemini
CLI, OpenClaw's LOLBAS-style bypass writeups) converges on the same principle: a name-based wrapper
allowlist can only ever be partial, and the failure mode of an incomplete allowlist is *fail open* — the
exact opposite of what a floor rule with no config switch is supposed to guarantee.

**Matching the whole segment instead of the resolved head verb is the general fix, for a wrapper that
delays the verb as a plain word.** `git`, `push`, and `--force`/`-f` appearing anywhere in the same shell
segment is exactly as easy to construct honestly (a real `git push --force` always has all three) and
exactly as hard to construct by accident (an ordinary command that happens to contain all three unrelated
words is vanishingly rare) — the same trade-off this codebase already accepted for `hidesDestructiveVerb`'s
handling of `eval`/`bash -c` bodies. No wrapper needs to be named by this project for the rule to see
through it, including one that does not exist yet — this claim is scoped to a plain-word delay, not to
every way a wrapper could hide a command; see Trade-offs for the case it does not cover.

## Trade-offs

**Only `history-rewrite` is fixed this way.** `MACHINE_VERBS`, `DESTRUCTIVE_VERBS`, `READER_VERBS`
(secret-access), and the other `verb === ...` checks in `floor.service.ts` still resolve through `verbOf`
and its `WRAPPERS` allowlist, so the same unrecognized-wrapper gap plausibly still applies to them. Not
fixed here: the scope found and proven live was the forced-push case; generalizing every floor check to a
whole-segment match is a larger, riskier change to make under the time pressure that produced this record,
and deserves its own review rather than being rushed in alongside it.

**A contrived command containing the literal words `git`, `push`, and `--force`/`-f` in unrelated
argument positions would still be denied.** No such case exists in this project's own test corpus or was
found in review; the trade-off is accepted for the same reason `hidesDestructiveVerb` already accepts it.

**A wrapper that hides the command inside a quoted string still bypasses this rule, unchanged by this
record.** `sh -c "git push --force origin main"` tokenizes its quoted argument as a single word, so `git`,
`push`, and `--force` never appear as separate words in the segment and `forcedGitPush` does not match.
This is not new — `verb === "git"` never matched this shape either — but it means the fix's own claim above
("no wrapper needs to be named") holds only for a wrapper that delays the real command as plain words, not
one that quotes it. `buildsCommandAtRuntime`/`hidesDestructiveVerb` already deny this same shape for
`DESTRUCTIVE_VERBS`/`MACHINE_VERBS`; extending that existing opaque-body handling to cover a forced push too
is a natural next step, not attempted here.

**Two real spellings of a forced push are caught by neither the old nor the new check.** `git push origin
+main` (a leading `+` on a refspec means force, per git's own documentation) and grouped short flags like
`git push -fu origin main` (`-f` bundled with another flag) are both pre-existing gaps this record found in
review but did not fix — reproduced locally, both perform a forced update. Worth closing in the same place
as the quoted-string gap above.

## Not decided here

- **Applying the same whole-segment match to every other floor check.** A real follow-up, not attempted
  here — see Trade-offs.
- **An operator-configurable wrapper allowlist.** Considered and rejected for this record: floor rules take
  no config surface at all today, and adding one — even one that can only widen detection, never narrow it
  — is a bigger architectural decision than the fix this record makes.
- **Closing the quoted-command, `+refspec`, and grouped-short-flag gaps.** All three are real and
  pre-existing (not introduced by this record); see Trade-offs.

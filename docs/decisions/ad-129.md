# AD-129 — Turn-scope git diffing runs at the event's own working directory, not the project root

- **status**: active

## Decision

1. **`computeTurnScope(root, gitRoot, provider, sessionKey, policy)`** (`src/entrypoints/support.ts`) gains a
   second, required parameter. `root` still resolves `handoffInjectable`/`readHandoff` — state, unchanged,
   per [/decisions/ad-114.md](/decisions/ad-114.md). `gitRoot` now feeds `listChangedRepoFiles`, the one call
   this function makes that actually reads the repository's file state.
2. **`pendingCommentViolations(root, gitRoot, ...)`** takes the identical second parameter, passed through to
   `computeTurnScope` and to `coreFacade.commentPolicy.scanAddedComments`.
3. **Every call site passes `shaScopeRoot(event)`** — already computed at each one, for the rules engine's
   proof sha since AD-114 — as `gitRoot`: `shipGateVerdict` (`ship-gate.ts`), `commentGateBeforeCommit`
   (`tool-before.ts`), and `stopHandler` (`stop.ts`, which duplicates `computeTurnScope`'s logic inline rather
   than calling it, and needed the identical substitution applied by hand at each of its own seven call sites:
   `listChangedRepoFiles`, two `listAddedLines`, `listTrackedFiles`, two `readFileSync`, `scanAddedComments`).
4. **No new field, no new helper.** `shaScopeRoot` already existed and was already correct; this record only
   threads its result into functions that did not yet receive it.

## Why

**AD-114 named this exact gap and deferred it, on purpose, to a narrower fix first.** Its own "Not decided
here": *"`turn_base_sha` in `prompt-submit.ts`... has the same root cause and is plausibly wrong inside a
worktree too. Not fixed here — different subsystem (gate diffing, not rule proof), different, unverified blast
radius."* [/decisions/ad-117.md](/decisions/ad-117.md) picked up half of that — the sha *value* — leaving the
other half, where the value is actually diffed from, exactly as it was.

**Confirmed live, independently, in a different repository.** An agent working in a git worktree hit a
comment-gate denial whose own diagnostic listed hundreds of files with no relation to the session: other
worktrees' listings, unrelated stacks' lockfiles. The cause, read directly from this project's source rather
than guessed: `event.projectDir` stayed at the main checkout (AD-114's deliberate choice), while
`turn_base_sha` ([/decisions/ad-117.md](/decisions/ad-117.md)) correctly recorded a sha valid on the worktree's
own branch. A git worktree shares one
object database with its main checkout, so that sha *resolves* from either directory — but `git diff <sha> --
file`, run from the main checkout, diffs it against the *main checkout's* working tree. Comparing an unrelated
branch's entire file state against a foreign sha reads as "everything was added this turn." Deleting the
flagged line, restating it, even amending the commit that introduced it — nothing the agent did in the
worktree could clear a denial being evaluated somewhere else entirely.

**State and git-diffing are different questions, and AD-114 already answered one of them correctly.**
`.tlc/harness/state`, policy config, and rule-file location have no reason to move into a worktree — a
session's identity and its configuration belong to where it started. What the turn actually *changed*, by
contrast, is a question about files, and files live where the agent is working, not where the session's env
var happens to still point. `decideStopRules(root, shaRoot, ...)` already answers exactly this way for the
rules engine (AD-114's own call site); this record applies the identical split one layer further, to the
comment/duplication/supply-chain gates that ask the same "what changed" question in a different vocabulary.

**Proven with a real worktree, not simulated.** A single-directory fixture cannot reproduce this defect — the
failure mode only exists because two working directories share one object database, so a sha valid in one
names real content when read from the other. Every new test in this record's diff uses a real `git worktree
add` against a real repository, with the main checkout deliberately polluted with unrelated commits so a test
that reads the wrong directory would visibly fail, not pass by coincidence.

## Trade-offs

**`stop.ts` still duplicates `computeTurnScope`'s logic rather than calling it.** This was true before this
record and remains true after it — unifying the two implementations is a real, separate improvement
[/decisions/ad-071.md](/decisions/ad-071.md) already named the risk of (two copies of a run drift apart) but
did not require closing here. Both copies received the identical fix, verified independently by their own
real-worktree tests, so the duplication does not currently hide a divergence — but a future change to one must
still remember the other exists.

**Cursor's `beforeSubmitPrompt` still cannot report a per-event `cwd`**, confirmed against its own
documentation (AD-114's Trade-offs, unchanged). `turn_base_sha`'s *value*, captured at that event, still
resolves from `event.projectDir` on Cursor specifically. This record does not worsen that — proven directly:
a worktree branches from a commit reachable from both directories, so a sha captured at the wrong root is
still a valid, shared ancestor, and the git-ops fix (this record) still diffs correctly from the worktree
against it. The residual gap is narrower than it looks and is exactly where AD-114 left it.

## Not decided here

- **Unifying `stop.ts`'s inline turn-scope logic with `computeTurnScope`.** Named above as a real, separate
  improvement; not required to close this defect, since both copies now agree.
- **A `cwd` source for Cursor's `beforeSubmitPrompt`.** No such field exists in the host's own payload
  (confirmed, not assumed, per AD-114); nothing in this project can invent one.

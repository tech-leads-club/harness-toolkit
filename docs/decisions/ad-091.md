# AD-091 — One workflow owns main and one owns pull requests, so there is one run and one matrix

- **status**: active

## Decision

1. **`ci.yml` triggers on `pull_request`, `workflow_call` and `workflow_dispatch`.** No `push`.
2. **`release.yml` triggers on `push` to `main`** and calls `ci.yml` as its first job, `gate`.
3. **Every release job depends on `gate`**, so a red matrix skips the release with no condition to get wrong.
4. **`workflow_run` is not used.**

## Why

**`workflow_run` fixed the duplication and cost a high-severity finding.** zizmor's `dangerous-triggers` audit
flags it because a `workflow_run` job runs with the base repository's secrets and token no matter what triggered the
workflow it chains from — the classic exploit being a fork's pull-request workflow completing and the privileged
chained run then consuming the fork's artefacts. `branches: [main]` narrows that here, but suppressing a high
finding to keep a design is how a security tool becomes decoration.

**Ownership splits cleanly, and then nothing is duplicated and nothing is chained.** A pull request is `ci.yml`'s
business; `main` is `release.yml`'s. On `main` the matrix runs as `release.yml`'s first job, called from the same
file that defines it for pull requests — so there is one definition, one run per commit, and one matrix inside it.
Before this there were two workflows firing on the same commit and, briefly, two copies of the matrix in them.

**`needs:` is a stronger guarantee than a conclusion check.** With `workflow_run`, the release depended on reading
`github.event.workflow_run.conclusion == 'success'` — a condition on somebody else's outcome, easy to write and
easy to forget, and wrong by default because `workflow_run` fires on completion rather than on success. As a
dependency there is nothing to remember: a failed `gate` skips every job that needs it.

## Trade-offs

**A pull request's run is named "CI" and a push's run is named "Release", for the same matrix.** Someone looking
for a CI run on `main` will not find one; they find the `gate` job inside Release. A required status check would
have to name that job.

**`release.yml` is now the file that runs on every push to `main`**, including pushes that release nothing. Most of
its jobs are skipped in that case — release-please runs, finds nothing releasable, and the rest do not start.

**The matrix is defined in `ci.yml` and consumed from two places.** That is the point, and it means a change to the
gate affects releases immediately, with no second copy to keep in step.

## Not decided here

- **Making the `gate` job a required status check.** It is the check that matters on `main` and nothing enforces it
  at the branch level.
- **Whether zizmor's remaining findings deserve attention.** 19 were suppressed below `high` and 4 ignored; nobody
  has read them.

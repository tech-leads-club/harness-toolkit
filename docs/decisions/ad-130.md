# AD-130 — `gh api` pr-open/push/pr-merge detection is scoped to the local checkout's own remote

- **status**: active

## Decision

1. **`TriggerContext` (`rules.trigger.ts`) gains an optional field: `repoRemote?: {owner: string; repo:
   string} | null`.** `undefined` means the caller never resolved this dimension — every existing call
   unaffected. `null` means the caller tried and found no confirmable local remote. An object is the local
   checkout's own `{owner, repo}`.
2. **`matchesApiShape` requires the API path's `repos/{owner}/{repo}/...` prefix to match `repoRemote` when it
   is supplied**, in addition to the path-shape and method checks [/decisions/ad-128.md](/decisions/ad-128.md)
   already applied. `repoRemote: null` fails every API-shaped match — there is nothing to confirm the call is
   about this project's own repository. `repoRemote: undefined` leaves today's behavior exactly as it was.
3. **`SHELL_SHAPES`'s CLI forms are untouched.** `gh pr create`, `git push`, `gh pr merge` never carry an
   explicit owner/repo in the shapes this project recognizes, and are not evidenced to need this check.
4. **A new `mentionsGhApi(command)` (`rules.trigger.ts`) decides whether `repoRemote` is worth resolving at
   all** — a CLI shape (`gh pr create`, `git push`, `gh pr merge`) never reads it, so a command that never
   contains a `gh api` phrase already has its final answer without spending a process on the remote. Both
   callers check this before resolving.
5. **Two callers resolve `repoRemote`, lazily, mirroring the rules engine's own sha-resolution pattern**
   ([/decisions/ad-100.md](/decisions/ad-100.md)): `ship-gate.ts`'s `isShipCommand` runs the existing cheap,
   repo-blind check first; only if that matched *and* `mentionsGhApi` is true does it resolve
   `platform/git.ts`'s new `localRepoRemote` and re-check with it supplied.
   `tool-before.ts`'s `rulesDecision` resolves it under the identical `mentionsGhApi` guard, alongside the sha
   it already fetches lazily, on the one real
   pass that follows a non-empty dry run.
6. **`localRepoRemote(projectDir, remoteName = "origin")` and `parseOwnerRepo(url)`** (new, `platform/git.ts`)
   read `git remote get-url origin` and parse both SSH and HTTPS remote URL forms.

## Why

**Confirmed live, and the category of the mistake matters.** An agent ran `gh api -X POST
repos/{unrelated-owner}/{unrelated-repo}/git/commits ...` followed by `gh api -X PATCH
repos/{unrelated-owner}/{unrelated-repo}/git/refs/heads/main -f sha=...` — a real, legitimate push to a
repository with no relationship to the local checkout. `ship-gate-comments` denied it, citing a finding from the
*local checkout's own* tree. `matchesApiShape` had no way to tell that the API call named a different
repository at all — it only ever checked the path's shape (does it end in a recognized segment) and the HTTP
method. A cwd drift in the reporting session made the first read of this look like a worktree-resolution bug;
tracing it to the actual command showed the mistake is independent of cwd correctness — the *category* is
wrong regardless of which directory the check runs from, because "what changed in my own local files" has
nothing to say about a push aimed at an unrelated repository.

**This is a distinct defect from [/decisions/ad-129.md](/decisions/ad-129.md), not a recurrence of it.** AD-129
fixed *which directory* a correctly-scoped check reads from. This record fixes *whether the check should apply
at all* to a given command — a question AD-128 never asked when it added REST-path recognition. Both are real;
neither one's fix stood in for the other's.

**The lazy-resolution shape is not incidental — it is the same trade-off AD-100 already made explicit and
measured.** `git remote get-url origin` is cheap in isolation, but this project's own principle (stated
directly in AD-100's own text: *"an operator whose only rule wants a subagent pays no git on any command"*)
is that no tool call should pay for a process spawn it turns out not to need. The cheap, repo-blind shape check
already exists and already returns `false` for the overwhelming majority of commands; gating the new git read
behind that existing check costs nothing in the common case and adds exactly one process spawn to the
already-rare case of a command that already looks ship-shaped.

## Trade-offs

**Laziness is proven on the pure decision (`mentionsGhApi`), not on a spy over the actual process spawn.**
Node's `node:test` mock could not reliably intercept `node:child_process`'s `spawn` as called through
`platform/process.ts`'s named import, in this runtime, confirmed by trying it rather than assumed — the
named binding did not observe the mutation made through a default-import reference to the same builtin
module. The property this record needs held (a non-matching command spends no process; a matching one
spends exactly one) is instead guaranteed by the two callers gating on `mentionsGhApi` before ever calling
`localRepoRemote`, and `mentionsGhApi` itself is fully covered as a pure function.

**A `gh api` call given an explicit path is trusted at face value; nothing resolves `{owner}`/`{repo}`
placeholders `gh` itself would substitute at runtime.** This is the same boundary AD-128 already drew — the
harness reads the command as typed, not as `gh` would resolve it — and this record does not widen or narrow
that boundary.

**CLI-form commands (`gh pr create`, `git push <url>`, `gh pr merge --repo owner/repo`) can, in principle,
target a different repository too**, via an explicit flag or URL this project's `SHELL_SHAPES` do not parse.
Not evidenced as exploited; a materially different parsing problem (CLI flags and positional arguments, not a
REST path) left for a future record if it is ever observed.

**A repository with no `origin` remote configured (or none at all) can never satisfy a `gh api`-shaped
push/pr-open/pr-merge**, even a legitimate one targeting a repository the local checkout genuinely lacks a
remote for. Accepted: there is no local ground truth to confirm relevance against, and failing closed is the
same direction this project already chose for a missing `context.command`.

## Not decided here

- **Parsing an explicit `--repo`/URL override on CLI-form commands.** Named above; not evidenced.
- **A configurable remote name.** Every repository this project has touched uses `origin`; no report has
  needed anything else.
- **GraphQL (`gh api graphql`) repo scoping.** Already out of scope per AD-128; unchanged here.

# AD-133 — `runCommand` stops truncating; the one caller that needs a bound already had one

- **status**: active

## Decision

1. **`runCommand`'s inline `maxChars`/`slice(-maxChars)` truncation is removed.** It now returns the full
   combined stdout+stderr (trimmed of surrounding whitespace), or `"(no output captured)"` when empty — the
   same fallback as before, unchanged.
2. **`listTrackedFiles` needs no code change of its own.** It already calls `runCommand`; removing the
   truncation one layer down is the entire fix — it now receives the complete `git ls-files -z` output, the
   same untruncated contract `gitLines` (the pattern every other function in `git.ts` already follows) has
   always had.
3. **The gate-log-output bound is unchanged**, because it was never really `runCommand`'s to begin with:
   `stop.ts`'s `runLockedGate` passes `result.output` straight into `coreFacade.gate.writeLastGate`, which
   already calls `trimOutputTail(args.output)` (`OUTPUT_TAIL_MAX = 8000`, `src/core/gate/gate.artifact.ts`).
   That call was previously a no-op re-truncation of already-truncated input; it is now the single place this
   policy is applied.

## Why

**Two callers, one truncation, one of them wrong.** `runCommand` is a generic "run a command, capture its
output" helper. Truncating to the last 8000 characters is a reasonable default for a lint/test/docs gate log,
where a failure sits near the end — but it is not a property of "running a command" in general, and
`listTrackedFiles` proved that by using the same helper for something that is not a log: a complete, structured
file list where every entry matters equally, and where the failure mode is silent (a shorter-than-expected
array, not an error).

**The bound already existed, one layer up, under its own name.** `trimOutputTail`/`OUTPUT_TAIL_MAX` in
`gate.artifact.ts` is a purpose-named primitive for exactly the gate-log policy `runCommand` was also
implementing inline. Two independent implementations of the same rule is what
[/decisions/ad-100.md](/decisions/ad-100.md) already argues against — the fix is not a third copy of the
policy scoped to `listTrackedFiles` alone, it is deleting the duplicate and trusting the one that was already
correct and already running.

**Confirmed live, distinct from [/decisions/ad-132.md](/decisions/ad-132.md).** AD-132 fixed six functions that
resolved the wrong directory. This is a different failure mode in a function AD-132 explicitly left alone
(`listTrackedFiles` had no `existsSync` guard to fix) — found by the same review, filed as its own follow-up
rather than folded into that record, because the root cause and the fix are unrelated to directory resolution.

## Trade-offs

**A gate command's captured output is no longer bounded until it reaches `writeLastGate`.** Between
`runCommand` returning and `trimOutputTail` running, the full, untruncated string exists in memory for as long
as a single gate run takes. Accepted: this codebase already holds a command's full stdout/stderr in memory
inside `runProcess` before `runCommand` ever saw it — nothing here is a new order of magnitude of memory use,
only a slightly longer-lived copy of data that already existed.

## Not decided here

- **Whether `trimOutputTail` should move earlier, into `runCommand` itself, as an opt-in parameter.** Not
  evidenced as needed — the one caller that wants the bound already has it, and `listTrackedFiles` must never
  get it by default again.

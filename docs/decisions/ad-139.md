# AD-139 — lessonsView joins ProviderPort, closing the one dispatcher that bypassed it

- **status**: active

## Decision

1. **`ProviderPort` (`src/providers/provider.port.ts`) gains `lessonsView(root: string): string | null`.**
   Every other port method already dispatches through the same interface and the same registry; this one
   did not, and that was the gap.
2. **`cursorProvider`/`claudeProvider` (`src/providers/cursor/index.ts`, `src/providers/claude/index.ts`)
   implement it** with the render functions that already existed (`renderCursorLessonsView`,
   `renderClaudeLessonsView`) — no behavior change for either host.
3. **`renderProviderLessonsView` (`src/entrypoints/support.ts`) looks the provider up in `providers`
   (the same registry `resolveFromRegistry` already reads) instead of naming it.** The two individual
   re-exports of `renderCursorLessonsView`/`renderClaudeLessonsView` from `src/providers/index.ts` are
   removed — `support.ts` was their only caller, and keeping them would leave the old, bypassable route
   sitting next to the new one.
4. **`assertSatisfiesContract` (`src/providers/__test__/provider.contract.test.ts`) checks `lessonsView` is a
   function**, alongside every other port method it already checks — a provider that skips it now fails the
   type check before it fails any test.
5. **`tools/dev/new-provider.ts`'s scaffold stub implements `lessonsView` as `() => null`**, matching the
   pattern its other stubs already use (`render` abstains, `wiring` names a placeholder target) — a
   contributor scaffolding a fourth provider gets a stub that compiles, not a missing-property error.
6. **`biome.json` adds `complexity.noExcessiveCognitiveComplexity` at `info` severity.** Confirmed empirically
   (`biome check --error-on-warnings`, the exact command this project's own lint gate runs) that `info` does
   not change the exit code, while `warn` would: the codebase already has 40+ functions over the default
   threshold of 15, almost all CLI `main()`-style argument dispatchers in `tools/`/`bin/`, none of them this
   record's to fix.
7. **The gate's `biome check` step gains `--max-diagnostics=none`** (`bin/tlc-cli.ts`, `CONTRIBUTING.md`).
   biome's own default caps displayed diagnostics at 20; with the 42 `info`-level findings from item 6 above,
   that cap could push a real `error` finding out of the printed output while the step still failed for the
   right reason but the wrong visible one.
8. **`tools/dev/check-complexity.ts` adds a ceiling on the `noExcessiveCognitiveComplexity` count**, exported
   as `COMPLEXITY_CEILING = 42` and wired into the gate as a new `check-complexity` step, mirroring
   `KNIP_EXPORTS_CEILING`'s existing shape (`bin/tlc-cli.ts`). Item 6's `info` severity means the rule never
   fails the gate on its own; this is what catches the count growing past today's total instead.

## Why

**A review found the concern in the right place, and one real instance of it.** "Several IFs checking which
tool" does not describe `src/core/` or the provider registry — both are already mechanically enforced
(`check-boundaries.ts` forbids `core/` importing `providers/` and forbids vendor identifiers under
`src/core/`/`src/contracts/`). It describes exactly one function, in `src/entrypoints/`, a directory that
scan never reaches. `git log -S` on `renderProviderLessonsView` traces it to the multi-provider feature's own
foundational commit — pre-existing, not introduced by the change under review.

**The fix reuses the registry, it does not invent a second one.** An object map (`{cursor: ..., claude:
...}`) would have removed the `if`s without removing the actual defect: a second, parallel place that has to
be remembered for every new provider, invisible to `check-boundaries.ts` either way. Extending `ProviderPort`
means a third adapter's `lessonsView` is enforced by the type checker the moment it is added to `providers`,
the same guarantee every other port method already carries.

**The lint rule is honest about what it does and does not fix.** `noExcessiveCognitiveComplexity` was chosen
over a nesting-depth-only check because cognitive complexity (the SonarSource metric Biome implements) scores
nesting more heavily than flat branching, which is closer to what "avoid nested ifs" actually means. Enabling
it at `warn` would have failed the gate on 40+ pre-existing functions this record never touched — a much
larger and riskier change than the one asked for. `info` makes the rule active and visible without silently
absorbing that debt into a single unrelated commit.

## Trade-offs

**`info` severity alone would neither have stopped a new deeply-nested function from being added, nor kept a
real gate error visible in `biome check`'s own output.** Both gaps are closed inside this same record — items
7 and 8 above — once biome's default `--max-diagnostics=20` and the rule's toothlessness at `info` were
measured rather than assumed, instead of being tracked as separate future work. Raising the rule itself to
`warn` is still a real, separate option once the existing 42 instances are worked through.

**Two individual re-exports were removed from `src/providers/index.ts`.** Anything outside this repository
importing `renderCursorLessonsView`/`renderClaudeLessonsView` directly from that barrel breaks. Nothing in
this repository did — `support.ts` was the only caller, confirmed by search before removing them.

## Not decided here

- **Fixing the 40+ existing `noExcessiveCognitiveComplexity` violations.** Real debt, not manufactured by
  this record, and an order of magnitude larger than what a code-review comment about one if-chain asked for.
- **Scoping the rule differently for `tools/`/`bin/` vs `src/`.** Considered an override that only applies
  inside `src/`; rejected for now because `info` severity already makes the distinction moot — nothing fails
  either way, so a per-directory override would add configuration surface for no behavior change.

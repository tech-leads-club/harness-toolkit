# AD-142 — Cursor's `usageInPayload` was never true

- **status**: active

## Decision

1. **`cursorCapabilities().usageInPayload` changes from `true` to `false`**
   (`src/providers/cursor/cursor.capabilities.ts`).
2. **`docs/providers/cursor.md`'s generated capability table is regenerated** to match.
3. **The exhaustive capability assertion** in
   `src/providers/cursor/__test__/cursor.detect.test.ts` ("capabilities match the design table
   exactly") is updated to expect `false` — this is the test that fails if the flag regresses.
4. **A `tool-after.ts` test's name and comment are corrected** — it was called "cost estimation is
   skipped when usage arrives in the payload (Cursor)", which restated the same wrong premise the
   capability flag itself carried. Renamed to state what is actually true: Cursor produces no
   `gen_ai` record because there is no payload field to read and `cursor.inbound.ts` never maps
   `transcript_path` onto `event.transcriptPath` in the first place — either reason is independently
   sufficient, so flipping the flag alone does not change this test's observable outcome, only its
   correctness as a description.

## Why

**Found live, at the end of a workshop demo rehearsal.** `tlc harness obs report` for a real Cursor
session — 14 prompts, real shell and tool activity — read `estimated: $0.0000` and `tokens in/out: 0
/ 0`. `usageInPayload: true` is supposed to mean this is expected to work, not a known gap.

**Investigated rather than assumed.** Three independent checks, in the order this project's own
Knowledge Verification Chain requires:
1. *Codebase:* `cursor.inbound.ts` has no code path that ever reads a token/usage field from a raw
   Cursor payload onto `HarnessEvent.usage` or anywhere else — the field the flag's own name promises
   is populated for no event kind.
2. *Vendor docs:* `cursor.com/docs/hooks`'s documented schema for every hook event this adapter maps —
   `preToolUse`, `postToolUse`, `afterShellExecution`, `stop`, `afterAgentResponse`, and the rest —
   contains no token, usage, or cost field of any kind.
3. *Real data on this machine:* the actual transcript file Cursor wrote for the session in question
   (`~/.cursor/projects/.../agent-transcripts/<id>/<id>.jsonl`) is a plain role/message/tool-call log —
   grepped directly for `token`, `usage`, and `cost`, with zero matches across 18KB of real transcript.

**A third-party integration's own docs (SigNoz, an OpenTelemetry-based dashboard) claim
`afterAgentResponse` carries token counts** — but that is Cursor's own separately-exported OTel trace
stream (`service.name: "ide-agent"`, `gen_ai.client.hook.event` span attributes), a different channel
than the flat JSON this project's hooks read from stdin. This project's own real audit log for the
rehearsal session recorded `afterAgentResponse`/`response.after` firing **zero** times across 198
`thought.after` events and dozens of others, despite being wired in `.cursor/hooks.json` — so even if
that hook's JSON payload turns out to carry usage data once confirmed, this session could not have
demonstrated it fired at all. Per this project's own Knowledge Verification Chain (flag uncertainty,
never fabricate), this record does not claim `afterAgentResponse` does or does not carry usage in its
hook JSON — only that nothing this project can currently observe confirms it, and `usageInPayload:
true` claimed a certainty that did not exist.

**The flag is corrected, not a new usage source built.** Building a Cursor-specific usage reader
(mirroring `readClaudeUsage`) needs a confirmed source of real token data to parse — no source exists
in the hook payload this project reads, which is the channel `usageInPayload` describes. Shipping a
reader for an unconfirmed shape would be exactly the "invent an API" failure mode this project's own
research discipline exists to prevent.

## Trade-offs

**Cursor's cost/token report stays at `$0.0000` / `0 / 0` after this fix, same as before.** This record
does not add real cost tracking for Cursor — it removes a false claim that real cost tracking was
already working. The visible number in `tlc harness obs report` is unchanged; what changes is that the
codebase no longer asserts (via the capability flag) that this is expected to be non-zero.

**The report does not yet distinguish "confirmed zero" from "no known source, so unknown."** A rollup
already has a comparable existing mechanism for a different kind of incompleteness
(`cost_incomplete`, for a model missing a catalog rate — see `observability.report.ts`). Extending that
same distinction to cover "this host has no usage source at all" would make the report clearer, but is
a UI/reporting change independent of the capability-flag defect this record closes, and is not made
here.

## Not decided here

- **Whether `afterAgentResponse`'s own hook JSON payload (not Cursor's separate OTel export) carries
  usage data.** Unconfirmed either way — the next step, if picked up, is to get that hook to actually
  fire (its `.cursor/hooks.json` matcher is `"AgentResponse"`; whether that matcher's condition was
  ever met in the rehearsal session is itself unconfirmed) and inspect its real raw payload before
  writing any code that assumes a shape for it.
- **Making the observability report distinguish "unknown" from "confirmed zero."** See Trade-offs.
- **Cursor's Admin API** (`/teams/filtered-usage-events`, `/teams/spend`, `/teams/daily-usage-data`)
  does return real per-request `tokenUsage` and cost fields — judge-found, verified against Cursor's
  own published API docs. It is a genuinely confirmed source, but a different channel entirely from
  what `usageInPayload` describes: an HTTP endpoint behind a team-scoped API key (Basic auth), not
  data riding on a hook's stdin JSON. It does not change this record's fix — `usageInPayload` is
  correctly `false` for the hook-payload channel regardless of what a separate, credentialed HTTP
  poll could return. Correlating an Admin API event back to a specific harness session would need
  its `conversationId` to match `cursor.inbound.ts`'s own `raw.conversation_id` — plausible, since
  `sessionKeyFor` already keys off that same field, but not verified against real data from both
  sides. Not attempted here. **Confirmed against Cursor's own API docs (`cursor.com/docs/api`): the
  Admin API, along with the Analytics and AI Code Tracking APIs, is listed as "Enterprise Teams
  only"** — not available to Hobby, Pro, Pro+, or Ultra, the individual-account tiers, and not
  purchasable as an add-on to one. This channel is only reachable at all for an operator whose
  organization is on a Cursor Enterprise Teams workspace. (Cursor's own per-endpoint API reference
  does not repeat this "Enterprise only" tag on the two endpoints this record cites,
  `/teams/filtered-usage-events` and `/teams/spend` — the two Cursor docs pages disagree with each
  other. The conclusion above does not depend on which is right: every one of these endpoints sits
  under `/teams/*` behind a team-scoped API key regardless, unreachable from an individual account
  either way.)
- **Cursor's own local chat-history database** (`state.vscdb`, a SQLite file under Cursor's
  `globalStorage`) was checked directly, since third-party extensions (e.g. `cursor-chronicle`)
  claim to derive "token tracking" from it. Confirmed empirically on a real installation: a
  per-message `tokenCount` field exists in the schema, sampled 5,000+ real messages spanning the
  full local history, `{inputTokens: 0, outputTokens: 0}` on every single one; a per-session
  `usageData` field also exists, sampled across 10 real sessions, `{}` (empty) on every one. The one
  real, populated, non-zero field in that same session record is `contextTokensUsed`/
  `contextUsagePercent` — context-*window* fullness (how much of the model's context is currently
  occupied), which is a different metric from token *spend*, and one this adapter already reads
  from the hook payload's `context_usage_percent` for an unrelated purpose (compaction warnings).
  Undocumented, unofficial, reverse-engineered storage — not something to build a reader against,
  consistent with the reasoning already given for not reading `afterAgentResponse` speculatively.

# AD-092 — The guard against the release loop counts untagged releases, because one is normal and two is the loop

- **status**: active

## Decision

1. **The guard counts released versions with no tag** and fails above one.
2. **The versions come from the bot's own release commits**, not from the manifest.
3. **The `release-please` job checks out with `fetch-depth: 0`**, because the guard reads tags and history.

## Why

**The first version of this guard blocked the release it was written to protect.** It required the tag for the
manifest's version to exist. There is a legitimate window where it does not: merging the release PR bumps the
manifest to the new version, and the *next* run is the one that creates the tag. So the check fired on the normal
path, on the first release after it shipped, with a message confidently naming the wrong cause.

**The commit cannot tell the two apart, which was the second wrong answer.** The next attempt exempted the case
where `HEAD` is the release commit. Two problems: after the merge, `HEAD` is the `docs(changelog)` commit the
changelog job appends, not the release commit — and during the loop the release commits existed too, so the
exemption would have covered exactly the thing being guarded against.

**Counting is what actually separates them, because the loop's signature is repetition.** One released version
waiting for its tag is the window. Six was the loop. Reading the versions out of the bot's release commits rather
than out of the manifest is what makes them countable at all — the manifest only ever holds the latest, which is
why a single lookup can see one instance and never the pattern.

**Proven in both directions before shipping this time.** In a scratch repository: one untagged release passes, four
fail, and three still fail after the oldest is tagged. Against the real history at the moment of writing: exactly
one untagged version, `0.2.3`, and the guard passes.

## Trade-offs

**A thirty-commit window.** A loop longer than thirty release commits, or a repository whose last release is further
back than that, reads as fewer untagged versions than there are. Thirty is about ten releases at this repository's
commit rate, and reading the whole history on every run to catch a case nobody has is worse.

**It parses commit subjects.** If release-please changes the wording of its release commit, the guard silently
counts zero and stops guarding — the same failure shape it exists to catch. The subject is matched loosely, on both
`chore(main):` and `chore(release):`, and nothing verifies that the pattern still matches anything.

**Two wrong guards shipped before this one.** The first blocked a real release; the second would have permitted the
loop. Both were written from a story about the failure rather than from its signature, and the signature was in the
run list the whole time: six versions in nine minutes.

## Not decided here

- **Asserting that the subject pattern still matches.** A guard that counts zero because the wording moved is a
  dead rail, and this one has no test that would notice.
- **Detecting a tag with no published package**, which is the inverse gap and still unreported
  ([/decisions/ad-090.md](/decisions/ad-090.md)).

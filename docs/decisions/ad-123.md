# AD-123 — Codex capability flags are read off the vendor's hook reference, and the four it cannot settle fail safe

- **status**: active

## Decision

The Codex adapter declares all fifteen `ProviderCapabilities` fields (`src/contracts/capabilities.ts`) as
follows. Each value cites either OpenAI's published Codex hooks reference (read 2026-09-04) or behaviour measured
against a running Codex and recorded in the feature's source transcription. No value is set by analogy to Cursor
or Claude.

| Flag | Value | Provenance |
| --- | --- | --- |
| `enforcesHooks` | `true` | Every hook is invoked synchronously; stdout is read back as a verdict. |
| `askSupportedOn` | `[]` | The reference states `permissionDecision: "ask"` is *parsed but unsupported*. Measured the same way in the transcription: Codex parses it and runs the tool anyway. |
| `sessionEnv` | `false` | `PLUGIN_ROOT` / `PLUGIN_DATA` are documented for plugin-bundled hooks only. Nothing is documented for a `hooks.json` command, so the safe value. |
| `nativeLoopCounter` | `true` | `Stop` and `SubagentStop` carry `stop_hook_active`. |
| `dedicatedShellEvent` | `false` | There is no shell event. Shell is `PreToolUse` with a `^Bash$` matcher. |
| `toolInputRewrite` | `true` | `PreToolUse` accepts `hookSpecificOutput.updatedInput` alongside `permissionDecision: "allow"`. |
| `toolOutputRewrite` | `false` | `PostToolUse` accepts `decision: "block"`, `reason`, and `additionalContext`. There is no field that replaces what the tool returned. |
| `contextAtToolBefore` | `true` | `PreToolUse` accepts `hookSpecificOutput.additionalContext`. |
| `contextAtToolAfter` | `true` | `PostToolUse` accepts `hookSpecificOutput.additionalContext`. |
| `contextAtStop` | `false` | `Stop` documents only `decision: "block"` with `reason`. No context channel. |
| `sessionStartContextReliable` | `true` | `SessionStart` accepts `hookSpecificOutput.additionalContext`, and plain stdout is documented as added to developer context. Corroborated by the transcription, which measured it as reliable. |
| `toolOutputAtAfter` | `true` | `PostToolUse` carries `tool_response`. |
| `usageInPayload` | `false` | No token or cost field appears in any documented payload. |
| `effortSignal` | `false` | Payloads carry `model`; no reasoning-effort field is documented. |
| `thoughtEvent` | `false` | No thought or reasoning event exists in the documented event list. |

The documented event list is `SessionStart`, `SubagentStart`, `PreToolUse`, `PermissionRequest`, `PostToolUse`,
`PreCompact`, `PostCompact`, `UserPromptSubmit`, `SubagentStop`, `Stop`.

## Why

**`askSupportedOn: []` is the load-bearing one, and the vendor says it outright.** A host that parses `ask` and
runs the tool anyway is worse than one with no ask channel, because the field appears to work. `degrade()` turns
an `ask` rule into a `deny` for this host only, so the rule author writes one rule and no core code learns the
host's name. Declaring `["shell.before", …]` here because Claude supports ask there would silently convert every
escalation into an approval.

**Going to the reference was not ceremony — it corrected four claims that would otherwise have shipped as
tests.** The design carried them from the transcription, which describes a working implementation and is good
evidence, but was transcribed from photographs of a sibling repository and had drifted:

1. **Codex has no `SessionEnd` event.** The wiring requirement said its timeout is capped at three seconds.
   `codex.wiring.ts` would have carried a rule about an event the host never fires, and the task's acceptance
   criterion asserted it. `timeout` is in seconds, default and ceiling 600.
2. **`PermissionRequest` does not speak `permissionDecision`.** It takes
   `hookSpecificOutput.decision.behavior: "allow" | "deny"` with a `message`, and any deny wins across competing
   hooks. `PreToolUse` speaks `permissionDecision`. Two events, two vocabularies — which is the reason Codex
   needs its own outbound file rather than sharing Claude's renderer.
3. **`hooks.json` is not a flat list of command strings.** It nests exactly the way Claude's does:
   `{ matcher, hooks: [{ type: "command", command, timeout }] }`. What survives from the transcription is
   narrower than it read — the innermost `command` is a single string rather than the `{ command, args }` exec
   form — and `matcher` is supported, so `WiringEntry.matcher` carries over instead of being dropped.
4. **`stop_hook_active` exists**, which settles `nativeLoopCounter` positively. The design had not accounted for
   a native loop signal on this host at all.

**A flag set by analogy is worse than a missing feature, so the unsettled ones fail safe.** A capability
descriptor exists so `degrade()` reasons over facts rather than over host names. Overstating a capability does
not produce an error — it produces a rail that quietly does nothing, which is the failure this whole mechanism
was built to prevent. Understating one costs a feature the operator can notice and report.

## Trade-offs

**Four flags are read from documentation rather than measured, and documentation cannot settle the question that
matters most for them.** `src/contracts/capabilities.ts:14` states the problem in the contract itself: a host can
accept a field, report it as merged, and still drop it. `sessionStartContextReliable` is precisely that class.
It is declared `true` here on two independent sources — the vendor's own reference and a measurement recorded in
the transcription — but neither is this project running this host. If it turns out false, lessons silently fail
to reach a Codex session at startup. The cheap check is one session with a session-start hook that echoes a
sentinel; until someone runs it, this flag is the least certain value in the table.

**`sessionEnv: false` is probably an understatement.** Codex documents environment variables for plugin-bundled
hooks and says nothing either way for a `hooks.json` command. Declaring `false` costs whatever rail would have
read the session environment; declaring `true` on silence would have that rail read undefined values. Chosen in
the direction that fails visibly.

## Not decided here

- **The remaining two hosts' flags.** opencode and VS Code get their own records; nothing here transfers to them,
  which is the point of the rule.
- **Whether Codex honours `sessionStartContextReliable` in practice.** Recorded as the flag's known weak point
  above, not settled. A measured session upgrades it without touching the adapter.
- **The v1 pipeline gaps** — `WebSearch`, `write_stdin` on an already-approved session, and `apply_patch` body
  parsing not reaching the hook pipeline. Carried from the transcription, not re-verified against the reference,
  and out of scope for the capability table.
- **Whether `matcher` should be used to register a dedicated shell entry.** `dedicatedShellEvent: false` records
  that the host has no such event; whether the wiring writes a `^Bash$`-matched entry is a wiring decision.

# AD-123 — Policy stays declarative; no custom executable policy code, ever

- **status**: active

## Decision

The harness's policy surface — the floor's rules, `Policy`'s rail fields, and the operator-rules vocabulary in
`.tlc/harness/rules/` — never grows an execution surface. Two concrete forms of "run code as policy" were
evaluated and rejected, closing the question rather than leaving it open for a later feature to reach for by
default:

1. **Custom user-supplied policy functions** (an operator drops a `.js`/`.ts` file that the hook path
   `require`s or `import()`s and calls at decision time). Rejected.
2. **Remote policy "packs" as executable code** (a package or URL fetched and executed inside the hook process
   to compute a decision). Rejected.

The alternative for every future expressiveness need is the same one the floor and the rails already use:
**extend the declarative schema** — a new `FloorRule` member, a new `Policy` rail field, a new entry in the
operator-rules trigger/proof vocabulary ([/decisions/ad-100.md](/decisions/ad-100.md)). The vocabulary grows;
the execution model does not.

## Why

**A hook is exactly the shape of decision restricted declarative grammars are built for.** It runs synchronously,
inside another program's request/response cycle, with a real latency budget, and it answers one of a small,
closed set of outcomes (allow, deny, ask, rewrite, context). That is the textbook case the authorization-engine
literature (policy-as-data engines such as OPA/Rego, Cedar, and the same reasoning behind this harness's own
closed `Decision` union) converges on a restricted grammar for, rather than a general-purpose scripting
surface — the grammar can be reasoned about exhaustively (`tsc`'s exhaustive `Decision.kind` switch is the same
property, enforced by the compiler); an arbitrary function cannot.

**Every mainstream JS sandboxing option carries residual RCE risk.** `vm2`, Node's built-in `vm` module, and
worker-thread isolation have each had sandbox-escape CVEs; a boundary that occasionally fails open is worse than
no boundary at all when what runs inside it decides whether a destructive command is allowed. The floor's own
posture — no config switch, because a limit an agent can turn off is not a limit — would be directly
undermined by a policy layer that could itself be reached by arbitrary code, agent-supplied or fetched from a
network the floor otherwise refuses to trust ([/decisions/ad-034.md](/decisions/ad-034.md)'s fetched-program
reasoning applies here too: code that arrives over the wire does not exist when the decision to trust it is
made).

**A remote policy pack is a supply-chain surface with no corresponding benefit.** The harness already refuses to
run a fetched program through a shell ([/decisions/ad-034.md](/decisions/ad-034.md)); fetching one to decide
policy instead of to run a command is the same hazard wearing a different name, and it would apply to every
decision the harness makes rather than to one command.

**The declarative alternative already has capacity proven by this repository's own history.** Every prior
extensibility need — a new floor rule, a new rail, a new operator-rules trigger/proof pair
([/decisions/ad-100.md](/decisions/ad-100.md)) — landed as a schema/vocabulary addition, never as a code hook.
`enforcement-hardening`'s own two mechanisms (`wiring-tamper`, `secrets.redactOutput`) are two more data points:
both shipped as a new `FloorRule` member and a new `Policy` field, with nothing resembling a plugin API.

## Trade-offs

**An operator cannot express a policy this harness's vocabulary genuinely cannot state.** A truly novel
decision shape has to become a feature request — a new `rules` trigger/proof pair or a new rail — rather than
something an operator can bolt on unilaterally the same day. This is deliberate: the alternative is exactly the
execution surface this decision closes.

**The declarative vocabulary must keep growing to stay sufficient.** Rejecting code-as-policy raises the bar on
this project's own responsiveness — a real, recurring need that the schema cannot express is a gap this
decision commits future work to closing through the schema, not around it.

## Not decided here

- **Which specific vocabulary addition serves any particular future request.** This decision closes the
  execution-surface question; it does not pre-select the next `FloorRule` or rail.
- **Whether a future declarative rule language (e.g. a restricted expression grammar richer than today's
  trigger/proof pairs) is warranted.** That is a schema-design question or a candidate for a future AD; it is
  still not an execution surface, and nothing here should be read as blocking it.

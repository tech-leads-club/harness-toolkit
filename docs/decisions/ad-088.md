# AD-088 — The release keeps its pull request and merges it with --admin, and a hand-written workflow linter is replaced by zizmor

- **status**: active

## Decision

1. **The release PR stays, and the bot merges it with `gh pr merge --rebase --admin`.** No `--auto`, no fallback.
2. **The App token is scoped**: `owner` and `repositories`. ~~`permission-contents`, `permission-pull-requests`~~
   — the verb scope broke release creation and was withdrawn ([/decisions/ad-093.md](/decisions/ad-093.md)).
3. **`persist-credentials: false`** on every checkout that does not push.
4. **`zizmor` audits the workflows**, and `tools/dev/check-workflows.ts` is deleted.
5. **The changelog's tag glob is derived from the package name**, not written down separately.
6. **No hand-rolled version arithmetic.** `release-please` keeps computing the version.

## Why

**`--admin` is the flag this repository spent an afternoon working around.** The chain was: the ruleset requires
one approving review, an App cannot approve its own pull request, so `--auto` armed the merge and waited for a human
for ever — measured with the App on the bypass list, all three CI jobs green, still `reviewDecision:
REVIEW_REQUIRED`. The conclusion drawn from that was that a PR-shaped release cannot be unattended under this
ruleset, and the next step taken was to start replacing release-please with a version calculator written here.
`BHubAI/platform` releases through the same action, the same ruleset shape and the same App, and its merge step is
one line: `gh pr merge "$number" --rebase --admin`. `--admin` exercises the bypass rather than waiting on the rule.
The reasoning was sound and the search was not.

**A hand-rolled release was solving a problem that did not exist.** The calculator written before finding that —
Conventional Commits to semver, `bump-minor-pre-major`, tag naming — reproduced every version this repository has
released, which is a good sign about the code and the wrong thing to have. It is deleted. The lesson is not "never
build it": it is that a convention this repository shares with the rest of the organisation is a fact to look up,
not to re-derive.

**One of those hours did find something real, and it was not the release tool.** The changelog generator listed tags
with the glob `v*`, and every tag ever created here is `harness-toolkit-v…`. It matched none, so all 88 decision
records sat under `## Unreleased` through three published releases — and `render-changelog --check` passed the whole
time, because the generated document and the committed one were wrong identically. This is the dead-rail shape the
repository has now hit several times: a consumer whose empty answer is indistinguishable from a correct one. The
prefix is now derived from `package.json`'s `name`, the same source the tag is written from, and a test asserts it
against a tag that actually exists.

**`zizmor` supersedes a checker written here hours earlier.** `tools/dev/check-workflows.ts` enforced one rule —
actions pinned to a SHA. `zizmor` enforces that as `unpinned-uses: hash-pin` and adds impostor-commit detection,
over-broad `GITHUB_TOKEN` permissions, injectable template expressions and credential persistence. Keeping both
would be two implementations of one rule, and keeping only ours would be choosing the smaller of the two on the
grounds that we wrote it.

**A scoped App token and `persist-credentials: false` were free and missing.** An App token defaults to everything
the App can reach across every repository it is installed on; naming `owner`, `repositories` and the two
`permission-*` fields bounds a leak to this repository and to two verbs. `persist-credentials: false` keeps the
checkout credential out of `.git/config` on the jobs that only read — including the one holding the npm publishing
identity.

## Trade-offs

**`--admin` bypasses the review for real, and that is the point and the cost.** Nothing human looks at a release
before it lands on `main`. What remains is mechanical: `verify` runs the full three-platform matrix before the
publish ([/decisions/ad-084.md](/decisions/ad-084.md)), and `--admin` bypasses the *review* and never the gate. If
that trade stops being acceptable, the lever is the `publish` environment's required reviewers, not this flag.

**The gate no longer catches an unpinned action locally.** `zizmor` runs in CI, so a contributor learns about a
tag reference on the push rather than before it. Running zizmor in the local gate would add a Rust binary to a
toolchain that needs only Node or Bun today. This is the same trade `check-dist-fresh` already makes.

**`min-severity: high` leaves lower findings unread.** It is what this repository holds at zero today, and picking
a level nobody has measured findings for would mean either a red gate on day one or a threshold chosen to be quiet.

**A deleted calculator is work thrown away.** About two hundred lines with sixteen tests, all passing, all
correct. Keeping it because it exists would have put a second source of truth for versions next to the one the
organisation uses.

## Not decided here

- **Whether `zizmor` should run in the local gate.** It would need the binary on every contributor's machine.
- **Lowering `min-severity`.** Needs the findings read first.
- **Whether the `publish` environment keeps required reviewers.** With `--admin` on the merge, that environment is
  now the only human step in a release ([/decisions/ad-087.md](/decisions/ad-087.md)).
- **`workflow-pin-inventory` and `workflow-pin-deprecation`**, which the same repository runs and which report on
  pins across a fleet. This repository is one workflow file and two jobs, so the inventory has nothing to inventory
  yet.

# AD-122 — Handoff continuity is scoped per session, and a live neighbour is never a source

- **status**: active

## Decision

1. **`handoff.json` shrinks to the project-wide facts only** (`mode`, `project_name`, `git_branch`, `git_sha`) —
   `HandoffFile` v3. The turn-scoped continuity slice (`blockers`, `next_action`, `plan_*`, `previous_gaps`,
   `turn_base_sha`, `pending_lesson_credit`, `last_ship_claim_*`, `last_changed_files`, `last_stop_status`,
   `last_gate_result`, `last_fingerprint`, `fingerprint_hits`, `last_failure_category`, `completed`,
   `session_narrative`) moves to its own file per `(provider, session)`, under a new `handoff-sessions/`
   directory — sealed and locked exactly as the old shared file was, one lock per session so two sessions never
   contend on the same one. `HandoffProviderSlice.session_key` (written once, read nowhere) is retired; the
   fact it tried to carry now lives in the session file's own `owner`.
2. **Liveness is decided by presence, not by pid.** `isSessionLive(root, provider, sessionKey)`
   (`src/core/presence/presence.service.ts`) reads the same heartbeat record every recognized hook event already
   refreshes ([`run.ts`](/src/entrypoints/run.ts), regardless of which one-shot process handled that event) and
   asks only whether it is still fresh — against `CONVERSATION_STALE_MS` (thirty minutes), a threshold owned by
   this question alone and never shared with `checkCollision`'s much shorter file-claim expiry
   (`CLAIM_STALE_MS`, ten minutes; see Why for why conflating the two was itself a defect). `heartbeat` also
   self-heals: a call against a session with no existing record creates one rather than no-op-ing, so a record
   `sweepStale` removed for looking quiet is restored by that same session's own very next event, not left
   permanently unreadable as live. `isProcessAlive(pid, host, thisHost?, probe?)` was extracted to
   `src/platform/process.ts` from `gate.lock.ts`'s `isLockOwnerGone` in the same change, and stays exactly where
   it was already correct — the grind lock, held for one long-running gate command's own duration. It is not
   reused for handoff, and `HandoffSessionOwner` carries no pid or host of its own — see Why for the reason a
   pid-based first draft of this same fix was provably wrong for this purpose.
3. **`readHandoff(root, provider, sessionKey)` merges shared facts, a dead predecessor's slice, then this
   session's own** (own wins on conflict). A predecessor is the most-recently-updated *other* session file for
   the same provider whose conversation is confirmed not live via `isSessionLive` — a live neighbour is filtered
   out before the "most recent" comparison even runs, so recency never rescues it. Both a predecessor's slice
   and a foreign provider's slice (`readForeignSlices`) are trusted only once their own file's seal verifies
   ([/decisions/ad-078.md](/decisions/ad-078.md)) — a session file changed outside a harness write is withheld
   the same way the shared file already was, not merely the reader's own.
4. **`pruneDeadHandoffSessions`, run once at session start,** deletes a confirmed-not-live session file only
   once its `owner.updated_at` is older than seven days — long enough for a same-week restart to still inherit,
   bounded so a long-lived project's directory does not grow forever — and removes that file's seal sidecar in
   the same pass, so a pruned session never leaves an orphaned seal behind for a later path to collide with.
5. **The operator's own tools are not liveness-gated.** `readLatestSlice` (the `tlc harness handoff` CLI's
   diagnostic view) and `clearStuckSignals` (`tlc harness reset`) read and act on every session file,
   live or dead — an operator's own terminal command, not a turn's decision
   ([/decisions/ad-078.md](/decisions/ad-078.md) draws the same line: reading is not the injection surface).

## Why

**Reported live, twice, independently.** Two operators running more than one agent tab on the same Cursor
workspace and branch saw a "BLOCKED" follow-up meant for one tab's turn get processed by a different, unrelated
tab. Traced to `handoff.json`'s `by_provider[providerName]` slice: keyed only by provider name, so every
session of that provider on that project read and wrote the exact same record. A blocked session's own
`blockers`/`next_action` would sit there until *any* session's next read surfaced it as that session's own
follow-up — not a routing bug in either host, a genuine shared-mutable-state defect in this harness.

**The field that should have caught this was already there.** `HandoffProviderSlice.session_key` was recorded
at session start and compared by nothing — the dead-rail pattern this project has already named four times
before ([/decisions/ad-034.md](/decisions/ad-034.md) and its own list of instances): a producer with no
consumer reads as a safeguard and is not one.

**Liveness, not a session-key comparison, because the field's own limits were already visible.** A bare
"is this a different session_key" check cannot distinguish a session that is still running from one that
merely restarted — either answer is "different," and the continuity's whole cross-restart purpose depends on
telling those apart.

**A pid-based first draft of this same fix was proven wrong before it landed, by the exact same shared-state
class of defect this AD closes.** `gate.lock.ts`'s `isLockOwnerGone` already solves this for the grind lock with
`process.kill(pid, 0)` — the one definitive signal for "is the process that wrote this still alive" — and the
first version of this fix reused it directly for handoff, recording `owner.pid`/`owner.host` on each session
file. That mechanism is correct for the grind lock, whose pid belongs to one long-running gate command still
executing when the lock is read. It is meaningless for handoff: every hook process is one-shot and calls
`process.exit()` at the end of its own turn ([`run.ts`](/src/entrypoints/run.ts)), so `owner.pid` is already
dead by the time *any* later turn reads it — including a genuinely still-open conversation's own next turn.
Under that mechanism, `findDeadPredecessor` treated every other session as dead, live or not, reproducing the
original bug under a different name. The harness already has a signal that means "is this conversation still
active" rather than "did the last process handling it exit yet": presence's heartbeat, refreshed on every
recognized event regardless of which process handled it. Reusing *that* instead is the fix that actually holds.
Extracting `isProcessAlive` for the grind lock's own genuine use was correct and is kept
([/decisions/ad-100.md](/decisions/ad-100.md) and [/decisions/ad-114.md](/decisions/ad-114.md) already applied
the same "extract, don't duplicate" reasoning to their own repeated mechanisms) — it is simply not the same
mechanism handoff needed.

**Verified against a real presence record, not a mocked liveness stub.** A "live" fixture modeled as an
injected function that never returns false cannot fail the way the pid draft actually failed — the discrimination
sensor a fresh-agent verifier ran against the pid draft passed it by construction. The corrected tests instead
register a real presence record via `presence.service.ts`'s own `register()` and assert the resulting live
session's fields are withheld; `handoff.concurrency.test.ts` separately spawns a genuine subprocess for the
locking behaviour itself, confirming two live writers under the same or different sessions never clobber each
other.

**A second review pass reproduced the exact reported symptom against the presence-based fix itself, before it
landed.** Presence's own staleness threshold was ten minutes — sized for `checkCollision`'s file-claim expiry,
a genuinely short window — and `isSessionLive` reused that same number for a different question, "is this
conversation still open." An operator idle for eleven minutes (reading output, thinking) was enough to make
`sweepStale` (run at another tab's session start) delete the idle tab's presence record outright; because
`heartbeat` treated a missing record as a no-op, that tab stayed misdiagnosed as dead for the rest of its life,
regardless of how soon it became active again — reproducing the original bug's symptom by a different path.
Both halves are fixed together: `CONVERSATION_STALE_MS` (thirty minutes — this codebase's own precedent for a
stale-but-alive tolerance, `GATE_LOCK_STALE_MS`) is now the only threshold `isSessionLive` and `sweepStale`
answer to, decoupled from `checkCollision`'s unrelated `CLAIM_STALE_MS`; and `heartbeat` self-heals a missing
record instead of leaving it gone, so the idle tab's own next event — not a fixed deadline — is what ends the
misdiagnosis. The same pass found `HandoffSessionOwner.pid`/`.host`, inherited from the pid draft, had become
exactly the dead rail this AD's own second paragraph already named: written on every patch, required by the
type guard, read by nothing since liveness moved to presence. Both fields are gone from the type.

## Trade-offs

**One more file per session, forever until pruned.** Bounded at seven days of confirmed-dead retention (point
4); a project with many short-lived sessions carries that many small files in the interim, not an unbounded
directory.

**A session that restarts under a genuinely new `session_key` (not a resumed one) only inherits once its
predecessor is confirmed dead** — for a session still technically alive but abandoned by its own process
without exiting (a hang, not a crash), continuity is withheld until the process is actually gone, same as the
grind lock already tolerates for its own stale-but-alive case.

**Up to thirty minutes without any event is still read as not-live.** A session idle longer than
`CONVERSATION_STALE_MS` — a very long pause with no tool call, no prompt, nothing recognized — can have its
presence swept and, in that window only, be treated as a dead predecessor by a concurrent session. It self-heals
on its own very next event and is bounded to that one window, never permanent; a shorter window would misfire
on ordinary long-output pauses (the case a second review pass reproduced against ten minutes), a longer one
would leave a genuinely-ended session's continuity uninherited for that much longer.

**`tlc harness reset`'s reported identifier changed** from a bare provider name to `provider:session_key`, since
more than one session can now be cleared per provider. `resetStuckState`'s own doc comment, which described the
old shared behavior as intentional, is corrected to match.

## Not decided here

- **Detecting a hung-but-alive predecessor faster than seven days** (`pruneDeadHandoffSessions`'s own retention
  window, distinct from presence's thirty-minute conversation-liveness threshold above). Not reported, not
  evidenced beyond the case already closed.
- **A richer `tlc harness handoff` view listing every concurrent session distinctly**, rather than one
  most-recent row per provider. The diagnostic shape is unchanged from before this fix; a fuller view is a
  natural follow-up, not required to close the reported defect.

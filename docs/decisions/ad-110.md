# AD-110 — The documented ship-gate excludes promised two paths core is not allowed to name

- **status**: active

## Decision

1. **`docs/concepts.md` no longer documents `.cursor/`/`.claude/` as default `runtimePathExcludes`.**
   The default stays `.tlc/`, `**/node_modules/`, `**/.git/` — three entries, matching
   `policy.defaults.ts` exactly, which is what [/decisions/ad-080.md](/decisions/ad-080.md)'s default
   check exists to guarantee.
2. **The doc now says why the other two are absent**: `src/core` stays provider-neutral
   ([/decisions/ad-011.md](/decisions/ad-011.md)), so a provider's own directory is not a core default —
   and names the real lever, a project's own `shipGate.runtimePathExcludes`.

## Why

**An independent audit of config loading found the drift and the first fix tried made it worse.**
`docs/concepts.md` named five default excludes; `policy.defaults.ts` carried three. Adding
`".cursor/"` and `".claude/"` directly to the array in `src/core/policy/policy.defaults.ts` looked like
the obvious one-line fix — `tlc harness test`'s `check-boundaries` step refused it on the first run:
`vendor-identifier-in-core` scans `src/core` and `src/contracts` for the pattern
`\b(cursor|claude|codex|composer|anthropic)\b` and failed on exactly that line.
[/decisions/ad-011.md](/decisions/ad-011.md) already settled why — vendor-specific data belongs to the
provider that owns it, not to core — and a path literal naming a specific host's config directory is
the same shape of violation as the model catalogs and cost-pool names that decision moved out.

**So the doc's promise, not the code's default, was the thing wrong.** Building a provider-additive
excludes mechanism (the pattern `claude.policy-defaults.ts`/`cursor.policy-defaults.ts` already use for
`blockedPatterns`/`untrustedTools`) would satisfy the doc as written, but is a real feature — a new
`ProviderPolicyDefaults` field, a merge point in `support.ts`, and tests for both providers — for a gap
that is inert under every default configuration today (no default `runtimePathPrefixes` entry matches a
dotfile directory, confirmed by the same audit). Correcting the doc to state the actual, deliberate
constraint is the smaller, honest fix; building unused provider-merge plumbing to satisfy a five-item
list nobody asked for is not.

## Trade-offs

**A project whose `runtimePathPrefixes` is customised broadly enough to reach `.cursor/` or `.claude/`
gets no automatic exclusion.** The doc now says so directly and names the escape hatch (a project-level
`shipGate.runtimePathExcludes` override) instead of promising a default that core cannot carry.

## Not decided here

- **A provider-additive `runtimePathExcludes` mechanism.** Worth building if a real project hits the
  gap this record found inert; not worth building ahead of one.

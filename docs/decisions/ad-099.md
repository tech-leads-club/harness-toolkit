# AD-099 — Reading a file claimed it, so a review agent locked the operator out of writing

- **status**: active

## Decision

1. **Only a write claims a file.** `edit.after`, and `tool.before`/`tool.after` whose tool writes.
2. **The heartbeat stays unconditional.** A reading session is live; staleness is what expires a claim.
3. **The message says what happened and how to clear it** — that the other session *wrote* the file, and that
   ending it or waiting for the claim to go stale are the two exits.
4. **One list of writing tools**, in `src/contracts/tool-names.ts`, shared with the policy-surface guard.

## Why

**Measured on a real machine.** An operator asked a second agent to review a pull request. The reviewer read two
files to measure a claim in the code. Every later write to those files was refused:
`claude session e5acc2a8 touched identity.verifier.spec.ts just now`. Their own `git status` showed one
modification — theirs — and the reviewer had changed nothing.

**The claim was recorded for any event carrying a path.** `read.before` carries `file_path`, and so does
`tool.before` for a read tool, so `run.ts` wrote both into `recent_files`. The rule that then refused is called
`edit-collision`, and its message said the other session had *edited* the file. Three things wrong at once: a
reader cannot lose work, the rule fired outside what it is named for, and the message asserted something that had
not happened.

**And there was no exit.** `ask` becomes a refusal wherever no operator can answer the prompt, which is every
non-interactive mode. So the operator got a hard block, a false reason, and nothing to do about it — the claim
expires after ten minutes without a heartbeat, and nothing said so.

**The suite had pinned the defect.** A test named "presence heartbeat records the touched file for a read.before
event" asserted exactly the behaviour that caused this. It is inverted now
([/decisions/ad-041.md](/decisions/ad-041.md) is the sibling: a test can encode a defect as a requirement).

## Trade-offs

**A read that precedes a write no longer warns.** Two agents can now read the same file and both start writing;
the collision is caught at the first write rather than at the first read. That is the correct trade — the check
exists to protect work in progress, and a read is not work in progress.

**The ten-minute window is unchanged.** A session that dies without releasing its claim still holds it for ten
minutes. Shortening it would raise the chance of two live writers slipping past each other.

**`ask` still hardens into a refusal where nobody can answer.** That is the safe direction for a write collision,
and it is why the message now has to name the exits itself.

## Not decided here

- **A command to release another session's claim.** `tlc harness status` shows them; clearing somebody else's
  claim from a third session is a way to lose the work the check protects.
- **Whether a stale claim should be swept on read rather than on write.** `sweepStale` exists and runs where it
  runs today.
- **Making `ask` reachable in non-interactive modes.** That is the host's prompt, not ours.

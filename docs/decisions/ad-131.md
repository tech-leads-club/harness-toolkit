# AD-131 — A ship-gate denial names what it checked and points at `tlc harness why`

- **status**: active

## Decision

1. **A new core module, `src/core/diagnostics/diagnostics.message.ts`, computes one shared diagnostic from
   `(shaRoot, sha, files)`.** `diffDiagnostic` returns `{footer, summary}`: `footer` is the multi-line block a
   diff-based denial appends to its message — `Checked <root> at <sha>.`, up to 5 distinct `Reproduce: git diff
   <sha> -- <file>` lines, then a pointer to `tlc harness why` — and `summary` is the single bounded line stored
   for later. `rootDiagnostic(shaRoot)` is the same shape without a sha or a reproduction line, for a check that
   ran a command rather than a diff. Exported as `coreFacade.diagnostics`.
2. **The comment gate, the duplication gate and a lint/test/docs gate failure all get this footer**, in both
   places they can fire: `ship-gate.ts`'s `shipGateVerdict` (push/pr-open/pr-merge, [/decisions/ad-116.md]
   (/decisions/ad-116.md)) and `tool-before.ts`'s `commentGateBeforeCommit` (commit,
   [/decisions/ad-115.md](/decisions/ad-115.md)). Each already had `shaRoot` in scope; `sha` is fetched lazily,
   only inside the branch that is about to deny, so the pass path spends no new git call
   ([/decisions/ad-100.md](/decisions/ad-100.md), [/decisions/ad-130.md](/decisions/ad-130.md)).
3. **`Decision`'s `deny`/`ask` variants gain an optional `diagnostic?: string`** — the bounded `summary`, additive
   and never required. The two obs writers that turn a decision into a record (`run.ts`'s `recordRefusal`,
   `tool-before.ts`'s `recordShellDecision`) forward it into `attrs.diagnostic`, defaulting to `"none"` the same
   way `attrs.rule` already does.
4. **`tlc harness why` ([/decisions/ad-062.md](/decisions/ad-062.md)) renders it.** `decisionsFrom` prefers a
   `policy.deny`/`shell.start` record's `diagnostic` attr over the tool-name/command fallback when present, and
   marks the decision `selfDiagnosing`. `whyText` appends one static, plain-language sentence — naming no AD
   number, no internal field name — when the rendered window contains at least one such decision, never per line
   and never on an empty window.
5. **`ruleMessage` ([/decisions/ad-120.md](/decisions/ad-120.md)) gains the same pointer line**, immediately
   after its existing `— checked <shaRoot> at <sha>` phrase and before the operator's own body. That phrase is
   untouched; only the pointer is new.

## Why

**Three denials in the same session, and the third one is the one that mattered.** The first two were real
defects, already fixed and shipped: a diff running from the wrong directory ([/decisions/ad-129.md]
(/decisions/ad-129.md)) and a `gh api` push scoped to the wrong repository ([/decisions/ad-130.md]
(/decisions/ad-130.md)). The third denial was not a harness defect at all — the checked directory was correct,
and the comparison was correct; the calling agent's own shell had silently returned to a different checkout
than the one it believed it was in, a host-level fact the harness cannot see and has no obligation to fix.
Diagnosing that third case took exactly as long as the first two, for a reason that has nothing to do with
which of the three it was: **none of the three denials said what they checked.** A human had to read source
code and run `git diff` by hand each time to find out.

**AD-120 already solved this once, and solved it narrowly.** It taught an operator rule's `since HEAD` denial
to name the directory and sha it checked, because a denial that names its own verdict but not its own evidence
is only half a fact. This record is not a new idea — it is that same fix, extended to the three other
deny-producing checks in the same ship-gate battery that never got it, because AD-120 only ever touched the one
path it was diagnosing at the time.

**`tlc harness why` existed to answer exactly this question, and could not.** It was built ([/decisions/ad-062.md]
(/decisions/ad-062.md)) to tell an operator "did the harness do that, and why" without them reconstructing it
from a transcript. Read closely, it never actually read a denial's own reason text — `decisionsFrom` rendered a
`policy.deny`/`shell.start` record's bare tool name or raw command, which carries none of what was checked. The
one command built for this question was structurally unable to answer it. This record closes that gap by
carrying the diagnostic as its own obs attribute, not by asking `why` to re-parse a message string after the
fact — a re-derived directory or sha could drift from what the original denied event actually saw, and this
project already prefers recording a fact once, where it is known, over reconstructing it later
([/decisions/ad-058.md](/decisions/ad-058.md)).

**The two audiences are the same person at different distances from the terminal.** A blocked agent reads the
denial text in its own context and can act on the footer immediately. A human — or a different agent, in a
different session, with no memory of the first — reads `tlc harness why` afterward and needs the identical
fact, explained without assuming they know what `turn_base_sha` means. Neither audience should need the other
to translate.

## Trade-offs

**A comment or duplication denial now spends one lazy git call it did not before**, but only on the branch that
was already about to deny — a rare path, and one that already resolves a sha a few lines later for the
stop-rules check in `ship-gate.ts`. The pass path, the overwhelming majority of calls, spends nothing new.

**`Decision.diagnostic` is read by both obs writers, but only the shell-routed writer
(`recordShellDecision`) currently has a real producer.** Every check this record touches fires on a shell
command (`commit`/`push`/`pr-open`/`pr-merge`), so `recordRefusal` — the non-shell path — forwards a field
nothing yet populates through it. Accepted, for the same reason `attrs.rule` is read unconditionally in both
writers already: the pass-through is generic and correct regardless of which caller currently exercises it, and
it costs one already-defaulted field, not a new counter an operator could mistake for a working signal
([/decisions/ad-027.md](/decisions/ad-027.md)).

**The reproduction command trusts the caller's own `shaRoot` and `sha`, not a re-verified pair.** If a future
caller ever passed a mismatched root/sha combination into `diffDiagnostic`, the printed `git diff` would be
wrong in exactly the way this record exists to prevent. Nothing here re-derives or double-checks the pair; it
formats what it is given, the same trust boundary AD-120 already accepted for `ruleMessage`.

## Not decided here

- **`why`'s `--json` output does not gain a separate structured diagnostic field.** The existing `detail`
  string already carries it; a `--json` consumer that wants the parts separately (root vs. sha vs. reproduction
  command) is not evidenced as needed yet.
- **CLI-form commands that could target a different repository or directory than the one named.** Out of scope
  here, and already named as unresolved in AD-130's own "Not decided here".
- **The two-dot-vs-three-dot diff question** — whether a fast-forward mid-turn should ever count an unrelated
  upstream commit as "this turn's own" — is a distinct, unconfirmed question raised by the same investigation
  that led here. It needs its own evidence before it is a record.

# AD-136 — `hook.enter` makes a hook invocation observable before any decision is made

- **status**: active

## Decision

1. **`runHandler` (`src/entrypoints/run.ts`) records a `hook.enter` signal for `shell.before`/`mcp.before`
   events** — the two kinds `pr-open`/`push`/`pr-merge` actually gate on, the incident's own shape — the
   moment the event is resolved: after `provider.toEvent` returns a non-null `event` and `provider.capabilities()`
   runs (both pure, neither can throw or block), before `loadPolicy`, before `handler(event, context)` runs,
   before anything in the existing `try` block that could throw or take meaningful time. It carries `event`,
   `toolName`, and `sessionKey`, tagged with the real provider name (not the `"unknown"` placeholder the three
   earlier, pre-event failure paths already use for `adapter.unrecognized`/`adapter.ambiguous`).
2. **The existing `recordAdapterEvent` helper gains an optional `provider` parameter**, defaulting to
   `"unknown"` — its three existing callers are unchanged; `hook.enter` is the first caller that has a real
   provider to attribute the record to at the point it fires.
3. **Nothing about the decision path changes.** `hook.enter` is additive: every existing record
   (`policy.deny`, `shell.start`, `adapter.error`, the provider's own rendered output) is produced exactly as
   before, at the same point, with the same content — `hook.enter` only adds one record ahead of whatever
   already gets written for that invocation.

## Why

**The incident could not be read from the operator's own state files — it had to be reconstructed.** A shell
command that opened a pull request left nothing in `obs.jsonl`: not a denial, not an allow, nothing. An
almost-identical command from the same session, seconds earlier, was correctly evaluated and denied — proving
the rule-matching logic itself was not at fault. Answering "why did this one command leave no trace" required
reading `src/entrypoints/run.ts` and `src/platform/fs-atomic.ts` directly, ruling out an uncaught exception
(the `catch` block's `adapter.error` has zero occurrences in the operator's own `obs.jsonl` history — if the
handler had thrown, this record would exist) and lock contention (the hot path only reads handoff state,
never the locked write path `withFileLock`/`updateJsonAtomic` guards). What was left after ruling out every
internal, code-inspectable candidate is host behavior this project has no visibility into — and no amount of
further code reading could narrow it further, because the absence of a record is consistent with several
different failure points, and nothing distinguished them.

**Recording as early as possible is what makes the distinction legible.** A future incident with `hook.enter`
present and no paired completion record is a hook that started and died mid-flight — consistent with a host
timeout killing the process after it began running user code. A future incident with no `hook.enter` at all is
a hook that never started, or died before reaching even this first line — a different failure point entirely,
one this project's own code cannot be the site of a fix for. Today, both looked identical: nothing. This
record is the one change that separates them, without needing to guess which one actually happened this time.

**A fix was not designed because the cause was not confirmed, and designing one anyway would have risked
solving the wrong problem.** This project's own knowledge-verification chain treats an unconfirmed hypothesis
as exactly that — never presented as fact, never acted on as though it were. Changing `.cursor/hooks.json`'s
timeout, or any other change premised on the host-timeout hypothesis, would be exactly the fabrication that
chain exists to prevent. The honest, useful action available today is visibility; the fix, if one is needed at
all, waits for the next occurrence to confirm what actually happened.

## Trade-offs

**The first version of this record was unscoped, and that was a real defect, not a hypothetical one.**
Recording `hook.enter` for every `runHandler` invocation — `read.before`, `tool.after`, `edit.after`,
`prompt.submit`, every kind — was measured, by an independent reviewer, against a pre-existing baseline: 501
allowed invocations produced 501 signal-plane records where the baseline produced roughly one, because
`SIGNAL_KINDS` (`observability.types.ts`) had deliberately excluded ordinary tool traffic from this plane.
Two consequences were measured, not assumed: `turn.activity.ts`'s `readTurnActivity` lost its `prompt.submit`
boundary once `hook.enter` filled its fixed-count tail, silently stopping the idle-turn gate
(`src/entrypoints/stop.ts`); and `tools/obs-cli.ts`'s `live` command, the command
[/diagnose.md](/diagnose.md) prescribes for an empty-signal investigation, showed a screen of
`hook.enter` with the actual `policy.deny` pushed out of its tail. The claims this section originally made —
"already grows on every tool call today," "roughly doubles" — were wrong by measurement, not by degree. Fixed
by scoping `hook.enter` to `shell.before`/`mcp.before` only (Decision §1): the incident this record and
[/decisions/ad-135.md](/decisions/ad-135.md) both address is shell- or MCP-shaped, so nothing outside that
surface needs the record, and the resulting volume tracks `shell.start`'s, which this plane already carried
without incident.

**`tlc harness obs live` gained a second fix, for the same incident, on the read side.** A declared
`LIVE_ALLOWLIST` (`observability.types.ts`) existed, unread by `obs-cli.ts`, for exactly the purpose of
keeping this command's tail meaningful. `obs-cli.ts`'s `live` command now reads a wider raw window, filters to
`LIVE_ALLOWLIST`, then truncates to the requested count — filtering before truncating, not after, or the
screen goes empty instead of decluttered. This is defense in depth alongside the scope fix above: even a
future addition to the signal plane that is *not* filtered at the write side stays contained at the read side
for this one command.

**This closes the *visibility* gap, not the incident.** If the cause turns out to be a host-side timeout, this
record does not fix it — a future record would, once the cause is confirmed. If `hook.enter` itself is absent
on the next occurrence, that is new information this project did not have before, not evidence this record
failed.

**Every existing test asserting an exact `obs.jsonl` record count needed updating.** `hook.enter` fires for
every `shell.before`/`mcp.before` invocation, so tests that counted records by an exact literal number — not
by kind — needed either an updated count or a filter for `hook.enter` specifically, depending on whether the
test was about `hook.enter` itself or about something else entirely that happened to share the file.

**`hook.enter` never reaches the global spool, unlike every typed `recordObs`-produced signal record.**
`recordAdapterEvent`'s `appendRecord` writes only the project's own `obs.jsonl`; it does not call
`appendSpoolRecord` the way `recordObs` does when `obs.globalSpool` is on. This follows the same bypass the
pre-existing `adapter.*` records already have, for the same reason (no provider/session at the point the
other three fire — though `hook.enter` itself does have both by the time it fires). The practical effect:
`hook.enter` is the one signal-level record absent from a spooled, cross-repository corpus. Accepted, not
fixed here — spooling it would mean either widening `ObsKind` for one more adapter-boundary member or adding
a second, narrower spool call, and nothing has asked for `hook.enter` in the spool yet.

**`recordHookEnter` bypasses `observability.enabled`, same as the three pre-existing `adapter.*` records it
shares a helper with.** An operator who sets `obs.enabled: false` still gets `hook.enter` written, contradicting
what `docs/diagnose.md` tells an operator to expect from that switch. Accepted, not fixed here: `hook.enter`
fires deliberately before `loadPolicy` runs, so the policy value that would gate it does not exist yet at the
point it fires — checking it would mean either moving the record after `loadPolicy` (reopening the exact
window this record exists to cover) or a second, `loadPolicy`-independent read of the same config value (the
duplication [/decisions/ad-100.md](/decisions/ad-100.md) argues against). The pre-existing `adapter.*` records
share this bypass already; unlike them, `hook.enter` fires on every gate-relevant invocation rather than a rare
failure, so the practical exposure is larger, and named here rather than left implicit.

## Not decided here

- **A fix for the host-timeout hypothesis, or any other candidate cause for the second gap.** Not evidenced;
  this record adds only the visibility that would confirm or rule it out on the next occurrence.
- **Instrumentation inside `bin/tlc-exec.mjs`, before the TS handler runs at all.** The failure modes
  reachable at that layer (`spawnSync` error, missing `dist/`, wrong Node version) are deterministic
  environment conditions that do not match this incident's shape — one command denied correctly, the next,
  seconds later in the same session, left no trace at all. Reaching that layer would also require buffering
  and re-parsing stdin before the child process consumes it, a materially riskier change than this record's
  evidence justifies.
- **Reproducing the incident's timing/concurrency conditions live.** Would require two real, concurrent host
  sessions against the same project directory — outside what an automated test in this repository can set up.
- **A test that discriminates the exact statement position of `recordHookEnter` relative to the three
  statements between it and `handler(event, context)`.** The unsensed window is not one line — it is
  `loadPolicy`, `upsertParentModelState`, and `presence.heartbeat`, all three. Each writes through its own
  `try`/`catch` that swallows every error (`policy.loader.ts`'s `readJsonFile`, `presence.store.ts`, and
  `subagent-policy.parent-model.ts`'s own local write), so none of them fails in an observable way a test
  could use to prove `hook.enter` was written *before* any of them, as opposed to merely before
  `handler(event, context)` itself (which a real throwing handler does prove, and is tested — moving the call
  to immediately before `handler` is caught). The code is written in the position the design states; a
  discrimination test for the exact position ahead of all three would need either a dependency-injection seam
  none of them otherwise needs, or an implementation-mirroring test this project's own testing discipline
  forbids. Named rather than silently left — the same choice AD-130 made for `matchesApiShape`'s `repoRemote`
  spawn-avoidance, which a Verifier independently flagged and recorded on this feature too.

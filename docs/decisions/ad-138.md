# AD-138 — a pr-open rule's own denial names its draft escape hatch

- **status**: active

## Decision

1. **`rules.trigger.ts` gains `TRIGGER_ESCAPE_HATCH_HINT`, a `Partial<Record<RuleTrigger["kind"], string>>`
   colocated immediately after `SHELL_SHAPES`.** Today only `"pr-open"` has an entry — the one trigger kind
   whose `SHELL_SHAPES` shape carries an `excludeIfAny`. The two facts sit next to each other on purpose: a
   future trigger gaining its own `excludeIfAny` shape has this constant right beside the reminder that its
   own message may need one too.
2. **`ruleMessage` (`rules.decide.ts`) looks up `TRIGGER_ESCAPE_HATCH_HINT[rule.on.kind]` and, when present,
   inserts it between the harness's own `rule <name> (<tier>): missing ...` / `WHY_POINTER` head and the
   operator's own `body`.** The operator's body is untouched — same verbatim text, same position relative to
   everything after the hint, whether the hint is present or not.
3. **The hint is generated unconditionally for every `pr-open` rule, regardless of what the operator wrote in
   their own rule body.** It requires nothing from the operator — not a checklist item to remember, not a
   convention to follow — and it appears even when the rule's own `body` is empty.
4. **No change to `SHELL_SHAPES` itself, to which shell shapes exist per trigger, or to any other message.**
   This record only makes an already-existing, already-correct mechanism's reasoning visible at the one moment
   an agent actually reads it.

## Why

**AD-118 built the mechanism; nobody made it speak for itself.** `gh pr create --draft`/`-d` was excluded
from `pr-open` for a real reason — a draft is not yet open for review, so a rule gating `pr-open` has no
proof to demand of it, and it is also the only way a proof that itself depends on the pull request already
existing can ever run. AD-118 itself added the explanation to `docs/concepts.md` and to
`skills/harness-init/SKILL.md`'s rule-authoring checklist — both read by a human writing a rule, or by an
agent helping one write it. Neither is read by an agent mid-denial, holding a blocked `gh pr create` and no
docs open.

**Confirmed live, not theoretical.** An operator's own `pr-open` rule denied a real `gh pr create`. The
rule's own body explained a different remediation in detail (spawn a specific review subagent) and never
mentioned draft at all — reasonable, since the operator writing that rule was solving their own review
requirement, not re-deriving AD-118's own reasoning from scratch. The agent had no way to discover `--draft`
existed; a human had to say so by hand, the exact class of repeated, avoidable friction this project's own
lessons discipline exists to close.

**Generated once, in the harness, reaches every operator's rule without asking any of them to write
anything.** The alternative — asking every author of a `pr-open` rule to remember and repeat AD-118's own
escape hatch in their own body — does not scale past the first rule that forgets, and there is no way for
the harness to know whether an operator's prose already covers it well enough to skip. Saying it once,
automatically, at the point of denial, costs nothing on the healthy path (a rule whose proof holds produces
no message at all, per AD-034) and reaches every project, not just the one that hit it first.

## Trade-offs

**One more line of harness-authored text in every `pr-open` denial, even when the operator's own body
already explains the same thing.** Accepted: repetition in a denial message an agent reads once per genuine
block is a smaller cost than an agent that cannot discover the escape hatch at all, and the hint is short
enough not to bury the operator's own body beneath it.

**`TRIGGER_ESCAPE_HATCH_HINT` and `SHELL_SHAPES`'s own `excludeIfAny` are two separate structures an author
must remember to keep in sync by hand, not one derived from the other.** Considered deriving the hint text
mechanically from `SHELL_SHAPES`'s own `prefix`/`excludeIfAny` values instead. Rejected: the hint's most
important sentence — that `gh pr ready` is itself gated the normal way — is not a fact `SHELL_SHAPES` encodes
anywhere; it is editorial context about a *different* shape in the same array. Colocating the two constants
in the same file, immediately adjacent, is the cheaper correctness measure available today, given exactly one
trigger kind has this property.

## Not decided here

- **A generic mechanism for any future trigger's own escape hatch, beyond the one entry this record adds.**
  Not evidenced as needed; `TRIGGER_ESCAPE_HATCH_HINT`'s own type (`Partial<Record<RuleTrigger["kind"],
  string>>`) already accepts a second entry the day a second trigger kind needs one.
- **Whether an operator's own rule body can suppress or reword the harness's hint.** Not asked for; the
  operator's body already renders in full, unedited, immediately after the hint — a rule author who wants to
  add their own words about draft does so in their own body, same as any other context.
